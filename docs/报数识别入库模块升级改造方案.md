# 报数识别入库模块升级改造方案

## 1. 背景

当前系统已经完成固定产品二维码模式：管理员可以提前将一批二维码绑定到某一种产品，并在需要时打印使用。基于这个能力，可以重新设计之前的“自动入库”功能。

本次改造不再追求完全无人值守，而是做成：

> 报数文本识别 → 系统生成临时入库草稿 → 用户检查确认 → 系统自动分配固定产品二维码 → 创建真实任务 → 页面内直接确认入库

因此，本功能建议命名为：

- 智能报数入库

不建议直接叫“自动入库”，避免给甲方造成“系统可以完全替代人工判断”的误解。

此前已有部分逻辑，主要在
src\main\java\com\Laibin\SugarInventory\service\impl\AutoInboundConfirmServiceImpl.java
src\main\java\com\Laibin\SugarInventory\service\impl\AutoInboundParseServiceImpl.java

---

## 2. 本次改造目标

### 2.1 业务目标

1. 管理员或仓管人员输入一段报数文本。
2. 系统根据产品表、库位表等上下文识别出入库明细。
3. 系统生成一个 Redis 临时草稿，而不是立即创建正式 `pallet_task`。
4. 前端展示识别结果，让用户确认、补全、修改。
5. 用户选择“使用固定产品二维码”后，系统自动从固定产品二维码池中分配空闲码。
6. 系统根据分配结果创建真实二维码任务。
7. 系统直接在当前页面完成确认入库，不再跳转任务确认页。
8. 页面展示最终绑定二维码、入库位置、成功/失败原因。

### 2.2 技术目标

1. 复用现有二维码任务和入库确认链路。
2. 保持现有 `pallet_task`、`pallet_code`、`inventory`、`pallet_flow_record` 的主链路不被破坏。
3. 把 AI 模型限定在“文本解析”环节，不允许模型直接写库或直接创建正式任务。
4. 所有业务校验、二维码分配、库存写入、状态更新均由后端确定性代码完成。
5. 支持后续扩展为 Agent Skill，但第一阶段不要做过度复杂的 Agent 框架。

---

## 3. 核心业务规则

### 3.1 成品和半成品必须分开

一段报数文本中不允许同时包含成品和半成品。

允许示例：

```text
4月27日 黄中冰 10板 1号库位
4月28日 黄中冰 8板 2号库
```

不允许示例：

```text
4月27日 黄中冰 10板
4月28日 黄冰糖 8板
```

如果模型判断报数文本同时包含成品和半成品，应返回：

```json
{
  "parseStatus": "NEED_SPLIT",
  "message": "本次报数同时包含成品和半成品，请拆分后分别提交"
}
```

前端提示用户拆分后重新提交。

---

### 3.2 模型不能确定的字段必须留空

模型解析时必须遵守：

> 不能确定的字段返回 `null`，不能猜。

例如：

- 产品名称模糊或找不到，不能确认产品 ID：`productId = null`
- 库位名称模糊或找不到，不能确认库位：`warehouseName = null`
- 侧别未提到：`side = null`
- 日期未提到：可按规则默认当天，但必须标记为默认值

前端需要把空字段高亮展示，由用户手动补全。

---

### 3.3 建议用户严格使用产品表和库位表中的名称

报数输入页需要给出提示：

> 请尽量按照系统中的产品名称、库位名称进行报数，例如：“黄中冰 10板 2026年4月1日 入库1号库左侧”。

如果使用俗称、简称、错别字，系统可以尝试匹配，但不能保证一定成功。

---

### 3.4 固定产品二维码规则

本功能只从“固定产品二维码池”中分配二维码。

分配条件：

1. 二维码属于当前产品。
2. 二维码状态为 `FREE`。
3. 二维码未作废。
4. 二维码当前没有未完成任务。
5. 同一批确认过程中必须加锁，避免并发重复分配。

分配顺序：

> 空闲时间最长的二维码优先。

如果没有空闲时间字段，可以暂时用：

```text
updated_at ASC, id ASC
```

表示越久未更新的二维码越优先被使用。

---

### 3.5 散件处理规则方案

> 每次散件录入必须绑定一个新二维码。  
> 不满一板按一个板位占用，一批散件共用一个二维码。  
> 不允许后续散件补入已有不满一板的二维码库存。

规则说明：

1. 一个二维码最多对应一条 `inventory` 记录。
2. 整板：一个二维码代表一板。
3. 散件：一个二维码代表一批不满一板的散件。
4. 散件也占用一个板位。
5. 散件实际件数写入 `inventory.pieces`。
6. 不允许把新散件补到已有散件库存行。
7. 不允许一个二维码承载超过一板的散件。
8. 如果散件数量超过每板件数，必须先标准化为整板 + 剩余散件，再分别分配二维码。

---

## 4. 数量拆分规则

报数文本可能包含：

- 整板
- 散件
- 多板多件

系统必须在分配二维码前统一拆分。

### 4.1 输入字段

每条识别明细中建议保留：

```json
{
  "boardCount": 3,
  "pieceCount": 10
}
```

其中：

- `boardCount`：板数，可以为 0
- `pieceCount`：件数，可以为 0
- `piecesPerPallet`：产品每板件数，从产品表获取

---

### 4.2 标准化公式

```text
extraBoards = pieceCount / piecesPerPallet
remainingPieces = pieceCount % piecesPerPallet

finalBoardCount = boardCount + extraBoards
finalPieces = remainingPieces

requiredQrCount = finalBoardCount + (finalPieces > 0 ? 1 : 0)
```

---

### 4.3 示例

假设每板 25 件。

#### 示例 1：3 板

```text
输入：3板
拆分：3个整板二维码
需要二维码：3个
```

结果：

```text
二维码1：1板
二维码2：1板
二维码3：1板
```

#### 示例 2：3 板 10 件

```text
输入：3板10件
拆分：3个整板二维码 + 1个散件二维码
需要二维码：4个
```

结果：

```text
二维码1：1板
二维码2：1板
二维码3：1板
二维码4：10件
```

#### 示例 3：10 件

```text
输入：10件
拆分：1个散件二维码
需要二维码：1个
```

结果：

```text
二维码1：10件
```

#### 示例 4：60 件

```text
输入：60件
每板：25件
标准化：2板10件
需要二维码：3个
```

结果：

```text
二维码1：1板
二维码2：1板
二维码3：10件
```

#### 示例 5：2 板 40 件

```text
输入：2板40件
每板：25件
标准化：3板15件
需要二维码：4个
```

结果：

```text
二维码1：1板
二维码2：1板
二维码3：1板
二维码4：15件
```

## 5. 单个二维码任务约束

为了保证追溯一致性，单个二维码任务只允许以下两种情况：

### 5.1 整板任务

```json
{
  "quantity": 1,
  "unit": "0"
}
```

含义：

```text
1板
```

### 5.2 散件任务

```json
{
  "quantity": 10,
  "unit": "1"
}
```

含义：

```text
10件，占1个板位
```

### 5.3 禁止情况

单个二维码禁止承载：

```json
{
  "quantity": 3,
  "unit": "0"
}
```

也禁止件数超过每板上限：

```json
{
  "quantity": 60,
  "unit": "1"
}
```

这些都必须在上层拆分为多个二维码任务。

## 6. 整体流程设计

### 6.1 流程总览

```text
1. 前端提交报数文本
   ↓
2. 后端构造业务上下文
   - 产品候选
   - 库位候选
   - 单位规则
   - 日期规则
   ↓
3. 调用模型解析报数文本
   ↓
4. 后端对模型结果做强校验
   ↓
5. 后端生成 Redis 临时入库草稿（保存一天）
   ↓
6. 前端展示草稿
   - 已识别字段
   - 缺失字段
   - 二维码需求数量
   - 可用二维码数量
   - 风险提示
   ↓
7. 用户补全并确认
   ↓
8. 后端锁定固定产品二维码池中的 FREE 码
   ↓
9. 后端创建真实二维码任务
   ↓
10. 后端直接确认入库
   ↓
11. 前端展示入库结果
```

---

### 6.2 临时草稿阶段

临时草稿只存 Redis，不落 `pallet_task`。

原因：

1. 模型解析结果可能有错。
2. 用户可能取消。
3. 字段可能不完整。
4. 二维码还没有正式绑定。
5. 不应污染任务中心。

Redis Key 建议：

```text
report-inbound:draft:{draftId}
```

过期时间建议：

```text
24小时
```

允许用户查询历史草稿并修改、确认

---

### 6.3 正式提交阶段

用户确认后，后端才开始真实写库。

正式提交必须放在同一事务中处理：

1. 校验草稿状态。
2. 校验字段完整。
3. 校验产品状态一致。
4. 校验固定产品二维码数量充足。
5. 加锁选取二维码。
6. 调用现有绑定逻辑创建 `pallet_task`。
7. 调用现有确认入库逻辑写入库存。
8. 写入流转记录。
9. 更新草稿状态为 `COMMITTED`。
10. 返回结果。

如果中途失败，整个事务回滚。

## 8. 模型输出 JSON Schema

模型只输出解析结果，不直接输出正式任务。

建议模型输出：

```json
{
  "parseStatus": "READY",
  "productStatus": "半成品",
  "items": [
    {
      "lineNo": 1,
      "rawText": "黄中冰3板10件，入库1号库左侧",
      "productNameRaw": "黄中冰",
      "productId": 101,
      "warehouseNameRaw": "1号库",
      "warehouseName": "1",
      "side": "左",
      "productionDate": "2026-04-24",
      "boardCount": 3,
      "pieceCount": 10,
      "confidence": 0.92,
      "reason": "产品名称和库位名称均为精确匹配"
    }
  ],
  "warnings": []
}
```

### 字段要求

| 字段 | 说明 |
|---|---|
| parseStatus | READY / NEED_REVIEW / NEED_SPLIT / FAILED |
| productStatus | 半成品 / 成品 |
| lineNo | 文本中的明细行号 |
| rawText | 原始片段 |
| productNameRaw | 用户原始输入产品名 |
| productId | 后端候选中的产品 ID，不能确定则为 null |
| warehouseNameRaw | 用户原始输入库位 |
| warehouseName | 后端候选中的库位名，不能确定则为 null |
| side | 左 / 右，不能确定则为 null |
| productionDate | 生产日期，不能确定则为 null 或由规则默认 |
| boardCount | 板数 |
| pieceCount | 件数 |
| confidence | 置信度 |
| reason | 匹配说明 |

## 9. 上下文包设计

### 9.1 不建议每次传全量产品表和库位表

为了节省 token，不建议每次把全量产品表、全量库位表都发送给模型。

推荐做法：

1. 后端先从报数文本中提取关键词。
2. 根据关键词在产品表、库位表中做本地候选匹配。
3. 只把候选产品、候选库位传给模型。
4. 模型只能在候选列表里选择。
5. 候选外不能猜，必须返回空。

---

    "库位必须从候选库位中选择",
    "散件不允许补入已有二维码，每次散件录入必须新分配二维码",

### 9.3 关于 CAR 包 / Agent Skill

这里可以借鉴“上下文包”的思路，但第一阶段不建议真的做复杂的 Agent Skill 运行时。

建议先实现：

```text
后端动态生成上下文包
  ↓
模型按照固定 Prompt + JSON Schema 解析
  ↓
后端校验
```

后续如果要升级为 Agent Skill，可以把以下内容封装成 Skill：

1. 输入定义。
2. 上下文包生成。
3. JSON Schema。
4. 校验工具。
5. 固定产品二维码分配工具。
6. 创建任务工具。
7. 确认入库工具。

接口：

```http

```

```json

  "productStatus": "半成品",
  "productionDateDefault": "2026-04-24"
}
```

返回：

```json
{
  "draftId": "RI202604240001",
  "parseStatus": "READY",

接口：

```

用于前端刷新草稿或返回页面后恢复数据。

### 10.5 取消草稿

接口：

```http

```

用途：

取消 Redis 临时草稿，不影响正式任务和库存。

如果草稿已提交，不允许删除，只能查看历史结果或重新生成新的报数草稿。

## 11. 后端服务设计

建议新增模块：

```text
reportinbound
```

或：

```text
intelligentinbound
```

### 11.1 ReportInboundController

职责：

1. 接收报数文本。
2. 查询草稿。
3. 更新草稿。
4. 提交草稿。
5. 取消草稿。

### 11.2 ReportInboundParseService

职责：

1. 构造上下文包。
2. 调用模型。
3. 解析模型 JSON。
4. 返回原始解析结果。

### 11.3 ReportInboundDraftService

职责：

1. 创建 Redis 草稿。
2. 查询 Redis 草稿。
3. 更新 Redis 草稿。
4. 设置过期时间。
5. 管理草稿状态。

### 11.4 ReportInboundValidateService

职责：

1. 校验产品。
2. 校验产品状态。
3. 校验库位。
4. 校验侧别。
5. 校验数量。
6. 校验二维码余量。
7. 校验库位容量。
8. 生成缺失字段和警告信息。

### 11.5 FixedQrAllocationService

职责：

1. 根据产品 ID 和数量查询空闲固定二维码。
2. 使用 `FOR UPDATE` 加锁。
3. 按空闲时间顺序分配。
4. 校验数量是否充足。
5. 返回分配结果。

### 11.6 ReportInboundCommitService

职责：

1. 读取草稿。
2. 执行幂等校验。
3. 调用 `FixedQrAllocationService` 分配二维码。
4. 按任务项创建二维码任务。
5. 调用确认入库逻辑。
6. 记录结果。
7. 更新草稿状态。

## 12. 正式提交时的执行细节

### 12.1 分配二维码

每条草稿明细经过数量拆分后会得到多个 `taskItems`。

每个 `taskItem` 都需要一个二维码。

分配时按产品维度批量取码：

```text
productId = 当前产品
status = FREE
fixedProduct = true
ORDER BY updated_at ASC, id ASC
LIMIT requiredQrCount
FOR UPDATE
```

如果数量不足，整批失败。

错误示例：

```text
黄中冰需要 4 个空闲二维码，当前固定产品二维码池仅有 2 个，请先补充打印或释放二维码。
```

---

### 12.2 创建真实任务

分配到二维码后，对每个二维码调用现有绑定逻辑，生成真实 `pallet_task`。

整板：

```json
{
  "code": "BT000A",
  "productId": 101,
  "productStatus": "半成品",
  "productionDate": "2026-04-24",
  "quantity": 1,
  "unit": "0",
  "remark": "报数识别入库"
}
```

散件：

```json
{
  "code": "BT000D",
  "productId": 101,
  "productStatus": "半成品",
  "productionDate": "2026-04-24",
  "quantity": 10,
  "unit": "1",
  "remark": "报数识别入库：散件"
}
```

---

### 12.3 直接确认入库

创建任务后，不跳转任务中心，直接调用现有确认入库逻辑。

确认项示例：

```json
{
  "code": "BT000A",
  "warehouseName": "1号库",
  "entryDate": "2026-04-24",
  "side": "左",
  "quantity": 1,
  "unit": "0",
  "remark": "报数识别入库"
}
```

散件确认项：

```json
{
  "code": "BT000D",
  "warehouseName": "1号库",
  "entryDate": "2026-04-24",
  "side": "左",
  "quantity": 10,
  "unit": "1",
  "remark": "报数识别入库：散件10件"
}
```

### 12.4 化验处理

本功能不强制要求化验先存在。

如果系统当前已经支持化验后关联，则报数入库直接沿用现有规则：

1. 入库时可以没有 `assayId`。
2. 根据产品 ID + 生产日期后续解析化验。
3. 有唯一化验结果时自动回填。
4. 无化验不阻断入库。
5. 多候选化验不自动绑定，由前端提示人工确认。

## 14. 容量处理策略

第一阶段不建议做复杂自动换库位。

建议规则：

1. 如果指定库位容量足够，直接入库。
2. 如果指定库位容量不足，草稿阶段提示风险。
3. 用户必须手动改库位或减少数量。
4. 第一阶段不要让模型自动拆分到多个库位。
5. 后续可以扩展“系统推荐库位”。

风险提示示例：

```text

```

## 15. 并发与幂等

### 15.1 并发控制

正式提交时必须加锁：

1. 固定产品二维码池取码加锁。
2. 库位分配加锁。
3. 同一草稿提交加锁。
4. 同一个二维码状态更新加锁。

二维码选取必须使用类似：

```sql
SELECT *
FROM pallet_code
WHERE product_id = ?
  AND status = 'FREE'
  AND fixed_product_flag = 1
ORDER BY updated_at ASC, id ASC
LIMIT ?
FOR UPDATE;
```

具体字段按当前固定产品二维码实现调整。

---

### 15.2 幂等控制

草稿需要有状态：

```text
DRAFT
COMMITTING
COMMITTED
CANCELED
EXPIRED
FAILED
```

提交时：

1. 如果状态不是 `DRAFT`，不允许重复提交。
2. 提交开始先改为 `COMMITTING`。
3. 成功后改为 `COMMITTED`。
4. 失败后改为 `FAILED`，记录失败原因。
5. 前端重复点击时返回已有结果或提示正在处理中。

---

## 16. 流转记录要求

每个二维码仍然要写入正常流转记录。

整板入库：

```text
绑定半成品 / 绑定成品
半成品入库 / 成品入库
```

散件入库：

```text
绑定半成品 / 绑定成品
半成品入库 / 成品入库
```

但 `ext_data` 或 `remark` 中必须记录：

```json
{
  "source": "REPORT_INBOUND",
  "draftId": "RI202604240001",
  "lineNo": 1,
  "quantityText": "10件",
  "isPieces": true,
  "pieces": 10,
  "occupyPalletSlot": true
}
```

前端展示时应显示：

```text
10件，占1板位
```

## 17. 与现有散件规则的关系

本模块采用方案 1：

> 每次散件录入必须绑定新码。

因此需要保证二维码入库链路中：

1. 不允许散件补入旧库存行。
2. 有 `palletCodeId` 的散件入库必须新建一条 `inventory`。
3. 一个二维码最多对应一条 `inventory`。
4. 如果查询到同一个二维码有多条库存记录，应报数据异常。
5. 散件数量不能大于等于产品每板件数，必须提前拆分。

如果旧版非二维码入库仍保留“散件凑板”逻辑，可以暂时只限制二维码链路：

```text
有 palletCodeId：严格一批散件一个二维码
无 palletCodeId：可暂时沿用旧逻辑
```

但长期建议统一散件模型，减少歧义。

### 20.2 数量拆分

1. 3板 → 3个任务。
2. 10件 → 1个任务。
3. 3板10件 → 4个任务。
4. 60件 → 3个任务。

1. 二维码数量充足。

4. 不允许取其他产品二维码。

## 21. 给 Codex 的执行要求

请按本方案实现“报数识别入库”模块。

### 核心原则

1. AI 只负责文本解析。
2. 后端负责所有业务校验和执行。
3. 临时结果存 Redis，不直接落 `pallet_task`。
4. 用户确认后才分配二维码并创建真实任务。
5. 真实任务仍复用现有二维码任务链路。
6. 每个二维码最多对应一条库存记录。
7. 每次散件录入必须绑定一个新二维码，不允许补入旧散件。
8. 多板多件必须拆分成多个二维码任务。
9. 成品和半成品不能混在一次报数中。
10. 前端必须支持用户补全空字段后再提交。

### 优先实现顺序

1. 先实现数量拆分和二维码需求计算。
2. 再实现 Redis 草稿。
3. 再实现模型解析接口。
4. 再实现固定二维码分配。
5. 再实现创建真实任务和确认入库。
6. 最后做前端页面和结果展示。

## 22. 总结

本次升级的核心不是让模型直接操作库存，而是建立一个安全可控的流程：

> 报数文本 → AI 解析 → 后端校验 → Redis 草稿 → 用户确认 → 固定二维码分配 → 真实任务 → 确认入库

散件规则采用甲方确认的方案 1：

> 每次散件录入必须绑定新码；不满一板按一个板位处理；多板多件必须拆分；一个二维码最多对应一条库存记录。

该方案改造量适中，能最大程度复用现有二维码状态机、任务确认、库存写入和流转追溯能力，同时为后续 Agent Skill 化预留空间。
