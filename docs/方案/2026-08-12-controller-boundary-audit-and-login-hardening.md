# Controller 分层、异常、审计与登录安全收口

日期：2026-08-12

范围：传统仓储 Controller、生产 Controller、通用操作日志切面、Web 登录与登录页持久化

结论：代码与自动化测试已完成；真实浏览器验收结果见本文末尾

## 1. 本轮解决的问题

历史实现中存在以下生产化债务：

1. 多个 Controller 捕获 `BusinessException` 或 `Exception` 后直接拼接并返回异常消息，绕过了统一异常处理；部分路径还调用 `printStackTrace` 或 `System.out`。
2. `OperationLogAspect` 用一个大 `try/catch` 包围审计准备、业务调用和审计落库。业务方法抛异常或审计落库失败时，兜底分支会再次调用 `joinPoint.proceed()`，存在重复写业务数据的风险。
3. 产品、库位、筛网、员工、操作日志、质量标准、批量化验组和生产订单等接口直接接收或返回 PO。
4. 员工、出入库、托盘任务、RBAC、生产订单等真实写路径缺少通用操作日志注解；产品库位查询误标为删除审计。
5. Web 登录共享口令硬编码在 Java 源码中；前端“记住登录”会将密码随 Pinia 状态持久化。
6. 更新不存在的库位时会空指针，最终只能得到不稳定的通用 500。

## 2. 异常边界

- 39 个 Controller 当前没有本地 `catch` 块，也没有 `System.out`、`System.err` 或 `printStackTrace`。
- 业务校验继续抛 `BusinessException`，由 `GlobalExceptionHandler` 保留稳定业务码和业务消息。
- 未预期异常只在全局处理器记录完整服务端日志，客户端统一收到“服务异常，请稍后重试”，不再暴露类名、SQL 或内部堆栈。
- `WarehouseServiceImpl` 对查询、状态变更、更新和删除不存在库位统一返回 `WAREHOUSE_NOT_FOUND(1023)`。

## 3. 审计切面的一次执行保证

`OperationLogAspect` 将执行状态明确拆成三种：

1. 审计准备失败、业务尚未执行：记录错误后只执行一次业务方法；
2. 业务方法已经开始但抛出异常：原异常向上抛出，绝不重放；
3. 业务已成功、审计落库失败：记录审计故障并返回原业务结果，绝不重放。

同时补充了以下约束：

- 无认证上下文时安全回退为 `system`，不再空指针；
- 忽略空值、零值和重复 ID；
- 没有数字主键的批量 DTO 仍会形成一条操作摘要；
- `password`、`authorization`、`token`、`secret`、`openid`、`sessionKey` 等字段不会写入通用审计载荷；
- 只读的 `ProductController#getProductWarehouse` 已移除错误的 `DELETE` 审计。

自动入库确认、Agent L3 确认/执行与 Agent 会话继续使用各自的专用控制面/审计表，不重复套用通用操作日志表达其安全状态机。

## 4. DTO/VO 边界

新增 `ManagementViewAssembler`，Controller 只负责 DTO/VO 与业务调用编排，Service/Mapper 继续使用实体：

| 模块 | 请求/响应收口 |
| --- | --- |
| 员工 | 新增使用 `EmployeeCreateDTO`；查询、更新返回 `EmployeeRosterVO` |
| 产品 | 查询、分页、更新返回完整 `ProductVO` |
| 筛网 | 列表、分页、新增、更新返回 `ScreenMeshVO` |
| 库位 | 查询、新增、更新、状态变更返回 `WarehouseVO` |
| 操作日志 | 分页返回 `OperationLogVO` |
| 质量标准 | 新增、更新返回 `QualityStandardVO` |
| 批量化验组 | 更新返回 `AssayGroupVO`，关联产品改为 `ProductVO` |
| 生产订单 | 新建返回 `ProductionOrderBaseVO`；打印状态更新返回 `ProductionOutputCodeVO` |

VO 保留当前前端所需字段，避免借分层整改改变页面合同。

## 5. 写操作审计覆盖

通用审计已补齐到员工导入/新增、成品及半成品出入库、托盘码及任务流转、角色与权限维护、生产订单/领料/产出/标签、煮糖批次等业务写入口。当前 Controller 共登记 76 个 `@LogOperation` 方法。

通用审计是面向操作日志页面的补充留痕。事务级安全链路仍以领域事务和专用执行台账为准，不能用通用 AOP 日志替代幂等、确认令牌或 L3 审计。

## 6. 登录安全

- Java 源码不再包含默认 Web 登录口令；运行环境必须提供 `WEB_LOGIN_PASSWORD`。
- 启动门禁要求 Web 口令至少 12 位且不能是占位值；`JWT_SECRET` 必须为有效 Base64，解码后至少 64 字节以满足 HS512。
- 简易部署的 `init-env.sh` 会生成随机 Web 登录口令并写入权限受控的 `.env`。
- 登录页文案改为“记住用户名”，持久化状态只保留 `{name}`。
- 历史持久化对象中的明文 `password` 会在登录页初始化时清除。
- 当前仍是“员工身份 + 环境共享口令”模式，并非逐用户密码体系；SSO 或逐用户凭证属于后续身份架构议题。

## 7. 自动化验证

- 后端：108 个测试套件、416 个测试，0 failure / 0 error / 0 skipped。
- 新增回归：审计故障和业务异常都只能调用业务方法一次；Controller 无本地异常吞噬/调试输出；关键写入口必须有审计；管理接口不能暴露 PO；不存在库位返回稳定业务码；源码无硬编码 Web 口令。
- 前端：`rememberedLogin.test.mjs` 2/2 通过，证明历史密码被剔除且只保留用户名。
- 前端生产构建通过。

## 8. 真实浏览器验收

使用桌面影子环境连接本地数据库、Redis 和前端开发服务器完成验收。桌面环境原有 JWT 密钥解码后只有 328 位，不满足 HS512 的 512 位最低要求；新启动门禁已在服务接收流量前准确拒绝该配置。验收进程仅在进程内覆盖随机 64 字节 JWT 密钥及一次性 Web 口令，没有修改桌面配置文件。

验收结果：

1. 管理员真实登录成功；浏览器本地存储中不存在 `password` 字段，也不存在验收口令明文，记住登录状态仅保存用户名。
2. 产品管理、库位管理和操作日志页面均能按新的 VO 合同加载；产品类型、状态、标准、包装、重量、件数、筛网与堆叠字段正常显示。
3. 更新不存在的库位返回业务码 `1023` 和“找不到库位”，没有产生数据写入。
4. 通过真实浏览器会话新增并删除唯一前缀库位；新增审计记录包含库位名，删除审计记录包含删除前快照，操作人均为当前登录员工，审计载荷没有敏感字段。
5. 操作日志页面可见新增、删除两条库位审计，分页响应保持 `total + records`。
6. 浏览器控制台 0 error；OpenAPI 快照与运行实例 214 条路径完全一致，Agent 上游注册表 60 条路径全部存在。
7. 验收库位、对应两条操作日志和临时权限账号/角色均在结束后清理，不保留测试业务数据。
