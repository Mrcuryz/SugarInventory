# 标签打印助手从 0 到 1 实施方案

## 1. 目标

当前系统打印二维码的方式是：

1. Web 端导出 PDF  
2. 用户手动下载 PDF  
3. 手动选择打印机打印  
4. 打印后再手动裁剪  

这种方式不适合标签打印机场景，操作链太长，且容易出现：

- 字体乱码
- 缩放错误
- 边距错位
- 二维码大小不稳定
- 批量打印效率低
- 需要人工裁剪

本次要改造成：

> Web 系统点击“打印”后，本地连接的 POSTEK 标签打印机直接打印标签；  
> 批量打印时，打印机连续出标签，不再依赖 PDF。

---

## 2. 核心结论

这里**不是重写打印机驱动**，而是开发一个安装在本地电脑上的：

- 打印助手
- 本地打印桥接程序
- 本地打印服务

其职责是：

1. 接收 Web 页面发来的打印请求  
2. 生成标签内容  
3. 调用本机已安装的 POSTEK 打印机  
4. 控制单张或批量连续打印  

整个链路为：

```text
Web 管理端
   ↓（HTTP 请求到本机）
本地打印助手
   ↓（调用 Windows 打印能力 / 厂家 SDK）
POSTEK 官方驱动
   ↓
POSTEK 标签打印机
```

---

## 3. 为什么必须做“本地打印助手”

浏览器 Web 页面天然不适合直接完成以下能力：

- 静默打印（不弹系统打印对话框）
- 指定某台本地标签打印机
- 精确控制标签尺寸
- 连续打印多张标签
- 稳定适配专用标签打印机

因此必须在打印机所在电脑上部署一个本地程序，专门负责桥接：

- Web 系统
- 本机打印机
- 标签打印模板

---

## 4. 一阶段推荐方案

### 推荐路线
先做：

> 本地打印助手 + 固定模板标签图片打印

即：

1. Web 端发送标签数据  
2. 本地打印助手收到后按固定模板生成标签图片  
3. 再调用系统打印机进行打印  

### 为什么先这样做
优点：

- 实现最快
- 调试最直观
- 可复用现有二维码生成能力
- 中文字体更容易控制
- 不需要一开始就研究 POSTEK 原生命令或 SDK

### 暂不做
第一阶段先不研究：

- POSTEK 原生打印指令
- 专用标签语言
- 更底层的 SDK 调用

这些可以放在第二阶段优化。

---

## 5. 第一阶段系统架构

```text
[Web 管理端]
    |
    | POST http://127.0.0.1:9527/print
    v
[本地打印助手]
    |
    | 生成标签图片
    | 调用系统打印机
    v
[Windows 中已安装的 POSTEK 打印机]
    |
    v
[标签打印机连续出纸]
```

---

## 6. 业务流程

## 6.1 单张打印流程

1. 用户在 Web 系统点击“打印”
2. 前端请求本地打印助手
3. 打印助手收到 1 条标签数据
4. 生成 1 张固定模板标签图
5. 调用 POSTEK 打印机打印
6. 标签机直接出 1 张标签

---

## 6.2 批量打印流程

1. 用户在 Web 系统勾选多条二维码
2. 点击“批量打印”或“打印并启用”
3. 前端将多条标签数据一次性发送给本地打印助手
4. 打印助手逐条生成标签图并循环打印
5. 标签机连续吐出多张标签

---

## 6.3 打印并启用流程（后续可接）

建议逻辑为：

1. Web 先调用后端接口完成“启用”或“打印并启用”
2. 后端返回成功后的标签数据
3. 前端再调用本地打印助手执行打印

这样可以避免：
- 打印成功但业务状态没更新
- 业务成功但打印失败的混乱

第一阶段也可以简单先做：
- 先业务后打印
- 打印失败只提示用户重打

---

## 7. 打印助手对外接口设计

本地打印助手建议提供本地 HTTP 服务，监听：

```text
127.0.0.1:9527
```

至少提供以下接口：

---

## 7.1 健康检查接口

### 请求
```http
GET /health
```

### 返回示例
```json
{
  "success": true,
  "message": "printer-assistant-online"
}
```

### 用途
Web 页面进入打印页时可先探测：
- 打印助手是否已启动
- 当前电脑是否具备打印能力

---

## 7.2 获取打印机列表

### 请求
```http
GET /printers
```

### 返回示例
```json
{
  "success": true,
  "data": [
    "POSTEK G-3106",
    "Microsoft Print to PDF"
  ]
}
```

### 用途
- 首次配置默认打印机
- 调试
- 打印机故障排查

---

## 7.3 打印接口

### 请求
```http
POST /print
Content-Type: application/json
```

### 请求体示例
```json
{
  "template": "fixed_product_qrcode",
  "printerName": "POSTEK G-3106",
  "copies": 1,
  "labels": [
    {
      "code": "BT000ZJM",
      "title": "黄中冰"
    },
    {
      "code": "BT000RLG",
      "title": "黄中冰"
    }
  ]
}
```

### 字段说明

- `template`：标签模板类型
- `printerName`：打印机名称，可为空；为空时用本地默认打印机
- `copies`：每张标签打印份数
- `labels`：标签数组
  - `code`：二维码内容 / 标签编号
  - `title`：产品名称或标签标题

### 返回示例
```json
{
  "success": true,
  "message": "打印任务已提交",
  "printedCount": 2
}
```

### 失败返回示例
```json
{
  "success": false,
  "message": "未找到打印机 POSTEK G-3106"
}
```

## 8. 标签模板建议

第一阶段不要做自由排版，直接做固定模板。

### 推荐模板内容
每张标签包含：

1. 顶部：产品名称
2. 中间：二维码
3. 底部：二维码编号

### 推荐标签尺寸
由现场实际标签纸决定，建议选一个固定尺寸，例如：

- 50mm × 30mm
- 60mm × 40mm
- 80mm × 60mm

第一阶段选定一个尺寸后，不做复杂多模板切换。

## 9. 技术实现原理

## 9.1 Web 端原理

Web 页面点击打印时，不再下载 PDF，而是直接调用本地服务：

```js
await fetch('http://127.0.0.1:9527/print', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    template: 'fixed_product_qrcode',
    printerName: 'POSTEK G-3106',
    copies: 1,
    labels: [
      { code: 'BT000ZJM', title: '黄中冰' }
    ]
  })
})
```

本质上只是一个普通 HTTP 请求，只不过目标地址不是后端服务器，而是本机上的打印助手。

---

## 9.2 打印助手原理

打印助手收到请求后：

1. 解析 JSON 请求体  
2. 检查打印机是否存在  
3. 根据模板把标签内容渲染成图片  
4. 将图片按固定纸张尺寸发送到指定打印机  
5. 返回成功或失败结果  

---

## 9.3 打印机原理

打印助手不直接控制 USB 底层协议，而是：

- 通过 Windows 已安装好的打印机
- 调用系统打印能力
- 借助 POSTEK 官方驱动完成最终打印

所以：

> 本项目开发的是“打印桥接层”，不是“打印机驱动层”。

---

## 10. 技术选型建议

考虑当前项目是 Java 后端，建议打印助手也优先使用 Java 实现，方便复用。

### 推荐技术栈
- Java 17 或 21
- 本地 HTTP 服务：
  - Spring Boot（更完整）
  - 或 JDK 自带 `HttpServer`（更轻量）
- 二维码生成：
  - ZXing
- 图片绘制：
  - `BufferedImage`
  - `Graphics2D`
- 打印能力：
  - Java Print Service（`javax.print` / `java.awt.print`）

### 第一阶段建议
优先选：

- Spring Boot / 轻量 HTTP 服务
- BufferedImage 画标签图
- Java Print Service 调用本机打印机

---

## 11. 打印助手模块设计

建议拆成以下模块：

### 11.1 HttpApiController
职责：
- 提供 `/health`
- 提供 `/printers`
- 提供 `/print`

---

### 11.2 PrinterDiscoveryService
职责：
- 获取本机打印机列表
- 检查默认打印机
- 校验指定打印机是否存在

---

### 11.3 LabelRenderService
职责：
- 根据模板和标签数据生成图片
- 控制二维码位置、产品名位置、编号位置
- 控制字体、边距、背景、尺寸

---

### 11.4 PrintExecutionService
职责：
- 接收渲染好的图片
- 按指定尺寸发送到系统打印机
- 支持单张和批量循环打印

---

### 11.5 LocalConfigService
职责：
- 保存默认打印机名称
- 保存标签尺寸
- 保存打印浓度或预留参数（如后续需要）

---

## 13. Web 端改造点

### 当前方式
- 导出 PDF
- 手动打印

### 改造后
新增前端打印能力：

1. 检查本地打印助手是否在线
2. 若在线，则直接请求本地打印接口
3. 若不在线，则提示用户：
   - 请先启动标签打印助手
   - 或退回原有 PDF 打印方案

### 建议保留兜底
第一阶段建议：

- 保留原 PDF 导出按钮
- 新增“直接打印”按钮

这样即使打印助手未安装，也不影响业务继续使用。

## 14. 常见异常与处理

### 14.1 打印助手未启动
表现：
- 请求 `127.0.0.1:9527` 失败

前端提示：
- 未检测到标签打印助手，请先启动本地打印助手

---

### 14.2 找不到打印机
表现：
- 指定打印机不存在
- 或驱动未安装

前端提示：
- 未找到指定打印机，请检查打印机连接与驱动安装

---

### 14.3 打印失败
表现：
- 驱动异常
- 打印机离线
- 标签纸缺失

前端提示：
- 打印失败，请检查打印机状态后重试

---

### 14.4 中文乱码
原因：
- 标签渲染图片时未正确加载中文字体

解决：
- 打印助手内置中文字体文件
- 不依赖系统默认字体

---

## 17. 给 Codex 的明确实现要求

### 目标
开发一个安装在本地电脑上的“标签打印助手”，用于桥接 Web 管理端与本地 POSTEK 标签打印机，实现单张和批量连续打印，不再依赖 PDF。

### 第一阶段要求
1. 使用 Java 实现本地打印助手
2. 打印助手启动后监听 `127.0.0.1:9527`
3. 提供接口：
   - `GET /health`
   - `GET /printers`
   - `POST /print`
4. `POST /print` 接收：
   - 模板类型
   - 打印机名称
   - 打印份数
   - 标签数组（每条包含 code、title）
5. 打印助手收到请求后，按固定模板生成标签图片
6. 通过 Windows 已安装的打印机将标签图片打印到指定 POSTEK 打印机
7. 支持：
   - 单张打印
   - 批量连续打印
   - 默认打印机
   - 测试打印
8. 第一阶段先不接 POSTEK 原生命令，优先走“图片打印到系统打印机”
9. 中文字体必须随程序打包，避免乱码
10. Web 端后续通过 `127.0.0.1:9527` 调用打印助手；第一阶段保留 PDF 导出作为兜底

---

## 18. 总结

本方案的本质不是开发打印机驱动，而是开发一个：

> **本地打印桥接程序**

它负责：

- 接收 Web 的打印请求
- 渲染标签
- 调用本机标签打印机
- 完成单张/批量连续打印

这样可以把当前“导出 PDF + 手工打印 + 手工裁剪”的流程，升级为：

> **系统点击打印 -> 标签机直接出纸**

这比继续优化 PDF 更适合工厂现场场景。
