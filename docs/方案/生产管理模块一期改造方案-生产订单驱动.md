# 生产管理模块一期改造方案：生产订单驱动半成品领用、成品产出贴码与入库追溯

## 1. 本文目标

本文用于交给 Codex 理解并实现新一阶段的“生产管理模块”。

本次不做完整 MES，不做客户订单、销售订单、生产计划排产、设备采集、工时统计、成本核算等大模块。

本次只补齐当前 WMS 最缺的一个生产源头：

> 通过“生产订单”把半成品领用、成品产出、成品二维码、成品入库串起来。

核心闭环：

```text
创建生产订单
  ↓
实际领用半成品二维码
  ↓
登记多种成品产出
  ↓
批量从固定产品二维码池分配成品二维码
  ↓
打印/发放二维码给现场贴码
  ↓
成品入库
  ↓
通过生产订单追溯半成品输入与成品输出
```

---

## 2. 系统定位

本模块不是完整 MES，而是：

> 轻量生产订单模块 / 生产追溯模块。

它应该做在现有系统中，作为一个一级菜单“生产管理”。

部署形态：

```text
同一个系统入口
同一个前端项目
同一个后端服务
同一个数据库
同一套登录和权限
```

不要新开服务器、不要新建独立 MES 域名、不要另起独立数据库。

建议后端按模块化单体分包：

```text
com.Laibin.SugarInventory.production
├── controller
├── service
├── mapper
├── domain
│   ├── dto
│   ├── po
│   └── vo
```

## 3. 核心业务规则

### 3.1 生产订单类型

生产订单区分两类：

```text
SEMI    半成品生产
FINISH  成品生产
```

### 半成品生产订单

用于生产半成品。

特点：

1. 可没有半成品领用。
2. 产出产品应为半成品。
3. 产出二维码走半成品入库任务 `SEMI_IN`。

### 成品生产订单

用于半成品加工成成品。

特点：

1. 通常需要扫码领用半成品。
2. 产出产品应为成品。
3. 产出二维码走成品入库任务 `FINISH_IN`。
4. 不做成品二维码与半成品二维码一对一绑定。
5. 成品通过生产订单追溯到本订单实际领用的半成品。

---

### 3.2 新流程不再强依赖备料池

新增生产订单后，新流程里“转备料池”不再作为必经步骤。

生产订单应该直接关联真实库存中的半成品二维码：

```text
真实库存中的半成品二维码
  ↓ 扫码/选择领用
生产订单材料记录
  ↓
生产产出
  ↓
成品二维码
  ↓
成品入库
```

生产订单材料表本身就是“订单专属备料池”。

旧备料池功能可以暂时保留，用于历史兼容或无订单提前备料，但新生产订单主流程不依赖旧备料池。

---

### 3.3 半成品领用时完成仓库出库

半成品领用时：

1. 用户选择生产订单。
2. 小程序扫码半成品二维码，或 Web 端从库存二维码列表中多选。
3. 用户确认领用。
4. 系统校验二维码在库。
5. 系统从仓库 `inventory` 中移除这板半成品。
6. 系统将这板半成品写入 `production_order_material`。
7. 系统写托盘/二维码流转记录。
8. 系统释放半成品二维码为 `FREE`。

注意：二维码释放后，后续不再通过该二维码追踪这板半成品的生产过程。生产订单材料记录会保存来源二维码、来源库位、产品、日期、重量等快照，用于追溯。

---

### 3.4 成品产出通过固定产品二维码池批量关联

在生产订单里登记实际产出：

```text
产品：40kg黄碎冰
数量：7板16件
```

系统根据产品每板件数拆分二维码需求：

```text
7个整板码
1个散件码
```

然后从该产品的固定产品二维码池中选取 `FREE` 状态二维码。

每个二维码创建对应的 `pallet_task`：

- 半成品产出：`SEMI_IN`
- 成品产出：`FINISH_IN`

创建后二维码进入待入库任务状态。后续二维码贴到产出的成品上，再走现有成品/半成品入库确认流程。

---

### 3.5 一张订单可以产出多种产品

例如：

```text
订单 PO202604280001 实际产出：
- 40kg黄碎冰：7板16件
- 40kg正碎冰：5板8件
- 15kg黄冰糖小颗粒：30件
```

因此结构是：

```text
production_order 1
  ↓
production_order_output N
  ↓
production_order_output_code N
```

---

### 3.6 不再做成品与半成品一一绑定

不再要求：

```text
成品二维码 BT001 必须绑定半成品二维码 BT100
```

而是：

```text
成品二维码 BT001 属于生产订单 PO001
半成品二维码 BT100 被生产订单 PO001 领用
```

追溯时通过生产订单查看输入与输出。

## 4. 生产订单状态机

### 4.1 状态枚举

第一版建议使用：

```text
DRAFT           草稿
ISSUED          已下发
MATERIALING     领料中
MATERIALED      已领料
OUTPUT_BINDING  成品贴码中
WAIT_INBOUND    待入库
PART_INBOUND    部分入库
COMPLETED       已完成
CANCELED        已取消
```

### 4.2 状态流转

```text
DRAFT / ISSUED
  ↓ 开始领料
MATERIALING
  ↓ 领料完成
MATERIALED
  ↓ 添加产出/绑定二维码
OUTPUT_BINDING
  ↓ 全部产出项完成二维码绑定
WAIT_INBOUND
  ↓ 部分二维码入库
PART_INBOUND
  ↓ 全部二维码入库
COMPLETED
```

半成品生产订单可以跳过领料：

```text
ISSUED
  ↓ 添加产出/绑定二维码
OUTPUT_BINDING
```

第一版可以简化：新建订单后直接进入 `ISSUED`。

## 5. 数据库设计

### 5.1 production_order 生产订单主表

```sql
CREATE TABLE production_order (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键',
    order_no VARCHAR(50) NOT NULL COMMENT '生产订单号',
    order_type VARCHAR(20) NOT NULL COMMENT '订单类型：SEMI/FINISH',
    status VARCHAR(30) NOT NULL COMMENT '订单状态',
    production_date DATE NOT NULL COMMENT '生产日期',
    planned_material_json JSON NULL COMMENT '计划半成品用量，仅参考',
    planned_output_json JSON NULL COMMENT '预计产出，仅参考',
    team_name VARCHAR(100) NULL COMMENT '班组/工序/负责人备注',
    remark VARCHAR(500) NULL COMMENT '备注',
    created_by INT NULL COMMENT '创建人ID',
    created_by_name VARCHAR(100) NULL COMMENT '创建人名称快照',
    created_at DATETIME NOT NULL COMMENT '创建时间',
    updated_at DATETIME NULL COMMENT '更新时间',
    completed_at DATETIME NULL COMMENT '完成时间',
    UNIQUE KEY uk_production_order_no (order_no),
    KEY idx_production_order_status (status),
    KEY idx_production_order_type (order_type),
    KEY idx_production_order_date (production_date),
    KEY idx_production_order_created_by (created_by)
) COMMENT='生产订单主表';
```

说明：

- `order_no` 后端自动生成。
- 新建订单时用户只需要填写订单类型、生产日期、计划用量、预计产量、备注等。
- 计划用量和预计产量只是参考，不参与库存扣减。

### 5.5 是否修改原有表

第一版尽量少侵入原有表。

推荐先通过 `production_order_output_code` 关联到 `pallet_task_id`、`pallet_code_id`。

如果查询方便需要，可以给原表加可空字段：

```sql
ALTER TABLE pallet_task
    ADD COLUMN production_order_id BIGINT NULL COMMENT '生产订单ID',
    ADD COLUMN production_output_id BIGINT NULL COMMENT '生产订单产出行ID';

ALTER TABLE inventory
    ADD COLUMN production_order_id BIGINT NULL COMMENT '生产订单ID',
    ADD COLUMN production_output_id BIGINT NULL COMMENT '生产订单产出行ID';
```

但第一版不强制。

### 7.5 确认领用半成品

```http
POST /api/production/orders/{id}/materials/pick
```

请求：

```json
{
  "palletCodeIds": [2001, 2002],
  "remark": "生产订单领用"
}
```

小程序扫码可传：

```json
{
  "palletCodes": ["BT000A"]
}
```

后端逻辑：

```text
1. 校验订单存在且未完成、未取消
2. 校验订单状态允许领料
3. 对每个二维码加锁查询
4. 校验二维码在库
5. 校验库存存在
6. 校验产品状态为半成品
7. 写 production_order_material
8. 删除或扣减 inventory
9. 更新 warehouse.cur_capacity
10. 写 pallet_flow_record：生产订单领用
11. 释放 pallet_code 为 FREE
12. 更新订单状态为 MATERIALING
```

确认领用后不建议第一版支持直接撤销。若误领，应走退料重新入库或管理员人工处理。


### 7.7 添加产出

```http
POST /api/production/orders/{id}/outputs
```

请求：

```json
{
  "productId": 301,
  "productionDate": "2026-04-28",
  "boardCount": 7,
  "pieceCount": 16,
  "remark": "筛分产出"
}
```

后端逻辑：

1. 校验订单存在。
2. 校验产品存在。
3. 根据订单类型校验产品状态：
   - SEMI 订单产出半成品
   - FINISH 订单产出成品
4. 根据产品 `piecesPerPallet` 标准化数量。
5. 计算 `requiredQrCount`。
6. 创建 `production_order_output`。
7. 更新订单状态为 `OUTPUT_BINDING`。

---

### 7.8 绑定固定产品二维码

```http
POST /api/production/orders/outputs/{outputId}/bind-fixed-qrs
```

请求：

```json
{
  "autoPrint": false,
  "remark": "生产订单产出贴码"
}
```

后端逻辑：

```text
1. 查询 output
2. 计算还需绑定二维码数量
3. 按 product_id 从固定产品二维码池锁定 FREE 码
4. 数量不足则失败
5. 为每个拆分任务创建 pallet_task
6. 更新 pallet_code 状态为 PENDING 或现有待入库状态
7. 写 production_order_output_code
8. 更新 output.bound_qr_count
9. 更新订单状态
```

固定产品二维码查询规则：

```text
product_id = output.product_id
fixed_product_flag = true
status = FREE
ORDER BY updated_at ASC, id ASC
LIMIT requiredCount
FOR UPDATE
```

## 8. 数量拆分规则

输入：

```text
boardCount
pieceCount
piecesPerPallet
```

标准化：

```text
extraBoards = pieceCount / piecesPerPallet
remainingPieces = pieceCount % piecesPerPallet
finalBoardCount = boardCount + extraBoards
finalPieces = remainingPieces
requiredQrCount = finalBoardCount + (finalPieces > 0 ? 1 : 0)
```

示例：

```text
7板16件，25件/板 => 7个整板码 + 1个散件码
30件，25件/板 => 1个整板码 + 1个5件散件码
60件，25件/板 => 2个整板码 + 1个10件散件码
```

单个二维码不允许承载多板。

整板任务：

```json
{
  "quantity": 1,
  "unit": "0",
  "pieces": 0
}
```

散件任务：

```json
{
  "quantity": 5,
  "unit": "1",
  "pieces": 5
}
```

通过历史二维码或流转记录可看到：

```text

pallet_flow_record
```

## 14. 与现有模块的关系

### 固定产品二维码池

产出贴码必须复用固定产品二维码池。

要求：

1. 只取当前产品对应的固定二维码。
2. 只取状态为 `FREE` 的二维码。
3. 按空闲时间或 `updated_at` 升序。
4. 加锁，避免并发重复分配。

### pallet_task

绑定产出二维码时，必须创建真实 `pallet_task`。

任务类型：

```text
订单类型 SEMI 或产出产品状态为半成品 => SEMI_IN
订单类型 FINISH 或产出产品状态为成品 => FINISH_IN
```

后续入库仍然走现有二维码确认入库逻辑。

### inventory

半成品领用：

```text
从 inventory 移出
```

成品入库：

```text
向 inventory 写入
```

### pallet_flow_record

建议新增或复用流转类型：

```text
ORDER_MATERIAL_PICK     生产订单领用
ORDER_OUTPUT_BIND       生产订单产出贴码
```

如果不方便新增枚举，至少操作名称要清楚：

```text
生产订单领用
生产订单产出绑定二维码
```

## 17. 注意事项

1. 不要把生产订单做成完整 MES。
2. 不要新增独立服务或独立数据库。
3. 不要让成品二维码强制绑定半成品二维码。
4. 不要让生产订单依赖旧备料池。
5. 半成品领用后二维码释放，但必须保留历史快照和流转记录。
6. 成品产出二维码必须复用固定产品二维码池。
7. 所有真实库存变更必须继续走事务和锁。
8. 生产订单状态可以简单，但状态变化必须可解释。
9. Web 端半成品领用使用下拉/列表多选；小程序端使用扫码。
10. 第一版先解决“半成品输入 -> 生产订单 -> 成品输出 -> 入库追溯”的闭环。

## 18. 最终目标

第一版完成后，系统应支持以下完整闭环：

```text
1. 管理员创建生产订单
2. 仓管/生产负责人实际领用半成品，一板扫一码
3. 系统从仓库库存中移出半成品，并关联到生产订单
4. 生产完成后，管理员登记多种成品产出
5. 系统从固定产品二维码池批量分配成品二维码
6. 管理员打印二维码并发给现场贴码
7. 仓管确认成品入库
8. 扫任意成品二维码，可以追溯到生产订单
9. 查看生产订单，可以看到实际用了哪些半成品、产出了哪些成品
```

这就是当前阶段的轻量 MES 核心能力。
