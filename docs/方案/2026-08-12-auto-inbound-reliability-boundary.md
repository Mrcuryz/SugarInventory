# 自动入库可靠性边界审查与整改

日期：2026-08-12

范围：智能报数半成品快速入库；不包含成品生产报数的生产订单闭环。

## 1. 审查结论

历史方案已经覆盖“解析草稿、人工确认、固定码分配、入库”主流程，但原实现仍有四个可靠性缺口：

1. 批次详情仅按可猜测的 `batchId` 读取，没有校验当前用户是否为批次所有者。
2. 确认接口接收完整 `AutoInboundTask`，客户端可以回传并覆盖类型、状态等服务端字段。
3. 重复或并发确认没有跨请求互斥和持久幂等事实，存在重复占码、重复入库风险。
4. MySQL 事务提交与 Redis 草稿状态更新之间没有可恢复事实，提交成功后 Redis 更新失败时无法可靠重放。

本轮整改后，批次访问按登录用户隔离；确认请求只接收允许修订的字段；同一批次由 Redis 所有权锁串行化；每个任务以 MySQL 唯一执行事实完成幂等恢复。库存写入仍由原托盘码领域服务执行，未增加旁路库存 SQL。

## 2. 实现边界

### 2.1 批次所有权

- 解析批次时写入 `auto_inbound:owner:{batchId}`，TTL 与批次一致。
- 读取、保存和确认批次时必须传入当前登录用户并校验所有权。
- 对升级前没有 owner key 的批次，仅当该批次存在于当前用户历史集合时懒恢复所有权。
- 不属于当前用户的批次统一按不存在处理，避免批次枚举。

### 2.2 请求可信边界

`AutoInboundConfirmRequest.updatedTasks` 改为 `AutoInboundTaskUpdateDTO`，只允许修订：

- 任务标识、入库日期、侧别、备注；
- 产品/库位标识或名称；
- 板数、件数。

任务类型、状态、风险、二维码结果、内部批次数据和操作人均以服务端事实为准。操作人只取 `@AuthenticationPrincipal`，不接受客户端传入。

### 2.3 并发、幂等与恢复

- 同一批次使用 `auto_inbound:confirm-lock:{batchId}` 所有权锁，锁值为随机 token，释放时采用 compare-and-delete Lua 脚本。
- 单次最多确认 20 个任务、最多分配 100 个二维码板位；重复任务 ID、未知修订和非法产品类型在写入前拒绝。
- `auto_inbound_execution` 以 `(batch_id, source_task_id)` 建立唯一约束，保存请求指纹、执行状态、结果快照和创建人。
- 已提交的同内容请求直接返回原结果，不再次创建托盘任务或库存流水；不同内容重放返回冲突。
- 进入领域写入前将 Redis 状态标为 `COMMITTING`；MySQL `afterCommit` 后才发布 `COMMITTED`。Redis 发布失败时，下次请求从 MySQL 已提交事实恢复。
- 领域写入回滚后草稿标为可重试 `FAILED` 并附失败提示。
- 托盘任务写入 `operation_batch_no=AUTO_INBOUND:{batchId}`，保留跨表追溯线索。

数据库变更见 `migrations/2026-08-12-auto-inbound-execution-idempotency.sql`。
