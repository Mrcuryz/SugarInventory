# DT50 仓管 App 产品与实施方案

更新时间：2026-08-30

当前实现状态：DT50 App `v0.2.0` 已完成工作台、权限同步、扫码入库、扫码出库、扫码调拨、仓库概况、库位详情、产品查找、化验查询和托盘业务流转页面。扫码入库已完成真实写入验收；本次新增的出库和调拨已完成真机扫码读取与确认前清单验收，正式使用前仍需在隔离测试数据上分别完成一次创建/确认/回滚写入验收。

## 1. 产品定位

DT50 App 是仓库管理员在现场使用的专用作业终端，不是 Web 管理端的缩小版，也不是旧微信小程序的代码迁移版。

它只承载两类高频目标：

1. 通过 DT50 实体扫描头完成入库、出库和调拨等现场作业；
2. 在搬运和核对现场快速查看库位、库存、产品、化验和最近流转情况。

已经完成真机验证的“扫描库位码 → 连续扫描待入库托盘 → 二次确认 → 整批入库”继续作为可靠基线。扩展过程中不得破坏扫码队列、去重、整批回滚、声音/振动反馈和登录失效保护。

## 2. 旧小程序的复用边界

### 2.1 可以复用

- 工作台、任务、扫码、查询、我的五类信息架构思路；
- 蓝色主操作、卡片化结果、底部固定确认栏等视觉语言；
- 连续扫码任务池、重复码拦截、失败项不阻断后续扫码；
- 托盘详情中的库存、化验和流转记录组合展示；
- 用户语言状态标签和空状态、错误状态设计。

### 2.2 禁止直接迁移

- “备料池”“生产中半成品”“历史生产占用”及 `PREPARE_CONSUMED` 写流程；
- 半成品备料/消耗的创建和确认入口；新流程以生产订单领用并确认后扣减为准；
- 库位左右侧、排、层等库位内部位置输入；后端兼容值统一使用“左”，App 不展示；
- 旧版手工入库页中重复填写产品、生产日期、数量和库位内部位置的流程；
- 微信登录、手机号绑定、工号绑定等微信运行环境专属页面；
- 直接把低层 CRUD、内部枚举或数据库字段暴露给仓管。

小程序只能作为交互和历史业务线索。每个功能必须重新以当前 Controller、DTO/VO、Service 和数据库实际行为确认，不能以小程序调用方式作为业务真相。

### 2.3 移动端视觉基线

Android 端应参考旧小程序较新的工作台、扫码作业和查询页面，而不是早期表单页：

- 使用统一的小程序蓝 `#246BFE`、浅灰页面背景、白色圆角卡片和轻量阴影；
- 工作台必须形成“用户状态 → 扫码作业 → 快速查询”的清晰层级，不能把所有能力排成相同的系统按钮；
- 入库作为现场主入口使用高强调作业卡，出库和调拨使用并列次级卡；
- 扫码页面以当前步骤、目标库位/托盘、实时反馈和本次任务池为视觉中心；
- 查询页面统一使用页头、查询条件、状态反馈、结果标题和业务卡片；
- 状态使用用户语言和浅色胶囊，不把枚举、空值或底层字段暴露给仓管；
- 布局以 DT50 的 720×1344/1440 竖屏、单手操作和实体扫描键为准，不照搬微信导航和手机扫码按钮。

该规则只复用视觉语言和信息层级，不改变第 2.2 节的业务迁移边界。

## 3. App 信息架构

### 3.1 工作台

- 显示当前操作员、网络/服务状态和 App 版本；
- 现场作业：扫码入库、扫码出库、扫码调拨；
- 快速查询：仓库概况、库位详情、查找产品、化验查询、操作记录；
- 根据登录账号权限隐藏或禁用不可用入口，不允许进入页面后才返回无权限错误。

### 3.2 扫码入库

沿用已验收流程：

1. 扫目标库位码；
2. 连续扫已绑定、待入库托盘码；
3. App 自动读取产品、生产日期和标签数量；
4. 仓管核对清单并二次确认；
5. 调用整批确认接口，任一失败整体回滚。

App 不创建新入库任务，不让仓管补录生产信息。

### 3.3 扫码出库

建议采用“扫描在库托盘 → 校验 → 创建出库任务预览 → 明确确认”的任务流程：

- 成品使用现有成品出库任务接口；
- 半成品只支持普通出库，不恢复历史备料池；
- 同一批次不得混入不在库、已作废、已有冲突任务的托盘；
- 创建任务和最终确认在界面上必须是两个清楚的阶段；
- 断网时不缓存待执行写操作，不允许恢复联网后静默补写。

### 3.4 扫码调拨

建议沿用入库的低输入顺序：

1. 扫目标库位码；
2. 连续扫需要调拨的在库托盘；
3. App 展示原库位、目标库位、产品和数量；
4. 创建调拨任务并二次确认；
5. 后端统一使用兼容侧别“左”，App 不显示侧别。

### 3.5 查询能力

- 仓库概况：库位总数、当前/最大容量、剩余容量、占用率、空库位和满库位；
- 库位详情：当前托盘/产品、库存明细、最近入库/出库/调拨；支持扫库位码直达；
- 查找产品：按产品名称模糊查询，展示总板数/件数、所在库位和最早入库日期；
- 托盘详情：支持直接扫托盘码，展示状态、当前位置、产品、化验和完整流转；
- 化验查询：按产品、日期和判定筛选，展示合格/不合格/无标准等用户语言；
- 历史操作：优先展示托盘业务流转记录，按托盘、库位、日期和事件筛选；不直接展示底层操作日志 JSON。

## 4. 现有接口映射

| App 目标 | 当前接口 | 结论 |
|---|---|---|
| 登录与权限 | `POST /api/auth/web-login`、`GET /api/user/info` | 可直接复用；App 本地保存 JWT、姓名和权限，不保存口令 |
| 扫库位 | `GET /api/warehouse/location-code/resolve` | 已真机验证 |
| 入库托盘校验 | `GET /api/pallet-codes/parse`、`POST /api/pallet-codes/tasks/list` | 已真机验证 |
| 整批入库 | `POST /api/pallet-codes/tasks/confirm` | 已真机验证，整批事务回滚 |
| 仓库概况 | `GET /api/inventory/warehouses` | 可直接复用；返回库位 ID、容量、托盘数和产品数，支持进入详情 |
| 库位库存 | `POST /api/inventory/summary` 或 `POST /api/inventory/agent-read/ledger/query` | 可复用；移动端优先使用结构稳定的台账结果 |
| 库位最近操作 | `GET /api/inventory/warehouses/{id}/recent-operations` | 可直接复用 |
| 产品查找 | `GET /api/inventory/stock/page`、`POST /api/inventory/agent-read/ledger/query` | 可复用 |
| 托盘详情 | `GET /api/pallet-codes/parse`、`/{code}/inventory`、`/{code}/assay`、`/{code}/flows` | 可复用 |
| 化验列表/详情 | `POST /api/assay/records/query`、`POST /api/assay/report-detail/query` | 可复用，返回已转换的判定用户语言 |
| 历史流转 | `POST /api/pallet-codes/flow-records/query` | 可复用，避免暴露底层审计字段 |
| 成品出库 | `POST /api/pallet-codes/finish/out/create`、`/confirm` | 后端已存在；需补移动端场景验收 |
| 半成品普通出库 | `POST /api/pallet-codes/semi/out/create`、`/confirm` | 后端已存在；不得调用 `semi/prepare/*` |
| 调拨 | `POST /api/pallet-codes/transfer/create`、`/confirm` | 后端已存在；需补目标库位扫码和冲突校验验收 |

`docs/openapi.json` 暂未包含未提交的库位码接口，代码实际行为优先；后续正式发布前应同步 OpenAPI。

## 5. 需要补齐或确认的能力

1. **移动端权限返回和入口控制**：登录响应已经包含 `permissionCodes`，App 需要持久化并按权限控制入口。
2. **我的现场操作**：现有 `log:view` 更偏管理员审计且包含内部字段。第一版使用业务流转记录；后续如需严格的“只看本人”，应新增受控移动端聚合接口。
3. **出库/调拨预览**：现有任务创建接口可用，但需要验证返回是否足以在写入前展示产品、数量、原/目标库位和冲突原因；不足时补业务级 preview，不在 App 内猜测。
4. **弱网处理**：读查询可以短时缓存最后一次成功结果；写操作必须在线、显式确认、失败保留本地清单且不自动重试。
5. **版本与环境**：服务地址在测试版保留可配置；正式版固定生产域名并将环境切换放到受控设置页。

## 6. 可靠性与交互规则

- 扫描输入抽象为统一入口，继续兼容 ScanWedge 键盘输出和 180ms 无回车收束；
- 每次扫描立即给出声音、振动、颜色和文字四类反馈；
- 批量上限默认 20 个托盘，防止一次确认范围不可核对；
- 重复码只计数，不重复请求和写入；
- 401/403 立即停止写操作：401 返回登录，403 显示缺失权限；
- 服务端返回的业务错误优先原样展示，内部枚举必须在服务端或 App 映射为用户语言；
- 页面切换时不得丢失尚未提交的扫码清单，退出作业必须确认；
- App 不保存登录口令、数据库信息、模型密钥或其他服务端 Secret。

## 7. 分阶段实施

### P0：可扩展基础壳与入库保护

- 登录后进入权限感知工作台；
- 入库从工作台进入，完整保留已验收流程；
- 统一会话、网络错误、401/403 和页面导航；
- 建立可复用扫码接收、反馈和卡片样式。

状态：已完成。

### P1：现场只读查询

- 仓库概况和库位详情；
- 产品查找和托盘详情；
- 化验记录/详情；
- 业务流转历史；
- 支持在相关页面扫描库位码或托盘码直达。

状态：主体已完成。库位详情当前从仓库概况点击进入，托盘业务流转支持扫码/输入托盘码；后续可补工作台直接扫库位进入详情和化验报告指标详情。

### P2：出库与调拨

- 先补接口契约和隔离数据场景验收；
- 再实现扫码任务池、预览、二次确认和整批失败保留；
- 覆盖并发冲突、重复确认、部分托盘状态变化和目标库位不可用。

状态：App 流程和现有接口接入已完成；真机已验证在库托盘读取、去重、原库位展示和确认前摘要，尚未执行会改变库存的最终写入验收。

### P3：上线强化

- 弱网只读缓存、版本检查、升级包签名和受控分发；
- 设备编号、扫码失败率、接口耗时等非敏感运行指标；
- 真实仓管试用后的按钮尺寸、单手操作和流程耗时优化。

## 8. 验收口径

正式可用不以“页面能打开”为标准，而以现场目标完成为标准：

- 仓管不输入产品、日期、数量和库位内部位置即可完成已存在任务的入库；
- 10～20 个托盘连续扫码无丢码、无重复写入；
- 扫库位或托盘后 3 次以内操作可以看到所需详情；
- 出库/调拨必须在最终写入前看到完整摘要并显式确认；
- 断网、登录失效、权限不足和并发冲突均不会产生静默写入；
- App 中不再出现备料池、历史生产占用、左右侧、排、层等废弃概念。
