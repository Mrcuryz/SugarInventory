# Agent 分阶段性能与 MCP 运行制品门禁实施记录

实施日期：2026-08-03
环境：本地开发数据库、Java Agent Gateway、Python Agent、Warehouse MCP、Vite Web
结论：正确性与 MCP 制品一致性通过；首个进度反馈通过；端到端性能门禁尚未通过

## 1. 本轮目标

本轮只处理两个 P0 风险：

1. 把 Agent 一轮问答拆成可持续采样的阶段耗时，避免仅凭人工体感评价性能；
2. Java 启动时校验实际运行的 Warehouse MCP JAR 与源码登记工具清单一致，避免“源码已更新、运行制品仍是旧版本”。

本轮没有新增业务写工具，没有放宽权限，也没有改变“主模型理解 → 专家决策 → 工具调用 → 结果分析”的执行模式。

## 2. 分阶段性能指标

Python 指标现在同时保留 `count`、`sum`、`max`、最近秩 `p50` 和 `p95`。新增或细化的关键指标为：

- `stream_first_progress_duration{operation=...}`：收到请求到服务端生成首个业务进度事件；
- `model_decision_duration{stage=main_route,...}`：主 Agent 结构化路由；
- `model_decision_duration{stage=expert_initial,...}`：专家首次选择工具或追问；
- `model_decision_duration{stage=expert_result_analysis,...}`：专家基于工具事实分析结果；
- `tool_call_duration{tool=...}`：Java/MCP 工具调用；
- `agent_turn_duration{mode=...,operation=...}`：整轮服务端耗时。

指标不记录 Prompt、用户原问题、模型原始输出、工具参数、内部 ID、令牌或数据库字段值。

## 3. 主路由输入收缩

运行采样发现，工具调用本身约为 0.2 秒，而主路由曾出现约 45 秒长尾。最小模型连通请求约 1.6 秒，因此不能把问题简单归因于数据库或 MCP。

进一步审查发现，主路由每次重复携带了各专家的完整执行说明和每个 GoalContract 的实体校验细节。这些信息属于专家阶段，不是主 Agent 选择业务领域和目标归属所必需：

- 完整专家目录约 4,600 个字符；收缩后约 871 个字符；
- 50 个登记目标约 6,823 个字符；移除主路由不使用的实体细节后约 5,303 个字符；
- 单次主路由输入减少约 5,249 个字符。

调整后，主路由只接收专家名称、业务名称、领域，以及目标业务含义和唯一归属。专家完整说明、工具 schema、实体约束和事实约束仍在专家决策阶段提供，因此没有把专家决策重新退化为关键词 Router。

同时把稳定的专家、目标和配方目录放在用户消息之前，便于兼容端点利用稳定前缀缓存；这只是序列化顺序优化，不改变业务语义。

## 4. MCP 运行制品一致性门禁

Java 新增启动校验：

1. 启动一个隔离的 Warehouse MCP 预检进程；
2. 只执行 `listTools`，不调用任何业务工具；
3. 将实际工具集合与 Java 受控登记集合做精确比较；
4. 若存在缺失或意外工具，抛出启动异常并终止应用就绪；
5. 无论成功或失败都关闭预检进程。

预检使用无业务权限的占位委托值，不读取业务数据。默认开启；只有显式设置 `AGENT_MCP_RUNTIME_VERIFICATION_ENABLED=false` 才跳过，并记录警告。

2026-08-03 本地真实启动日志：

```text
Warehouse MCP runtime artifact verified; result=SUCCESS; durationMs=3220
```

这项门禁会增加约 3.2 秒启动时间，不增加单次用户问答耗时。

## 5. 本地真实运行样本

以下为重启并加载输入收缩后的真实 Java → Python → MCP 链路样本。样本量不足以形成正式 P50/P95，只用于判断当前门禁状态。

| 输入 | 结果 | 端到端耗时 |
| --- | --- | ---: |
| 查询3号库位现在有什么库存 | 返回 1 个库存分组、2板15件、3 个托盘及库存分布卡片 | 26.054 秒 |
| 查询2026-07-17的生产产量 | 返回无登记产出的权威空结果和生产日报卡片 | 12.959 秒 |
| 查询黄冰糖（袋）最近30天的化验质量趋势 | 返回 2 条记录、1 条可判定合格、1 条无历史标准及趋势卡片 | 26.294 秒 |

重启前的阶段样本曾出现：

- 主路由约 45.2 秒；
- 专家首次决策约 3.3 秒；
- 工具调用约 0.2 秒；
- 专家结果分析约 4.7 秒；
- 整轮约 53.6 秒；
- 首个服务端进度事件近乎立即生成。

输入收缩后同类库存查询从约 53.6 秒下降到 26.1 秒，证明优化有效；但两个 26 秒样本仍高于现有“跨域/复杂报表 P95 不超过 15 秒”的目标，所以性能门禁不能判定为通过。不能继续通过增大超时掩盖该问题。

## 8. 下一步

下一步不应继续扩充超时，而应按以下顺序推进：

1. 用固定库存、化验、生产和报表语料分别采集不少于 20 次，按阶段给出 P50/P95；
2. 保持主模型和专家模型职责不变，继续减少主路由重复上下文，并评估为主路由/专家动作使用独立低延迟模型配置；
3. 只有在阶段样本稳定后，才调整正式性能目标或发布结论；
4. 业务功能下一切片为 `today_operations_overview_v1`，只组合现有数据库已证明的事实：当日稳定登记产出、当日已登记化验、当日确认领用与稳定产出两条独立序列、当前库存水平、当日创建的托盘任务及进行中任务；
5. 库存变化趋势只在可信快照门禁通过时进入正式概览；本地历史回放必须继续明确标注模拟；
6. 继续禁止计划达成率、退料、返工、报废、损耗、收率、SLA 和预测，除非未来出现可审计字段与真实写入链路。

## 9. 固定语料复验补充

上述“样本量不足”已在同日补齐：库存、化验、生产和登记报表各 20 个冷会话样本，共 80 条。全部基线请求返回，整体端到端 P50 为 16.547 秒、P95 为 39.016 秒；四领域 P95 分别为 57.187、38.484、26.328 和 37.250 秒。工具调用整体 P95 只有 0.267 秒，长尾集中在主路由和专家结果分析。

稳定前缀对照的整体 P95 为 37.125 秒，但 P50 略升、生产 P95 恶化，且出现 1 次主路由模型不可用。因此性能门禁仍未通过，不能进入“已封板”状态。完整方法、分领域结果和安全原始数据见 `agent-four-domain-performance-acceptance-2026-08-03.md`。

## 10. 分阶段模型配置接线

在不更改执行图的前提下，Python Agent 增加主路由、专家首次决策和专家结果分析三个可选模型名。Runtime 在工具观察为空时标记 `INITIAL`，存在观察后标记 `RESULT_ANALYSIS`；兼容模型客户端据此选择对应配置。未配置或配置为空时均复用原 `AGENT_MODEL_NAME`。

这项改动只为同一固定语料下的受控 A/B 提供入口，不代表已经找到更快模型，也不允许跳过主路由、专家、工具或结果分析。自动化验证覆盖默认回落、三阶段独立覆盖、HTTP 请求实际模型名和工具返回后的阶段切换；项目虚拟环境全量回归为 `453 passed, 5 skipped`。
