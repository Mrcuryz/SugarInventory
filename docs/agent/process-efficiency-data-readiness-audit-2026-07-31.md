# 已登记流程效率数据成熟度审计

审计日期：2026-07-31
审计范围：托盘任务、生产订单状态、生产标签/产出码到入库，以及库存趋势门禁运行状态
数据来源：当前 Java 写入路径、数据库迁移、`laibin` 本地测试库纯只读聚合
风险边界：不修改业务数据，不新增 MCP 工具，不登记未通过门禁的报表

## 1. 结论

三条候选流程不能作为一个整体直接开放：

| 候选报表 | 结论 | 原因 |
|---|---|---|
| `pallet_task_cycle_time_v1` | **CONDITIONAL_GO** | 创建、确认和当前状态可形成同一任务创建队列；38 条已确认任务均有确认时间，6 条进行中可计算当前等待，取消任务可计数但没有取消时间 |
| `production_order_stage_duration_v1` | **BLOCKED** | 只有创建时间、当前状态、反复覆盖的更新时间和最终完成时间，没有不可变的中间状态历史，不能计算各阶段耗时 |
| `label_to_inbound_duration_v1` | **BLOCKED** | 23 个有效产出码仅 8 个有可识别打印起点，只有 6 个同时具备打印和入库时间；打印时间还只是系统登记/PDF 生成，不等于现场实际贴标时间 |

下一实现切片只允许 `pallet_task_cycle_time_v1@1`。它必须称为“已登记托盘任务处理耗时”，不能泛化为整个仓库现场效率。

## 2. 审计方法与口径

### 2.1 共同门禁

每个候选流程至少检查：

- 开始与结束事件是否由真实业务动作写入；
- 是否有稳定关联键，能否识别重复、撤销和跨轮次；
- 完成、进行中、取消和数据不完整是否可以分别统计；
- 负耗时、未来时间和缺失时间是否可识别；
- 是否能同时展示中位数、P90、最大值和长尾，而不是只给平均值；
- 是否有足够的历史样本及分组维度；
- 用户可见文案是否会夸大为现场完整作业效率或 SLA 逾期。

### 2.2 时间范围

本地业务时间为北京时间，审计时数据库时间为 `2026-07-31 18:21:41`。当前样本时间范围：

- 托盘任务创建：2026-04-23 至 2026-06-30；
- 托盘任务确认：2026-04-28 至 2026-07-20；
- 生产订单创建：2026-05-07 至 2026-06-30；
- 生产订单完成：2026-05-07 至 2026-07-20；
- 未发现未来时间或结束早于开始的记录。

## 3. 托盘任务：有条件通过

### 3.1 权威时间语义

`pallet_task.created_at` 在入库、出库或调拨任务创建时写入。成功处理任务时，`PalletCodeServiceImpl` 将状态改为 `CONFIRMED`，并在同一业务事务中写入 `confirmed_at` 和托盘流转记录。

首版必须按任务创建日期形成 cohort：

- 统计范围决定哪些任务进入队列；
- 已确认任务使用 `confirmed_at - created_at`；
- 进行中任务使用 `dataAsOf - created_at`，但不混入完成耗时；
- 已取消任务只计数，不进入完成耗时；
- 历史回看显示的是本次 `ReportRun` 生成时任务的受控快照，不伪装成当时即时状态。

### 3.3 限制

- 4 条已取消任务均没有独立取消时间，不能生成取消耗时或按取消日期趋势；
- `operation_batch_no` 仅覆盖 4/48，不能把任务按批次合并计算批量操作效率；
- 任务没有产品名称快照，按产品展示只能使用当前产品主数据名称，并在 `ReportRun` 中固化本次展示值；
- 待处理入库任务在确认前通常还没有目标库位，不能用目标库位过滤后再宣称覆盖全部进行中任务；
- 两条旧任务没有托盘流转关联，但任务自身创建/确认时间仍完整；
- 当前样本来自本地测试库，只能验证口径和程序行为，不能据此评价真实人员绩效。

## 4. 生产订单阶段：保持阻断

本地共有 19 个生产订单：9 个已完成、10 个未完成。9 个已完成订单均有 `completed_at`，没有负耗时或未来时间。

但 `production_order` 只保存：

- `created_at`；
- 当前 `status`；
- 会被每次更新覆盖的 `updated_at`；
- 最终全部产出码入库时写入的 `completed_at`。

`ISSUED → MATERIALED/PREPRINTED → OUTPUT_BINDING → WAIT_INBOUND → PART_INBOUND → COMPLETED` 没有不可变状态事件表。因此：

- 可以在未来单独定义“订单创建到全部登记入库”的窄口径；
- 不能发布名为“生产订单阶段耗时”的报表；
- 不能用当前 `updated_at` 反推每个阶段的开始或结束；
- 当前 9 个完成样本也不足以支撑细分订单类型的稳定趋势结论。

若后续确有阶段效率需求，应先建立不可变 `production_order_status_event`，至少保存订单号快照、前后状态、发生时间、操作者、业务动作和幂等键。

## 5. 标签到入库：保持阻断

### 5.1 两种打印来源

- 普通产出码使用 `production_order_output_code.printed_at`；
- 预打印流程的时间写在 `production_order_label_batch.printed_at`，核销后的产出码自身可能没有打印时间；
- 预打印批次的时间由 PDF 获取接口首次调用时写入，只代表系统登记为已打印，不是打印机或现场贴标扫描日志。

因此统一候选起点只能是受控的 `COALESCE(label_batch.printed_at, output_code.printed_at)`，不能只查产出码字段。

### 5.2 本地覆盖结果

| 项目 | 结果 |
|---|---:|
| 有效产出码 | 23 |
| 已入库 | 19 |
| 待入库 | 4 |
| 有可信打印起点 | 8 |
| 同时有打印与入库时间 | 6 |
| 已入库但缺打印起点 | 13 |
| 已打印但未入库 | 2 |
| 入库早于打印 | 0 |

打印来源分布：

- 预打印批次：4；
- 普通产出码：4；
- 缺失：15。

只有 6/23 的完整时间对，覆盖率不足以发布趋势。尤其是 19 个已核销使用的预打印标签中，存在批次从未经过系统“打印”登记的情况；`finishProduction` 允许核销仍为 `RESERVED` 的标签，不能把“已使用”反推为某个打印时间。

放行前至少需要：

1. 明确“PDF 生成”“打印任务发送”“实际贴标”哪个事件作为业务起点；
2. 对两条打印路径统一记录不可变事件；
3. 保证已使用标签的打印来源覆盖率达到门禁；
4. 将未打印、重打、回收、取消和入库失败分别建模；
5. 固定数据验证跨日与重试不重复计数。

## 6. 库存趋势门禁运行复核

审计过程中顺带核对了库存趋势门禁。2026-07-31 18:21 的实际状态仍为：

- `BLOCKED`；
- 连续通过 `0/7` 天；
- 2026-07-30 对账仍是 `INSUFFICIENT_DATA`；
- 缺少 2026-07-30 的日终期末快照。

代码中的北京时间零点任务会先生成快照再对账，但当前启动补偿只重新执行对账，不会补建错过的日终快照。服务若在零点未运行，稍后启动时不能安全地把“当前库存”冒充成前一日零点库存。因此：

- 文档中的“自然积累”必须以服务在日终任务窗口可靠运行或具备可审计重建能力为前提；
- 当前不得手工用 7 月 31 日白天的库存回填 7 月 30 日快照；
- 后续应选择可靠外部调度，或基于上一可信快照和不可变库存事件实现版本化重建；
- 在该问题关闭前，库存趋势继续保持阻断。

## 7. 下一实现切片的最小规格

`pallet_task_cycle_time_v1@1` 建议固定为：

- GoalContract：`PROCESS_EFFICIENCY_TREND`，但描述必须限定为托盘任务；
- 日期：北京时间任务创建日期，最长 366 天；
- 可选筛选：产品名称、任务类型；不按目标库位过滤整个 cohort；
- 指标：任务总数、完成/进行中/取消/数据不完整数；完成耗时平均值、中位数、P90、最大值；进行中等待中位数、P90、最大值；
- 分组：任务类型、任务创建日期；目标仓库只作为已完成任务的补充分布；
- 长尾：最久等待的受控示例，不展示数据库任务 ID；
- 数据质量：取消时间缺失、产品名称快照缺失、流转关联缺失和批次号覆盖不足；
- 文案：只说“已登记任务处理耗时/等待时长”，不说员工绩效、现场完整效率或 SLA 逾期；
- 执行链路继续复用 `run_registered_report`、`analytics_expert`、`ReportRun` 和同快照 XLSX，不新增专用 MCP 工具。
