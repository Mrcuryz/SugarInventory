# Agent 整体验收与写入阶段准入评估（2026-08-04）

## 1. 结论

本轮按“当前源码、当前本机部署、隔离 RAG 部署、生产发布”四个层级分别验收，避免把本地工作区或历史证据误写成已上线能力。

| 范围 | 当前结论 | 说明 |
|---|---|---|
| 只读查询源码与本机 UAT | `GO` | 10 个 Java 工具专家金丝雀全部通过；多轮澄清、候选恢复、上下文切换和安全拒绝通过 |
| 登记报表源码与本机 UAT | `CONDITIONAL GO` | 7 个登记定义均已实现；6 个使用真实业务事实，库存趋势仅允许可信日终快照或明确标注的本地模拟 |
| RAG 工程、隔离 UAT 与当前本地链路 | `GO` | 正式 v1 语料通过校验；当前 `5173 → 8080 → 8091` 已切换并完成 ADMIN/STAFF 全链路复验 |
| RAG 生产发布 | `NOT RELEASED` | 当前结论只覆盖本机 UAT；尚未形成生产环境密钥分发、部署、回滚和监控证据 |
| L2 待处理任务 UI 跳转 | `GO` | Agent 只查询 PENDING 任务；用户选择后打开既有业务弹窗，未新增或调用写工具 |
| L3 Agent 写入执行 | `NO-GO` | 当前可继续设计正式 preview/确认协议，尚不允许新增可直接执行的 Agent 写工具 |

因此，“只读查询”可继续保持本地/UAT 封板；“报表分析”已形成可用的受控报表体系，但库存趋势生产门禁和性能门禁仍未关闭；RAG 已进入当前本地链路并通过复验，但不能据此宣称生产发布完成。现阶段可以启动写入阶段的架构与 L2 预览工作，不能直接进入 L3 执行。

## 2. 当前能力清点

### 2.1 GoalContract 与工具面

`readonly-goal-contract-registry.yaml` 当前登记：

- 51 个 GoalContract：42 个普通业务只读目标、7 个登记报表目标、2 个知识目标。
- Java MCP 工具面为 52 个受控工具，其中登记报表继续共用唯一 `run_registered_report`。
- RAG 的 `search_approved_knowledge` 为 Python 本地 L0 知识能力，不计入 Java 52 工具。
- 当前本地链路启用 10 个 Java 工具专家、1 个进程内知识专家和 1 个无工具主 Agent；知识专家只能调用进程内只读知识检索，不能调用仓储 MCP。

执行图保持不变：

`模型理解 → 专家决策 → 工具调用 → 结果分析 → 受控展示`

本轮没有增加关键词 Router 快捷路径，也没有允许主模型直接回答实时业务事实。

### 2.2 登记报表

当前 7 个版本化报表定义：

1. `today_operations_overview_v1`
2. `daily_production_overview_v1`
3. `inventory_level_trend_v1`
4. `quality_assay_result_trend_v1`
5. `quality_metric_trend_v1`
6. `production_input_output_flow_v1`
7. `pallet_task_cycle_time_v1`

其中 `inventory_level_trend_v1` 仍为生产门禁目标：生产模式必须使用可信日终快照；本地/UAT 可用模拟数据，但必须在回答、卡片、历史快照和导出中持续标明“模拟”，且不得因此推进生产门禁。其余报表继续只统计数据库已有字段，不推导计划达成率、良率、收率、损耗、SLA、责任归因或预测。

### 2.3 RAG

正式 v1 语料包含 10 份文档、196 个知识块和 83 条固定评测；发布包重新执行 `validate-release`，状态为 `SUCCEEDED`。隔离链路 `5174 → 28080 → 28091` 与当前本地链路 `5173 → 8080 → 8091` 均已验证：

- ADMIN 能看到 5 张来源卡片，并命中受控事实 `Φ1.5mm / Φ2.0mm / Φ2.5mm`。
- 无证据问题返回 `NO_DATA`，不把“没有检索到”解释成“事实不存在”。
- 静态知识与实时业务混合请求会要求拆分。
- STAFF 前端入口隐藏，直接调用后端也返回 403。

当前真实状态更新为：

`ISOLATED_WEB_5174_VERIFIED / CURRENT_LOCAL_UAT_SWITCHED / PRODUCTION_NOT_RELEASED`

当前 8091 健康摘要为 `UP / OPENAI_COMPATIBLE / LLM / toolGateway=UP / stateStore=UP / rag=READY`。当前切换使用本地 UAT 密钥和 memory state，不能作为生产部署证据；统一 Git 基线仍需在共享工作区收口后建立。

## 3. 本轮缺陷与修复

### 3.1 候选选择偶发失效

根因不是后端错误取消，而是前端重复打开助手时可能并发创建两个会话。后创建的会话会正确替换旧会话，导致旧候选引用被标记为 `SESSION_CLOSED_OR_REPLACED`。

修复：前端复用同一个进行中的会话创建 Promise，确保重复打开只创建一个会话、只显示一次欢迎消息。没有放宽后端 interrupt token、会话归属或引用校验。

### 3.2 产品目录误路由

“查询成品产品目录”曾被主模型误判为成品库存。现明确登记为 `PRODUCT_MASTER_DATA → master_data_expert`；“成品/半成品”在该语境中是目录范围，不是库存事实。

### 3.3 库位库存误路由

“查询 8 号库位的库存情况”曾被误判为库位容量状态。现明确：

- “某库位库存情况/有什么库存/库存分布”属于 `WAREHOUSE_INVENTORY_DISTRIBUTION → inventory_expert`。
- “容量/占用率/剩余容量/库位状态”才属于 `warehouse_expert`。

### 3.4 验收脚本假阴性

旧 E2E 在 SSE 完成前检查页面，且普通查询只等待 12 秒、Playwright 单例默认 30 秒；模型变慢时会主动断开一个最终能够成功的请求。现将功能等待与性能门禁分离：

- 功能金丝雀普通查询最长等待 45 秒、登记报表 60 秒，单例上限 75 秒。
- 多轮旅程先验证对应 SSE 的 `message_end` 和 `finishReason`，再检查 UI。
- 文案断言接受“总容量/最大容量”“已用/已占用”等同义表达，并继续校验 `已用 + 剩余 = 总量` 和占用率数值。
- 性能仍由独立固定语料 P50/P95 验收，不因放宽功能测试等待而视为达标。

### 3.5 RAG 简短问法误路由

“白砂糖金属检测限值是什么？”曾被 LLM 误路由为产品化验标准查询，虽然 RAG 已经 `READY`，仍不会触发知识检索。根因是确定性知识边界只覆盖“生产工艺/流程”等长问法，没有覆盖用户更自然的“产品 + 金属检测 + 限值/阈值/参数”表达。

修复：在知识边界中登记金属检测、金属控制和金属探测的受控参数问法，并只在同时出现限值、阈值、参数、要求、标准或控制点时路由到 `PROCESS_KNOWLEDGE_QUERY`；同时提取显式产品标签用于检索范围约束。没有把普通化验标准或实时化验结果扩大为知识查询。

回归：Python 知识集成测试 `13 passed`；真实浏览器使用同一短问法后显示“现行资料”、5 张来源卡片，并命中 `Φ1.5mm / Φ2.0mm / Φ2.5mm`。

### 3.6 本地服务配置不一致

首次重启 8091 后，Java 使用的服务密钥与 Python 不一致，Python 访问日志明确返回 401；成对重启并统一本地测试密钥后恢复。随后首次 Java 重启使用了 256 位 JWT 测试密钥，而项目采用 HS512，登录日志明确抛出 `WeakKeyException`；改为 512 位 Base64 密钥后登录恢复。两项均为本地启动配置问题，没有修改认证规则或降低密钥强度。

### 3.7 待处理任务 L2 安全跳转与权限缺口

既有任务卡片已经能够跳转到业务处理弹窗，但自然语言“帮我处理当前入库/出库/调拨任务”仍可能被当作普通写操作直接拒绝；同时页面任务列表、创建、确认和取消接口缺少对应的细粒度 `@PreAuthorize` 注解。

修复后，Runtime 只把同时包含任务处理语义和入库/出库/调拨范围的请求解释为受控 UI 预览，强制查询 `PENDING` 任务并返回选择卡片。普通“帮我出库”仍拒绝。既有页面接口补齐 `task:view`、`task:create`、`task:confirm` 和 `task:cancel`，这些权限来自现有 RBAC 资产，没有新增权限概念。

真实浏览器输入“帮我处理当前入库任务”，查询到 4 条待处理成品入库任务；选择 1 条后成功打开既有“批量确认成品入库”弹窗，随后取消，未提交。反向输入“帮我出库”仍明确提示未开放写操作。详细记录见 `task-processing-l2-ui-handoff-2026-08-04.md`。

### 3.8 模型契约偶发失败的用户提示

新构建服务重启后的 RAG 冒烟中，两轮独立首次请求都出现主模型连续两次返回非契约动作，而相同输入人工重试后正常命中正式 v1 资料和 `Φ1.5mm / Φ2.0mm / Φ2.5mm`。这说明 RAG、工具和服务密钥链路可用，但“两次格式修复”不足以覆盖模型结构化输出长尾。

现将结构化决策的格式修复上限从 2 次调整为 3 次。第三次仍调用同一个主/专家模型按原 JSON Schema 修复，不走关键词 Router、不直接生成业务事实，也不绕过专家和工具；只有前两次格式失败时才触发，因此不增加正常请求延迟。三次都失败时，内部错误码、诊断和 `retryable` 语义保留，用户文本为“我暂时没能完成这次查询，请重试一次。本次没有执行任何业务变更。”，不暴露“结构化动作”等内部术语。该修复改善失败恢复，不把整体性能门禁改成通过。

### 4.3 性能

功能通过不等于性能门禁通过：

- 固定 80 请求基线：整轮 P50 `16.547s`、P95 `39.016s`；工具 P95 `0.267s`。

- 用户已确认约 21.8 秒的今日运营概览可接受，但 40 秒级长尾仍需优化。

因此性能结论保持 `NOT PASSED`。瓶颈主要在模型路由和结果分析，不在 MCP/数据库工具。

## 5. 写入阶段准入判断

### 5.1 可以立即开始的工作

允许进入写入阶段的设计与 L2 预览切片，首选复用当前“待处理任务卡片 → 选择任务 → 打开既有业务处理弹窗”的路径：

- Agent 只负责理解、筛选、生成预览和把受控引用传给现有业务 UI。
- 最终业务字段继续由现有弹窗展示和编辑。
- 用户仍在原业务 UI 中明确确认提交。
- 这一切片不新增 Agent `execute_*` 工具，不把跳转误称为 Agent 已执行写入。

### 5.2 L3 执行前的硬门禁

以下条件缺一不可：

1. **基线可复现**：先收口当前共享工作区，合并 RAG 与本轮路由修复，形成可构建、可部署、可回滚的确定 Git 基线；本地切换通过不代替生产发布与回滚验证。
2. **preview/execute 分离**：每个写目标必须是业务级工具；禁止任意 SQL、任意 HTTP 和 REST CRUD 一对一暴露。
3. **确认绑定**：预览产生不可变摘要、版本、操作者、实体引用、权限范围、过期时间和确认 token；execute 必须验证这些字段未变化。
4. **幂等与并发**：持久化幂等键；执行前重读业务状态并做版本冲突检查，避免重复入库、重复出库或使用过期任务。
5. **事务与失败语义**：业务写入、状态变化和审计必须处于明确事务边界；禁止把部分成功包装成全部成功。
6. **权限与职责分离**：为 preview、execute 分配细粒度权限；主 Agent 和无权专家不能执行，不能因为 RAG 命中某段资料而获得写权限。
7. **持久化 HITL**：当前本地 memory state 只适合 UAT。L3 的待确认动作必须使用可恢复的持久化状态，服务重启后仍能验证归属、过期和撤销状态。
8. **完整审计**：记录谁、何时、基于哪个预览、确认了什么、执行结果、业务引用和失败原因；不得记录密码、密钥或原始敏感上下文。
9. **负向与恢复验收**：至少覆盖重复点击、超时确认、权限撤销、数据已变化、网络断开、服务重启、事务回滚和审计失败。
10. **真实角色 UAT**：仓管、质检、生产主管按实际权限验收，不用 ADMIN 通过替代普通角色结论。

### 5.3 最终准入结论

- `GO`：写入阶段需求盘点、接口/事务审计、GoalContract 设计、L2 preview、现有弹窗跳转和预填。
- `NO-GO`：任何 Agent 直接执行真实业务写入、批量执行或自动主动触发写入。
- 第一项 L3 只有在上述门禁落地并通过单场景 UAT 后才能开放；不能一次把全部写接口接成 MCP 工具。

## 6. 建议的下一步

1. 合并并冻结本次只读/报表修复、RAG 当前本地切换、短问法路由修复和 L2 UI 跳转，建立统一开发基线。
2. 将已经通过的“查询 PENDING 任务 → 选择 → 打开既有弹窗”作为交互边界样例，补仓管真实角色 UAT；不得把 ADMIN 通过替代普通角色结论。
3. 从一个单一任务类型开始设计版本化 `preview_task_transition` GoalContract，定义受控输入、不可变摘要、状态重查、过期和冲突语义，但暂不新增 execute。
4. 独立分析 40 秒级模型长尾；只做有证据的低风险优化，不用放宽超时掩盖性能问题。
5. preview 门禁和真实角色 UAT 通过后，再单独评审是否新增第一个 L3 `execute` 工具。

本轮不需要产品经理补充虚构口径。下一步应先以现有代码、数据库字段、权限和页面流程为准完成写入接口审计；只有代码无法确认的规则，才整理为明确问题请求业务确认。
