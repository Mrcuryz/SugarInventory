# 报表分析现有数据事实与实现边界

更新时间：2026-08-01
状态：已替代原“业务口径确认清单”
适用阶段：Agent v2-A 报表分析

## 1. 修订结论

原清单错误地把通用制造系统中可能存在的“计划审批/顺延、确认投料、退料、在制品、返工、报废、损耗规则和 SLA”当成当前项目的待确认前置条件。这不符合本项目“只依据现有数据库和接口事实统计”的原则。

修订后的规则是：

1. 只有数据库已有字段、当前写入链路会真实写入、且读取语义可以从代码确认的事实，才能进入报表。
2. 数据库仅预留枚举值、但当前 Controller/Service 没有写入动作的状态，不作为现行业务概念统计。
3. 没有表、字段或事件的概念直接标记为“当前系统不支持”，不要求产品经理补定义，也不由模型推断。
4. 模型只解释后端已经确定性计算的结果，不生成 SQL，不补齐缺失事实，不把一种业务记录改称另一种业务事实。

## 2. 审查依据与优先级

本次依次核对：

1. 本地数据库 `information_schema` 和现有数据，只执行只读查询；
2. 建表脚本与迁移脚本；
3. Controller、DTO、Service 写入链路；
4. 报表 Mapper 的实际 SQL；
5. `docs/openapi.json` 和 MCP/Agent 登记文档。

发现文档不一致时，以代码实际行为为准：

- `docs/openapi.json` 已存在，但尚未包含当前 `/api/analytics/agent-read/**` 报表接口，不能作为报表接口的完整清单；
- `docs/mcp-analysis/api-inventory.md` 仍保留“OpenAPI 不存在”的旧结论，属于历史文档状态；
- 当前报表能力以 `AnalyticsAgentReadController`、登记报表服务和 MCP 工具注册表为准。

## 4. 五类争议事项的重新判定

### 4.1 生产计划

现有事实：

- `production_order.production_date`：订单生产日期；
- `planned_material_json`：计划半成品用量，数据库注释明确为“仅参考”；
- `planned_output_json`：预计产出，数据库注释明确为“仅参考”；
- JSON 中实际使用 `productId/productName/boardCount/pieceCount`，部分记录还包含 `productionDate/quantityText`；
- `production_order.status` 保存当前订单状态。

不存在的事实：

- 计划审批、发布版本、计划顺延、计划变更事件；
- 不可变计划版本；
- 正式日产计划表或计划生效时间。

因此：

- 可以展示订单中已经登记的计划用料和预计产出；
- 可以按 `production_date` 查询某日订单及其登记计划；
- 不能称为“审批后正式计划”，不能计算历史版本计划达成率；
- 不需要产品经理补充“计划顺延规则”，因为当前系统没有这一概念。

### 4.2 领料与生产消耗

系统当前存在两类现行业务事实，另有一组必须排除的旧流程表：

| 数据源 | 当前业务语义 | 可用时间 | 当前限制 |
| --- | --- | --- | --- |
| `production_order_material` | 用户确认生产订单领用后写入；同一事务完成出库、库存扣减和二维码释放 | `picked_at` | `PICKED` 表示已确认生产领用扣减，不是待确认记录 |
| `production_boiling_batch_usage` | 煮糖批次对订单的预留、释放或最终确认使用 | `created_at/updated_at` | `CONSUMED` 的更新时间不是现场投料时间 |
| `semi_prepare_pool*`、`production_consumption_record` | 已停用备料池流程的历史/兼容数据 | 不用于现行统计 | 旧接口明确拒绝写入，前端也已转向生产订单领用 |

因此：

- 已实现报表中的领料序列解释为“生产订单确认领用扣减”，权威来源是 `production_order_material.status=PICKED`；
- 用户询问现行生产消耗时，可使用确认领用扣减事实，但不能把领用确认时间说成现场投料时间；
- 不再要求确认“投料、退料、剩余料”等当前不存在的动作；
- `production_order_material` 表定义中虽然预留 `RETURNED/CONSUMED` 状态，但当前代码没有写入入口，报表只统计真实可达的 `PICKED`。

### 4.3 返工、报废和损耗

本次在当前数据库表名、字段名、字段注释、Controller、DTO 和 Service 中均未找到可用于统计返工、报废或损耗的业务事实。

结论：

- 这些不是当前报表的待确认口径，而是当前系统不存在的能力；
- 当前阶段不实现返工量、报废量、损耗率、收率或相关预测；
- Agent 不得用“领料减产出”推算上述指标；
- 只有未来系统真实增加相应业务模块和字段后，才重新评估，不提前设计虚构流程。

### 4.4 流程耗时与 SLA

现有托盘任务只有：

- `task_type`、`status`；
- `created_at`、`confirmed_at`；
- 产品、托盘、目标库位及操作批次等辅助字段。

这些字段足以计算“系统已登记托盘任务从创建到确认的耗时”，当前报表已经按完成、进行中和取消分开统计。

数据库中不存在 SLA 配置、截止时间、暂停计时、工作日历或超时等级。因此：

- 当前只展示处理耗时和等待时长；
- 不判断逾期，不要求产品经理补 SLA；
- SLA 不是“报表分析阶段完成”的前置条件，而是未来明确提出后才评估的新功能。

### 4.5 报表导出

现有实现已经支持：

- 同一 `ReportRun` 不可变快照；
- XLSX 导出；
- 报表说明、核心指标、趋势明细、数据质量和口径限制；
- 导出人、导出时间、审计编号和 SHA-256；
- 所有者、权限、有效期和内容哈希复检。

因此，现阶段不需要业务方提供“最终导出模板”。现有通用 XLSX 即为当前交付格式。Logo、PDF、签字栏或品牌样式只属于未来明确提出的展示需求，不阻塞报表分析完成。

## 5. 当前可继续实施的报表范围

完全基于现有字段继续推进：

- 已登记生产产量及趋势；
- 库存水平及可信快照趋势；
- 化验判定趋势和单项指标趋势；
- 生产订单实际领料与稳定登记产出的独立趋势；
- 生产订单确认领用、出库记录和库存流水的一致性审计；
- 托盘任务创建到确认的登记耗时；
- 上述报表的跨期比较、历史重开、XLSX 导出和综合摘要。

当前系统明确不实现：

- 计划顺延、计划审批版本和正式计划达成率；
- 退料、返工、报废、损耗、收率；
- SLA 达标率或逾期告警；
- 没有数据库事实支撑的原因分析和预测。

## 6. 后续防幻觉门禁

每个新增指标必须在开发前登记以下证据：

| 项目 | 必须回答 |
| --- | --- |
| 数据表与字段 | 具体表名、字段名和业务注释是什么 |
| 写入动作 | 哪个 Controller/Service 在什么业务动作中写入 |
| 时间字段 | 使用哪个业务日期或事件时间 |
| 状态白名单 | 当前代码真实会产生哪些状态 |
| 关联键 | 如何与产品、订单、托盘或批次稳定关联 |
| 空数据语义 | 无记录时是权威空结果还是数据缺失 |
| 用户语言 | 对外名称是否与数据库业务语义一致 |

任一项无法从现有资产确认时，该指标不得进入实现，也不得转化为让产品经理“补一个规则”后继续计算。
