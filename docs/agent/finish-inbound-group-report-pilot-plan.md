# 入库试点与工作群报数接入方案

日期：2026-08-13  
状态：业务安全边界继续有效；渠道方案已于 2026-08-14 调整，开发暂缓

> 2026-08-14 决策更新：商业试点继续以现有个人微信工作群、无需复制和无需 `@机器人` 为硬约束。当前首选渠道改为 Windows 微信客户端视觉采集 + 本地 OCR，并工程化为可替换的 `WeChatVisualAdapter`；企业微信会话内容存档保留为长期替代通道，不再作为试点前置条件。本文第 2 节渠道结论、第 4 节入口描述、P3、相关生产门禁及前置信息以 [个人微信群视觉采集与入库候选接入设计](personal-wechat-visual-collection-design-2026-08-14.md) 为准；群消息不具备执行权限、二维码来源区分、Web 人工确认和现有受控入库链路等业务安全边界继续有效。

## 1. 试点目标

写入阶段只交付一个闭环：**受控成品入库**。出库、调拨、半成品入库、生产领用、化验写入以及其他业务写操作均不进入本试点，也不得因为复用旧代码而被间接开放。

工作群消息只作为新的输入渠道。模型负责从消息中识别是否与成品入库有关，并提取可验证的业务字段；它不继承消息发送者的系统权限，也不能在群内直接执行入库。最终业务写入必须由已登录的仓管在 Web 受控界面确认，并继续复用现有的精确预览、一次性确认、幂等、状态重检、事务和审计链路。

试点成功的判定不是“模型能读群聊”，而是：从一条真实报数到一笔正确、可追溯、可撤销候选但不可静默执行的入库确认，能够稳定减少人工录入时间。

## 2. 渠道结论

### 2.1 商业演示要求

演示必须由真实工作群中的每条新消息自动触发，不能要求用户复制、转发或 `@机器人`。报数人员在演示中仍使用个人微信发送消息，系统逐条识别入库相关、其他业务、无关和不确定消息。

这一体验不等于可以直接监听现有普通个人微信群。普通个人微信群没有适合服务端读取全部消息的官方接口；微信个人账号规范也明确限制第三方软件自动访问、读取或控制微信客户端。PC Hook、非官方协议、读取客户端数据库、模拟点击和群控不进入产品实现，也不能作为可销售能力承诺。

### 2.2 正式实现：企业微信客户群 + 会话内容存档

满足演示体验和商业稳定性的推荐实现是：

1. 由一个开通会话内容存档的企业微信仓管账号创建客户群，或在客户端能力允许且迁移后可存档的前提下承接现有工作群；
2. 现场报数人员仍以个人微信身份留在群内并正常发消息；
3. 群成员按企业微信规则收到会话存档告知并完成同意；
4. 渠道服务使用企业微信会话内容存档 SDK 按 `seq` 增量拉取消息；
5. 每条消息以官方 `msgid` 去重后独立进入 Agent 分类和候选单链路。

会话内容存档是增量拉取接口，不是“每条消息立即推送”的 Webhook。产品层通过短周期轮询实现近实时触发，并监控最后成功 `seq`、拉取延迟和断点续传，不能宣传为绝对实时。未同意存档的个人微信成员所发消息可能无法获取，因此“每条消息”成立的前提是目标群和成员均处于可存档范围。

现有普通个人微信群是否能直接迁移并继续满足客户群存档条件，必须在目标企业微信版本和租户中现场验证。若迁移后不是可存档客户群，应新建客户群用于演示；不能用非官方自动化填补该差异。

企业微信智能机器人只适合内部群 `@机器人` 交互，普通群 Webhook 主要用于发送通知；两者都不能满足本试点“不 @、识别群内每条消息”的要求，因此不作为主接入方案。

渠道适配层必须与业务解析层解耦。开发期可用与会话存档事件格式一致的本地回放源验证业务闭环，但商业演示的验收必须使用真实企业微信客户群中由个人微信账号发送的消息。

## 3. 关键业务边界

### 3.1 群消息不是已授权的“系统用户输入”

群消息可以等价为一次 **Agent 解析请求**，但不能等价为一次 **已授权执行请求**。渠道发送人只作为来源事实保存；除非以后完成企业微信身份与系统账号的明确绑定，其身份不能用于权限判定。

唯一有权确认写入的是登录系统并具有 `agent:finish-inbound:execute` 的 `WAREHOUSE_MANAGER`。系统超级管理员负责渠道配置和异常治理，不应成为日常入库的默认操作人。

### 3.2 二维码来源必须显式区分

每条候选单都必须明确属于以下一种模式：

1. **处理已有待入库任务**：二维码已绑定产品，且存在 `FINISH_IN + PENDING` 任务；
2. **使用空闲固定二维码创建待入库任务**：管理员选择具体产品和指定数量的空闲固定二维码，先形成待入库任务，再进入精确预览；
3. **信息不足**：未明确二维码来源或数量不足，保持待补充，禁止静默改用另一种模式。

第二种模式当前尚未具备仓管专用的受控任务创建权限。实施时应新增狭义的成品入库准备权限和独立确认步骤，不能给仓管通用 `task:create`、`qrcode:activate` 或 `task:confirm`。

### 3.3 首版只支持成品入库

模型分类至少区分：

- `SUPPORTED_FINISH_INBOUND`：本试点支持的成品入库报数；
- `BUSINESS_BUT_UNSUPPORTED`：生产、半成品、出库、调拨、化验写入等业务相关消息；
- `IRRELEVANT`：与业务无关；
- `UNCERTAIN`：无法可靠判断。

`BUSINESS_BUT_UNSUPPORTED` 不能被当成无关信息丢弃，应在收件箱中提示“当前试点暂不支持”；`UNCERTAIN` 必须进入人工复核，不能自动忽略。

## 4. 推荐业务流程

```text
企业微信客户群中的每条新消息 / 本地同格式回放消息
  → 会话内容存档按 seq 增量拉取、SDK 解密、msgid 去重
  → 持久化不可变消息事件
  → 模型做受限分类与字段提取
  → 后端确定性解析产品、库位、日期、数量和二维码
  → 形成入库候选单
  → 仓管在 Web 补充或修正字段并选择二维码来源
  → 生成/绑定待入库任务
  → 复用现有任务资格预览与精确执行预览
  → 仓管再次确认
  → 受控入库执行、审计与结果回写
```

群消息进入系统后必须异步处理。拉取器只完成断点推进、解密、去重和落库，不得阻塞等待模型。只有消息落库成功后才能提交该段 `seq` 进度；模型超时、SDK 重试或服务重启都不能丢消息或重复生成候选单。

## 5. 模型与确定性系统的分工

模型只输出受控结构，不输出或猜测数据库 ID。建议结构包括：

- 业务分类及整体置信度；
- 产品原文、库位原文、数量与单位、业务日期、左右侧；
- 显式出现的二维码；
- 是否属于更正、撤回或引用上一条消息；
- 每个字段对应的原文证据片段；
- 缺失字段和需要人工确认的问题。

后端负责：

- 按北京时间解释日期；
- 用现有 resolver 匹配产品和库位；
- 校验板、件、重量和产品规格；
- 查询二维码是已绑定待入库还是空闲固定码；
- 检测回调重复和业务内容重复；
- 生成不可变预览并完成权限、幂等、并发、事务和审计校验。

群消息属于不可信输入。提示词注入、要求越权查询、要求忽略规则或要求直接执行等内容只能作为普通文本，不能改变工具白名单和运行时策略。

## 6. 页面方案

不建议把解析前的群消息直接混入现有托盘待处理任务列表。无关消息、信息不足、重复消息和未选择二维码的候选单都还不是业务任务，混在一起会让用户误以为库存操作已经创建。

推荐把现有“智能报数处理”收敛为 **入库报数收件箱**，或在任务管理页增加一个独立标签页：

1. 待复核；
2. 待补充；
3. 可生成入库任务；
4. 已转入待处理任务；
5. 已完成；
6. 已忽略/不支持/重复。

候选卡片展示来源群、报数人、时间、原文、模型提取值、确定性匹配结果、缺失项和修改差异。管理员完成任务准备后，卡片显示关联的待入库任务并可跳转现有处理弹窗。现有待处理任务页只展示已经真实创建的业务任务。

首版不要求逐条向客户群回复，以免无关聊天触发大量机器人通知。系统可通过独立的企业微信应用消息或 Web 待办提醒仓管；若后续要回群通知，必须单独解决发送身份、频率控制和消息关联，不在群里展示内部 ID、完整库存或执行 token，也不提供直接执行按钮。

## 7. 数据与审计

需要新增持久化收件箱，不能复用当前仅保留 24 小时、按 Web 用户隔离的 Redis 自动报数批次作为唯一事实源。至少保存：

- 渠道、群标识、消息唯一标识、发送人标识、发送时间、接收时间；
- 原文或按保留策略加密后的原文、内容哈希、引用关系；
- 分类、提取结构、模型/Prompt/Schema 版本和字段证据；
- 产品/库位/二维码解析结果及人工修改差异；
- 候选单状态、审核人、审核时间、关联任务和最终执行引用；
- 渠道重试、模型失败、人工拒绝和最终业务结果。

必须建立 `(channel, message_id)` 唯一约束，并增加规范化业务指纹识别“同一报数被复制多次”。更正消息不能覆盖原消息，应以版本或关联事件保留完整轨迹。

## 8. 对现有实现的复用与淘汰边界

可以复用：

- 主模型理解、专家决策、受控工具调用、结果分析的统一 Agent 范式；
- 产品/库位/二维码 resolver；
- `FINISH_INBOUND_GUIDED_PREPARATION` 等入库 GoalContract 的业务语义；
- 待入库任务查询、任务资格预览、精确执行预览；
- S2/S3 的确认、token、幂等、重检、事务和审计；
- 当前任务处理弹窗和入库卡片。

不能直接复用为群聊生产入口：

- `AutoInboundParseServiceImpl` 让模型返回产品/库位 ID 的旧解析方式；
- Redis 24 小时批次作为跨渠道共享收件箱；
- `AutoInboundConfirmServiceImpl` 中同时覆盖半成品、生产用料、固定码分配并直接确认入库的宽链路；
- `AutoInboundController` 的通用 `task:create` / `task:confirm` 权限模型。

旧“智能报数处理”应逐步收敛为本试点的页面壳和兼容入口，写入统一走新的狭义成品入库编排，不维护两套相互竞争的确认事务。

## 9. 实施阶段

### P0：冻结范围与消息适配契约

- 冻结“只做成品入库”；
- 建立群消息和候选单 schema；
- 用脱敏/合成群聊样本覆盖无关消息、缺字段、多消息、更正、重复和提示词注入；
- 建立企业微信会话内容存档 `seq/msgid/roomid/from/msgtime/msgtype` 适配契约和本地同格式回放源；
- 不再扩展现有手工粘贴智能报数入口。

### P1：入库报数收件箱

- 消息持久化、分类提取、确定性解析、状态机和审核页面；
- 仅生成候选单，不写库存；
- 接入已有待入库任务模式；
- 完成管理员修改、拒绝、重复检测和审计。

### P2：固定二维码准备闭环

- 新增狭义入库准备权限；
- 支持仓管选择指定数量的空闲固定二维码并确认创建待入库任务；
- 随后进入现有精确预览和受控入库执行；
- 禁止扩大到通用任务创建和其他任务类型。

### P3：企业微信客户群会话存档接入

- 开通最少必要的会话存档账号和目标群；
- 完成 SDK 拉取/解密、`seq` 断点续传、`msgid` 去重、成员同意状态、群白名单和密钥轮换；
- 用个人微信账号在目标客户群连续发送相关、无关、更正和重复消息，验证逐条入箱；
- 最终确认留在 Web，不在客户群消息上下文中执行入库。

### P4：小范围试运行与定价证据

- 开关默认关闭，限定一个群、一个仓库范围和少量仓管；
- 记录识别准确率、漏报率、字段人工修改率、重复率、从消息到确认耗时、执行失败率和节省的录入时间；
- 根据真实价值和运维成本，再对后续出库、调拨、报表推送或全量会话存档单独报价。

## 10. 生产门禁

试点上线前至少满足：

1. 普通个人微信群非官方自动化明确排除，商业演示使用企业微信客户群但允许成员继续使用个人微信；
2. 群消息不能直接获得执行权限；
3. 产品、库位和二维码不得由模型猜 ID；
4. 消息和业务双层幂等通过；
5. `UNCERTAIN` 与不支持业务不会被自动丢弃或执行；
6. 固定二维码准备使用专用权限和独立确认；
7. 业务写入只走现有受控成品入库事务；
8. 群消息来源、人工修改、预览、确认和执行全链可审计；
9. 渠道断线、模型超时、数据库失败、重复拉取和 `seq` 断点恢复完成测试；
10. 会话存档成员范围、外部联系人同意、消息保留周期、可见范围和责任人已明确；
11. 对客户演示材料明确说明渠道前提，不宣称可以监听任意普通个人微信群。

## 11. 实施前需要业务方提供的最小信息

研发可以先用同格式回放数据推进 P0/P1。进入真实渠道前，需要业务方确认和提供：

1. 企业微信组织及管理员权限，并确认是否可以开通会话内容存档试用或最少一个账号；
2. 20～50 条脱敏的典型群消息，包括正确报数、无关聊天、更正和多条连续报数；
3. 试点是否严格限定成品入库，以及常用二维码来源比例；
4. 哪些仓管账号负责最终审核；
5. 群消息原文保留周期及谁可以查看；
6. 选择一个可迁移验证的现有工作群，或新建一个由企微仓管担任群主的演示客户群。

若第 1 项暂时不能完成，可以开发并验收消息适配器、收件箱和入库候选链路，但不能完成用户要求的真实个人微信群消息商业演示。
