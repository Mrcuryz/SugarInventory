## 1. 范围与用户流程

沿用“主模型理解 → 化验专家决策 → 受控工具 → 结果分析”。写入必须再经过服务端保存的精确预览、用户明确确认和受控执行。不能将 `/api/assay/import` 原样开放给模型，也不增加任意 HTTP/SQL 工具。

先完成单个明确产品、一个日期的新增化验，再扩展既有化验组。产品重名时使用真实候选卡；不把产品大类当作某个具体产品。第一批不提供删除、覆盖旧记录、修改质量标准或自动补全检测值。

用户示例：“录入黄冰糖的化验，9月23日，色值268，还原糖0.15，pH7.52”。处理过程：

1. 识别录入意图和已提供指标，保留原数字；日期含义或产品规格不明确时集中补问。
2. 选择真实产品；单纯查询化验、询问如何录入，不得被转换成写入。
3. 显示产品、日期、全部已输入指标、未填项、已有记录/拟新增版本和现有服务的预判结果。没有提供的指标保持未填，不用0替代。
4. 用户可修改数值或取消；修改即作废旧预览。只允许对当前精确预览确认。
5. 执行端重新鉴权、核对版本和标准，再在事务内落库；返回实际记录和版本，可回查。重复点击/网络重试返回同一执行结果，不新增版本。

批量化验组属于后一批：必须完整列出展开产品及各自版本/判定，成员变化必须重新预览，不能暗中增加写入对象。

## 2. 已核实的现有事实

核查来源：`docs/openapi.json`（按路径/schema解析）、`AssayController`、`AssaySubmitDTO`、`AssayServiceImpl`、`AssayMapper`、`AssayStandardJudgeServiceImpl`、`webpage/src/components/Assay.vue`、`laibin.sql`及质量标准迁移。另只读查询本地数据库的列定义和索引；未连接生产库、未读取或修改实际化验记录。

| 现有能力 | 代码实际行为及接入影响 |
|---|---|
| POST `/api/assay/import` | `assay:create` 或 `quality:test`；操作员来自登录用户；事务、INSERT操作日志；重复请求会新增版本，没有请求级幂等 |
| POST `/api/assay/exists` | `assay:view`；请求使用`productId/entryDate`检查产品与日期是否已有记录，只返回布尔值，不足以作为并发版本依据 |
| GET `/api/assay/by-product-date` | `assay:view`；以产品和`productionDate`查询`sample_date`；最新记录排序为创建时间、版本 |
| POST `/api/assay/{id}` | `assay:update`或`quality:test`；实际按DTO产品/日期取最新并新增版本，路径id未作为目标校验依据；本阶段不开放此接口给模型 |
| 批量组导入 | 以首个DTO的`selectType=2/relatedId`展开组；只用首个DTO指标；空成员组直接返回，接口仍成功；受控预览须明确拒绝空组 |
| 版本 | 本地有唯一索引`uk_product_date_version(product_id,sample_date,version)`；当前先读最新再加1，没有在此服务中发现显式串行锁。唯一索引防重复版本不等于请求幂等 |
| 自动判定 | 复用`AssayStandardJudgeService.judge`，依据当前有效产品标准关联、标准项目及实测值，保存判定和标准快照；不得由模型判断“合格” |
| 无标准/多候选 | 既有服务支持无标准；命中多个标准时按已有默认/优先级选择并保留提示。不另造“无标准必定禁止录入”的业务规则 |
| 空指标 | 现有标准项目存在范围但缺检测值时，判定服务记录“缺少检测值”；不得擅自改成合格或为通过判定补数 |

方法级权限按各方法解释，不将Controller类和方法注解凭空合并成AND。Agent精确预览还需要读取产品和既有记录，权限方案必须显式验证查看权限和写权限，不能仅凭可打开助手即开放写入。

## 3. 字段、精度和日期差异

仅使用现有7个检测字段：色值、还原糖分、干燥失重、电导灰分、蔗糖分、不溶于水杂质、pH。DTO中前5项有非负约束，pH为0～14，不溶于水杂质未声明范围；不能把没有代码依据的百分比上限或全部必填当成既有业务规则。

本地实际列：色值、还原糖分、pH为`decimal(5,2)`，其他4项为`decimal(10,2)`，均可空。预览应校验可存储精度和位数，不能显示原值后让数据库静默舍入；超过两位有效小数的输入应提示用户调整或明确精度方案，不擅自四舍五入。单位从已登记标准/业务字段取，DTO本身没有单位，不能凭常识添加转换。

差异必须保留在实现/验收中：

- OpenAPI `selectType`示例为0，说明和服务实际为1产品/2组；应以代码行为为准并修正文档示例。
- OpenAPI/DTO声明日期和数值校验，但现有导入Controller没有对列表元素启用Bean Validation；不能认为注解已经在HTTP入口生效。新预览/执行必须显式校验。
- 表注释、DTO及Web表单为“抽样/采样日期”，库存关联和部分报表称“生产日期”，实际共用`sample_date`。不新增日期字段、不静默互换含义；预览沿用现有录入表单的“采样日期”，用户仅说“今天的化验”且未明确日期含义时补问。“今天”不能自动等同被检产品的生产日期。这是现有命名差异，不是新增业务概念。
- 基础`laibin.sql`仅有合格/不合格枚举，迁移后的本地实际列另含“无标准”及判定快照列；不能用旧建表脚本覆盖当前结构。

## 4. 受控写入边界

1. **预览不写业务数据**：保存控制层预览快照时与`assay`业务写入分开。复用已有入库预览/执行的设计原则，但不把化验内容塞进入库专用表，不做无关通用框架重构。
2. **确认绑定**：绑定当前用户、Agent会话、规范化输入、展开产品、日期、既有版本、标准内容与有效关联及到期时间。模型不能自制确认凭据，其他用户/会话不能接管。
3. **重试幂等**：执行记录使用唯一请求键和终态，执行记录与化验新增原子提交。超时后先回查，不盲目再次导入；同键不同载荷拒绝。
4. **并发**：确认时再次核对同产品同日期的最新记录，以及判定依赖的标准/关联。Web导入、Web更新与Agent执行应共享必要的锁定/版本分配边界；仅锁Agent端不能解决竞争。组操作按稳定顺序锁定，避免死锁。具体锁实现与控制表DDL在执行批设计后测试，不宣称现有代码已具备。
5. **权限与审计**：执行时重新读取业务权限，不能只信预览时token；撤权、过期、失效、重复确认均有明确结果。保留用户、输入、预览、目标版本及真实结果的关联，不记录凭据。
6. **事务与失败**：一批任一产品失败则全部回滚，不把空组或0条插入说成成功。业务错误用既有错误码/异常规范，结果返回DTO/VO，不暴露PO。
7. **上线开关**：本地先验证，默认不开生产执行。迁移与发布需独立确认；不修改既有账号或默认扩大仓管化验权限。
