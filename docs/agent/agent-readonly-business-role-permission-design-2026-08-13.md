# Agent 只读业务角色与助手入口权限设计

日期：2026-08-13  
状态：`R&D_ENGINEERING_PASS / HUMAN_UAT_DEFERRED_TO_PRE_PRODUCTION`

## 1. 审查结论

当前授权模型只有一个用户对应一个 `role_code`，通过 `role -> role_permission -> permission` 获得权限。数据库和前端均支持新增预置角色，无需引入多角色、部门数据权限或新的权限表。

现有正式数据只有 `ADMIN`、`QC`、`STAFF` 三类技术角色。“仓管”和“生产主管”是部门或岗位，不是可独立授权的角色；当前对应真实账号均为 99 项权限的 `ADMIN`。因此，不能把管理员验收解释成最小权限验收，也不能给通用 `STAFF` 叠加仓储与生产两组权限，否则两个岗位会获得彼此不需要的权限。

## 2. 本次最小改动

新增预置权限：

- `agent:use`：只控制是否能进入 AI 助手、创建会话和调用内部 Agent 服务；
- 它不替代每个业务接口已有的 `inventory:view`、`assay:view`、`production:*:view` 等权限；
- 它不包含 `agent:review:*`、`agent:audit:view`、`log:view` 或 `agent:finish-inbound:execute`。

新增两个预置只读角色：

- `WAREHOUSE_MANAGER`（仓管）：库存、库位、托盘、任务、产品、化验和单据查询，以及独立受控的成品入库执行权限；
- `PROD_SUPERVISOR`（生产主管）：生产批次、订单、领用、产出的只读权限，以及今日运营概览实际依赖的库存、化验和任务只读权限。初始迁移使用了超出历史用户字段 20 字符限制的 `PRODUCTION_SUPERVISOR`，补偿迁移在不扩大历史字段的前提下将其缩短为当前代码。

既有 `QC` 只增加 `agent:use`，继续沿用既有业务权限；既有 `STAFF` 不自动获得助手入口。`ADMIN` 保持兼容。这里需要特别区分：`QC` 历史上已有化验写入、任务处理和日志查看权限，因此它不是纯只读业务角色；本次不删除这些既有权限，也不把它们登记为 Agent 工具。当前 Agent 仍只能使用 L1/L2 白名单，不能因为账号在页面上有业务写权限就自行写入。

本次迁移只创建角色和权限，不修改任何现有用户的 `role_code`。正式用户由业务负责人在角色管理中显式分配，避免静默改变现有账号职责。

## 3. 前后端统一边界

- Web 入口根据 `ADMIN/SUPER_ADMIN` 或 `agent:use` 显示；
- Java 创建会话、消息、流式消息、续传、反馈和撤销都使用相同的 `agent:use` 门禁；
- 每次恢复用户或校验委派会话时重新读取当前权限，权限撤回后旧会话立即拒绝；
- Python 内部 chat/stream/resume 同时校验 `agent:use`，不信任单独的前端显示；
- 业务工具继续由 Java Controller 的细粒度权限控制。获得助手入口不等于获得跨域查询或任何写操作。

RAG 材料当前仍按其独立 `allowedRoles` 约束。给业务角色开放 `agent:use` 不会自动扩大知识材料可见范围；这避免把助手入口误当成 RAG 文档授权。

## 4. 最小权限矩阵

| 能力 | 仓管 | QC | 生产主管 |
| --- | --- | --- | --- |
| AI 助手入口 | 是 | 是 | 是 |
| 库存/库位/托盘查询 | 是 | 沿用既有 QC 查询权限 | 为运营与产出去向提供必要只读事实 |
| 化验和标准查询 | 是 | 是 | 为质量与运营概览提供必要只读事实 |
| 生产批次/订单/消耗产出 | 否 | 否 | 是 |
| 任务写入、库存写入、生产写入 | 仅受控成品入库；无通用任务确认、出库或调拨 | 沿用既有 QC 业务权限，本次不新增；Agent 不登记这些写工具 | 否 |
| AI 审查/审计 | 否 | 否 | 否 |
| L3 成品入库 execute | 是，受默认关闭开关和受控 UI 约束 | 否 | 否 |
