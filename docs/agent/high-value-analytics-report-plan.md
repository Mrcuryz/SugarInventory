# Agent v2-A 高价值报表与趋势分析方案

设计日期：2026-07-27

设计状态：`SEVEN_REPORT_DEFINITIONS_TODAY_OVERVIEW_ENGINEERING_ACCEPTED_INVENTORY_PRODUCTION_GATE_BLOCKED`

适用阶段：只读查询封板后的 v2-A 登记报表与受控分析

运行时影响：已实施五类高价值分析目标下的六个领域报表及一个“今日运营概览”跨域入口；原六个定义支持受控跨期比较，七类均支持同快照导出；不授权任何业务写操作、任意查询或预测执行

## 1. 结论

报表分析阶段的主线确定为五类用户目标：

1. 每日产量分析；
2. 化验质量与趋势；
3. 库存水平、流量和变化趋势；
4. 生产实际投入—产出趋势；
5. 已登记业务流程效率趋势。

另设一个跨域入口目标“今天整体运营情况如何”。它不创造新指标，只组合当日已登记事实和生成时当前快照，帮助用户先看全局、再下钻到上述五类领域报表。由于库存与待处理任务缺少可回溯的当日全量快照，该入口首版只支持北京时间今天，不支持历史日期或跨期比较。

库存健康、化验风险、待处理任务积压、生产订单闭环、标签/二维码入库对账继续保留，但定位调整为趋势报表的异常下钻和事实核对能力，不作为报表主目录。

总结、跨期比较、导出、订阅是所有登记报表复用的横向能力；预测是历史数据、指标口径和回测稳定后的独立阶段，不与首批报表同步开放。

本方案通过审查，可以作为 v2-A 报表分析阶段的产品与技术设计基线。但以下能力在相应前置条件完成前必须保持阻断：

- 生产库存趋势未通过连续可信日终快照门禁前，不生成或发布正式历史库存水平曲线；本地/UAT 只允许醒目标注的历史回放模拟；
- 未完成传统库存与托盘流转去重前，不发布权威出入库流量和库存净变化；
- 当前数据库没有返工、报废、损耗等事实，因此不实现良率、损耗率或材料消耗偏差率；这不是等待业务方补口径，而是当前系统能力边界；
- 未定义流程阶段和事件完整性前，不把已登记耗时解释为现场完整作业效率；
- 未完成固定历史数据、回测和漂移监控前，不提供生产、库存或质量预测。

## 2. 本轮审查修正了什么

### 2.1 处置型目标不是报表主线

此前选出的当前库存健康、化验风险日报、待处理任务积压、生产订单闭环和二维码入库对账都具有业务价值，但它们主要回答“现在具体哪里有问题、下一步去哪里处理”。

管理人员更高频的报表问题是：

- 今天生产得怎么样；
- 产品质量是在变好还是变差；
- 库存是在增加还是减少；
- 实际领料和产出是否出现异常变化；
- 哪个流程阶段越来越慢。

因此，处置型目标下沉为趋势报表的证据和下钻入口，趋势目标成为 v2-A 报表主线。

### 2.2 导出、总结和预测不是同一级业务目标

- 导出是同一份 `ReportRun` 的交付方式；
- 总结是基于受控事实的解释方式；
- 跨期比较是相同版本报表之间的分析方式；
- 订阅是登记报表的触发方式；
- 预测是具有数据、模型、回测和漂移门禁的更高阶段能力。

不得为上述每种交付方式重复建设一套业务指标或让模型重新查询数据。

### 2.3 趋势不能由当前查询结果反推

当前库存、当前订单状态和当前任务只能证明当前时点事实，不能恢复历史状态。趋势必须依赖版本化事实、事件或快照。

报表聚合也不能通过模型反复调用分页 L1 工具并自行求和。权威总数必须由登记数据集和 Java/SQL 确定性聚合产生。

## 3. 统一对象模型

不新增一套与 `GoalContract` 平行且重复的庞大合同。v2-A 使用以下四层对象：

### 3.1 `GoalContract`

表达用户要完成的业务目标、必需实体、可选范围、证据要求和完成条件。

例如：

- `DAILY_PRODUCTION_ANALYSIS`
- `QUALITY_TREND_ANALYSIS`
- `INVENTORY_TREND_ANALYSIS`
- `PRODUCTION_INPUT_OUTPUT_TREND`
- `PROCESS_EFFICIENCY_TREND`

### 3.2 `ReportDefinition`

表达登记报表的不可变定义：

- `reportDefinitionId`
- `reportVersion`
- owner domain / owner expert
- dataset 与 dataset version
- 允许的时间粒度、维度、过滤、比较期和排序
- 指标代码、公式版本、单位、精度、分母、空值和排除规则
- 数据新鲜度、迟到数据和重算规则
- 展示块、下钻定义和安全动作
- 权限、数据分类、导出和订阅策略
- 固定测试集和兼容范围

### 3.3 `ReportRun`

表达某一次实际生成的报表快照：

- `reportRunId`
- definition / dataset / metric version
- 当前用户与受信 scope
- `businessDateRange`
- `dataAsOf`
- `generatedAt`
- `filtersApplied`
- `totals`、`series`、`dimensions`
- `dataQuality`
- `limitations`
- `branchStatuses`
- `evidenceRefs`
- `revision`

用户重新打开历史报告时默认查看原 `ReportRun`，不得悄悄替换成实时数据；用户点击“刷新”才生成新的 `ReportRun`。

### 3.4 `ReportContext`

用于受控多轮追问，至少保存：

- 当前 report definition/version；
- 日期、产品、仓库、订单、批次等已确认范围；
- 当前分组、比较期和下钻位置；
- 上一次 `reportRunId`；
- 可执行的登记追问动作。

用户说“只看黄冰糖”“换成最近半年”“与上月比”“展开不合格批次”时，应复用 `ReportContext`，但仍由主模型理解目标、报表专家决策，Runtime 校验后执行，不能由前端或关键词 Router 绕过模型。

## 4. 统一时间语义

所有报表使用 `Asia/Shanghai`，并同时区分：

| 字段 | 语义 |
| --- | --- |
| `businessDate` / `productionDate` | 业务归属日期 |
| `occurredAt` | 业务事件实际发生时间 |
| `recordedAt` | 记录写入系统的时间 |
| `snapshotAt` | 状态快照时间 |
| `dataAsOf` | 本次报表已纳入数据的截止时间 |
| `generatedAt` | 报表生成时间 |

必须由业务确认“今天”是否等于北京时间自然日，还是生产班次业务日，例如 08:00 至次日 08:00。在确认前，首版按系统现有 `productionDate` 统计业务产量，并明确显示统计范围，不自行假设班次边界。

迟到录入和修订必须可识别：

- 产出晚一天补录，仍归属原生产日期；
- 报表需记录 `dataAsOf` 和 revision；
- 已导出的历史文件保持不变；
- 新数据导致历史报表变化时，新运行结果应标注“数据已补录/修订”，不能静默覆盖原结果。

## 5. 五个高价值目标

### 5.1 每日产量分析

#### 建议定义

- Goal：`DAILY_PRODUCTION_ANALYSIS`
- 首版 ReportDefinition：`daily_production_overview_v1`
- 数据口径 Owner：生产域；登记报表运行 Owner：`analytics_expert`
- 主要数据集：`production_order_fact_v1`、`production_output_fact_v1`

#### 用户问题

- 今天产量如何？
- 今天生产了哪些产品？
- 比昨天、上周同期和最近 7 日均值如何？
- 哪些订单或产品贡献最大？
- 已登记产出中还有多少没有完成标签或入库？

#### 首版权威口径

“产量”指按业务生产日期登记的实际产出，不使用以下数据替代：

- 标签打印数量；
- 二维码生成数量；
- 入库数量；
- 生产订单计划数量；
- 煮糖批次预留或引用重量。

产出、标签和入库作为三个独立阶段展示。

#### 首版指标

- 实际登记产出重量；
- 按产品可换算的件数、板数；
- 有产出记录的订单数；
- 按产品、订单、订单类型和生产日期分布；
- 标签数量及入库数量的独立完成情况；
- 与同版本可比期间的绝对变化和变化率。

不同产品无法安全换算到同一单位时：

- 总重量可在重量单位可靠时汇总；
- 件数、板数按产品分别展示；
- 禁止把不可换算单位直接相加。

#### 暂不支持

- `planned_material_json/planned_output_json` 仅为订单参考字段，缺少不可变计划版本，因此不提供正式计划达成率；
- 没有班组、产线和班次事实时的班组/产线效率；
- 没有实时现场采集时的“车间实时产量”；
- 良率、损耗率和实际产能利用率。

用户问“今天实时生产了多少”时，首版应回答“截至当前已登记产出”，并显示 `dataAsOf`。

### 5.2 化验质量与趋势

#### 建议定义

- Goal：`QUALITY_TREND_ANALYSIS`
- 首版 ReportDefinition：
  - `quality_assay_result_trend_v1`
  - `quality_metric_trend_v1`
- Owner：`quality_expert` / 运行登记报表时由 `analytics_expert` 隔离跨域范围
- 主要数据集：`quality_assay_fact_v1`

#### 用户问题

- 今天产品质量如何？
- 黄冰糖最近半年质量趋势如何？
- 哪个指标波动最大？
- 最近不合格率是否上升？
- 还原糖分、pH 或干燥失重的趋势如何？

#### 判定趋势

分别统计：

- 明确合格；
- 明确不合格；
- 无适用标准；
- 多个候选标准；
- 缺失化验。

合格率公式首版固定为：

`PASS / (PASS + FAIL)`

无标准、多候选标准和缺失化验不进入分母，必须单独展示数量和占比。

#### 原始指标趋势

支持已登记指标的：

- 样本数；
- 均值、中位数、最小值、最大值；
- P10 / P90 或登记分位数；
- 超出当时适用标准的数量；
- 按产品、生产日期、标准版本分组。

原始指标值可以跨标准版本连续展示；判定和合格率必须按当时实际采用的标准版本分段，不能用当前标准重算并覆盖历史判定。

`assay.sample_date` 按已确认业务语义作为生产日期。报表还应显示记录时间和标准版本，避免晚录数据或标准变更造成误解。

#### 不能由模型完成

- 模型不能自行选择质量标准；
- 模型不能修改历史合格判定；
- 模型不能把相关变化解释为生产原因；
- 小样本、无标准或缺数据时不能给出质量改善/恶化结论。

### 5.3 库存水平、流量和变化趋势

#### 建议定义

- Goal：`INVENTORY_TREND_ANALYSIS`
- ReportDefinition：
  - `inventory_level_trend_v1`
  - `inventory_movement_trend_v1`
  - `inventory_level_movement_reconciliation_v1`
- Owner：inventory / logistics 数据域，跨域运行由 `analytics_expert`

#### 当前实施状态（2026-08-01）

- `inventory_level_trend_v1@1` 已登记并复用唯一 `run_registered_report`；
- 生产数据源为连续通过每日守恒对账的 `TRUSTED_DAILY_CLOSE_SNAPSHOT`，查询范围不在可信窗口时拒绝；
- 本地/UAT 可显式启用 `HISTORICAL_REPLAY_SIMULATION`，以当前库存为锚点按登记流水反向回放产品总库存；
- 模拟回答、卡片、历史快照和 XLSX 必须标注“本地历史回放模拟”，且不推进生产发布门禁；
- 首版仅实现库存水平和产品分解；历史库位分布、权威出入库流量、周转率和原因解释仍未开放。

#### 必须拆开的两类事实

库存水平趋势回答某个时点“还剩多少”，依赖 `inventory_snapshot_v1`。

库存流量趋势回答某段时间“入库、出库、调拨了多少”，依赖 `stock_movement_fact_v1`。

理想日终关系为：

`期初库存 + 入库 - 出库 ± 已登记调整 = 期末库存`

但在传统库存与托盘事件去重、调整事件和历史快照完整之前，这个关系只能作为数据质量对账，不能默认成立。

#### 首版指标

- 期初、期末库存；
- 入库、出库、调入、调出；
- 净变化；
- 按产品、产品类型、仓库和生产日期分组；
- 库存年龄分布；
- 快照与流量对账差异。

#### 关键前置

- 立即开始按固定粒度生成库存快照；
- 明确保留期限和补采策略；
- 建立统一库存流转事件和去重键；
- 区分实际流转时间与记录时间；
- 明确非托盘历史数据是否进入趋势基线。

上线时清除旧库存不等于不需要历史设计。快照必须从新系统正式启用前开始积累，否则上线后的趋势能力仍需等待。

#### 暂不支持

- 没有销售、需求或保质期规则时，不把库龄解释为滞销或过期；
- 没有容量历史快照时，不生成历史库位容量趋势；
- 未完成事件去重时，不发布权威周转率。

### 5.4 生产实际投入—产出趋势

#### 建议定义

- Goal：`PRODUCTION_INPUT_OUTPUT_TREND`
- 首版 ReportDefinition：`production_input_output_flow_v1`
- Owner：`production_expert` / `analytics_expert`
- 主要数据集：`production_order_material`、`production_order_output`、`production_boiling_batch_usage`
- 旧 `semi_prepare_pool*` 与 `production_consumption_record` 不属于现行生产订单领用流程，不进入报表数据集

#### 两个视角必须分开

日历流量视角：

- 每日实际领料；
- 每日实际登记产出；
- 仅描述时间序列，不计算当天良率。

订单/批次归属视角：

- 成品订单展示 `production_order_material` 已登记领料；
- 半成品订单展示 `production_boiling_batch_usage.status=CONSUMED` 的最终确认使用；
- 同一订单展示稳定登记产出；
- 只并列事实，不计算比例或差额业务含义。

禁止直接使用：

`当天产出 / 当天投入`

领料使用 `picked_at`，产出使用 `production_date`，两条日期序列不是同一业务时间口径，不能直接相除。

#### 首版可支持

- 实际领料重量、件数和托盘数；
- 实际产出重量及可安全换算数量；
- 按订单、批次、产品和日期的独立趋势；
- 缺少关联、单位不可换算和订单未闭环提示。

#### 当前明确不支持

- 当前数据库没有返工、报废、损耗等业务字段，不实现相应指标；
- 已停用备料池表和历史消耗留档不得作为现行业务事实；
- 不要求产品经理为数据库不存在的概念补规则，未来若系统真实增加业务模块后再重新审计。

### 5.5 已登记业务流程效率趋势

#### 建议定义

- Goal：`PROCESS_EFFICIENCY_TREND`
- 首版 ReportDefinition：
  - `pallet_task_cycle_time_v1`
  - `production_order_stage_duration_v1`
  - `label_to_inbound_duration_v1`
- Owner：logistics / production / pallet 数据域，跨域运行由 `analytics_expert`

#### 首批阶段

- 任务创建 → 任务确认；
- 实际领料 → 产出登记；
- 产出登记 → 标签创建/打印；
- 标签打印 → 入库任务创建；
- 入库任务创建 → 实际入库；
- 生产订单创建 → 已登记闭环。

#### 指标

- 完成数量；
- 正在进行数量；
- 已取消数量；
- 数据不完整数量；
- 平均耗时；
- 中位数；
- P90；
- 最长耗时；
- 按产品、订单类型、任务类型和目标仓库分组。

不能只提供平均耗时。少量等待数天的任务可能被大量短任务掩盖。

#### 口径边界

- 已取消流程不进入完成耗时分母；
- 未完成流程展示当前等待时长，但不混入已完成耗时；
- 数据库没有 SLA、截止时间或暂停计时字段，只说“已等待 N 小时”，不说“已逾期”；
- 缺少独立扫描日志时，统一称为“已登记业务流程耗时”，不声称覆盖现场全部操作；
- 阶段缺事件时标记数据不完整，不计算伪造时长。

## 6. 处置型报告与趋势目标的关系

```text
每日生产分析
  └─ 生产订单闭环
      └─ 标签/二维码入库对账

化验质量趋势
  └─ 化验风险日报
      └─ 具体化验报告与异常指标

库存水平/流量趋势
  └─ 当前库存健康
      ├─ 产品库存分布
      ├─ 库位库存
      ├─ 无化验/无标准库存
      └─ 明确不合格库存

流程效率趋势
  └─ 待处理任务积压
      └─ 现有任务处理弹窗
```

趋势报表只引用处置型报告或事实的安全 `reportRef` / `evidenceRef`，不得重复抓取并生成另一套不一致数字。

## 7. 横向能力

### 7.1 总结

模型只基于 `ReportRun` 中已引用的指标和证据进行总结，建议结构为：

1. 一句话结论；
2. 2～4 个最重要变化；
3. 需要关注的数据质量或限制；
4. 登记的下钻或后续动作。

模型可以说“同时观察到”或“可能相关”，不能在没有规则或因果证据时断言根因。

例如可以说：

> 产量下降期间，实际领料次数也下降，同时部分订单仍未闭环；这些是同一期间观察到的事实，当前证据不足以确定产量下降的唯一原因。

### 7.2 跨期比较

截至 2026-07-31，五个当前登记报表已通过同一个 `run_registered_report` 接入统一跨期比较，没有新增报表专用 MCP 工具或 GoalContract。支持两种受控方式：

- `PREVIOUS_PERIOD`：紧邻本期之前的等长期间；
- `CUSTOM`：用户明确指定、与本期不重叠的对比期间。

Java Report Runner 使用同一报表定义、版本和领域筛选分别生成两期确定性事实，再由中央比较器只计算 registry 已登记指标。比较结果写入本期 `ReportRun` 快照，业务卡片和 XLSX 从同一快照读取。两期天数不同时，可累加指标补充日均值；正负变化保持中性，不自动标成改善或恶化。

两期必须使用相同：

- report definition/version；
- dataset version；
- metric version；
- 业务日边界；
- 过滤范围；
- 单位换算规则。

默认比较策略需登记，不能由模型任意挑选一个有利基线：

- 今日对昨日；
- 今日对最近 7 个同业务日均值；
- 本周对上周；
- 本月对上月；
- 用户明确指定期间。

不同天数期间比较总量时，同时提供日均值，避免把 31 天与 28 天总量直接解释为效率变化。

### 7.3 导出

导出必须复用同一个 `ReportRun`，不得重新查询后生成不同结果。

首批格式：

- XLSX：指标、序列和明细；
- PDF：摘要、图表、口径和限制；
- CSV：受控大明细。

导出必须包含：

- 报表定义和版本；
- 过滤条件；
- 数据截止时间；
- 指标口径和单位；
- 数据质量和限制；
- 导出人、导出时间和审计引用。

文件使用安全业务名称、短期下载引用、权限重检和过期策略，不返回服务器路径。

### 7.4 订阅与主动提醒

主动提醒只能由登记报表、登记事件或登记规则触发。订阅至少绑定：

- user/role 与受信数据 scope；
- report definition/version；
- 时间、频率、时区和有效期；
- 产品、仓库等允许过滤；
- 阈值、静默期和频率上限；
- 渠道、数据分类和退订入口。

重复事件按 fingerprint 合并。没有变化时不重复轰炸；新增、升级、恢复或达到再次提醒周期时才通知。

通知只展示安全摘要和 Web 跳转，打开后先显示原报告快照，并提供刷新入口。

### 7.5 预测

预测不作为首批报表的普通开关。每一个预测目标必须单独登记，例如：

- 未来库存水平；
- 未来产量；
- 未来质量指标区间；
- 未来任务积压；
- 未来库位占用。

准入至少要求：

- 稳定、连续且满足最小覆盖率的历史数据；
- 明确预测对象、粒度和业务价值；
- 简单基线模型；
- 滚动历史回测；
- 误差指标和可接受阈值；
- 预测区间而非单点假精确值；
- 数据漂移和特征缺失监控；
- 模型版本、训练区间和适用范围；
- 只生成 advisory 结果。

数据不足、超出训练范围或回测不达标时必须拒绝预测或降级为历史趋势，不得为了体验生成无依据数字。

## 8. 用户体验规范

一份报表在聊天中的默认层级：

1. 一句话结论；
2. 查询范围、业务日期和 `dataAsOf`；
3. 3～5 个核心指标；
4. 趋势图或阶段图；
5. 需要关注的变化；
6. 默认折叠的证据明细；
7. 修改范围、比较、下钻、导出和订阅动作；
8. 默认折叠的口径与数据限制。

文本负责结论和解释，不重复朗读卡片全部数据。

### 状态必须区分

- `COMPLETE`
- `PARTIAL`
- `NO_DATA`
- `PERMISSION_DENIED`
- `TIMEOUT`
- `FAILED`
- `STALE`
- `DATA_INCOMPLETE`

某个数据分支失败时保留成功部分，并提供“仅重试失败部分”。不把工具失败、权限拒绝或数据不完整解释为空数据。

### 长报告交互

- 同一个用户问题只使用一个 assistant message 容器；
- 进度、部分结果和最终结果在原容器更新；
- 用户位于底部附近时才自动滚动；
- 用户正在阅读上方内容时显示“有新内容”，不强制跳到底部；
- 报表卡片避免嵌套滚动，长明细使用分组、分页或展开；
- 报表生成后提供“重试本次”“仅重试失败部分”“缩小范围”；
- 移动端和窄抽屉内不依赖横向滚动阅读核心结论。

### 角色化展示

同一份报表的数字和口径不因角色改变，但默认视图可以不同：

- 仓管优先看到库存、任务和库位；
- 质检优先看到质量指标、无标准和缺化验；
- 生产主管优先看到产量、订单、投入产出和闭环；
- 管理人员优先看到跨期变化和异常摘要。

角色化只能影响排序和默认展开，不得扩大数据权限或改变事实。

## 9. 数据与治理前置

### 9.1 立即开始积累的数据

即使前端报表尚未开发，也应尽快开始：

- 固定粒度库存快照；
- 统一库存流转事件；
- 生产订单状态事件；
- 实际领料事件；
- 实际产出事件；
- 标签和二维码阶段事件；
- 托盘任务和流转阶段事件；
- 化验记录及标准版本。

### 9.2 数据质量

每个数据集登记：

- 完整性；
- 唯一性；
- 新鲜度；
- 迟到率；
- 可换算率；
- 事件配对率；
- 对账差异；
- 已知缺口。

报表必须展示影响当前结论的数据质量问题，不能只写入后台日志。

### 9.3 维度与历史主数据

产品名称、规格、标准版本、仓库名称等主数据会变化。历史报表应保存稳定业务标识和当时的安全展示快照，避免改名后历史结果失真。

### 9.4 所有权

每个数据集、指标和报表都必须有业务 owner 和技术 owner。变更需要：

- 新版本；
- 影响说明；
- 固定数据测试；
- 跨期兼容判断；
- 审批和生效时间；
- 旧版本保留或退役策略。

## 10. 分阶段实施

### 阶段 A：报表基础和数据开始积累

1. 建立 `ReportDefinition`、`ReportRun`、`ReportContext` registry；
2. 建立确定性 Report Runner；
3. 固化业务时间、单位、迟到数据和修订策略；
4. 启动库存快照和关键事件采集；
5. 建立统一报表卡片、部分失败和原地重试协议；
6. 不开放预测。

### 阶段 B：首批可交付报表

1. `daily_production_overview_v1`；
2. `quality_assay_result_trend_v1`；
3. `quality_metric_trend_v1`；
4. 基于同一 `ReportRun` 的总结、跨期比较和安全导出；
5. 真实生产主管、质检用户验收。

每日生产报表作为业务旗舰样板，质量趋势用于验证标准版本、指标序列和复杂数据语义。

### 阶段 C：库存、投入产出和效率

1. 历史库存快照达到可用覆盖后开放库存水平趋势；
2. 库存事件去重和对账通过后开放库存流量趋势；
3. 先开放实际领料和稳定登记产出的独立序列；
4. 流程事件完整性达标后开放已登记流程效率；
5. 审计 `production_order_material`、`out_stock` 与库存流水的一致性，生产消耗趋势只采用确认领用扣减事实。

### 阶段 D：订阅和主动触发

1. 化验趋势/风险摘要；
2. 产量日报；
3. 库存异常变化；
4. 任务积压和流程超阈值；
5. 标签到入库长时间未完成。

先支持用户显式订阅，不允许模型自行创建订阅。

### 阶段 E：预测

1. 逐个选择预测目标；
2. 建立基线和回测；
3. 完成误差、漂移和拒绝策略；
4. 只开放建议用途；
5. 与生产计划写入保持隔离。

## 11. 首批验收门槛

### 事实与口径

- 所有权威数字由 Java/SQL 确定性计算；
- 所有指标具有代码、版本、公式、单位、分母和排除规则；
- 业务日期、记录时间和 `dataAsOf` 可见；
- 迟到数据和修订可识别；
- 报表数字可追溯到登记数据集和证据；
- 当前库存、历史快照和流转事件不混用。

### Agent 行为

- 遵循“主模型理解 → 报表/领域专家决策 → 登记报表调用 → 结果分析”；
- 主 Agent 不持有业务工具；
- `analytics_expert` 只运行登记报表，不获得全部领域工具；
- 模型不计算权威指标、不补缺失数据、不生成任意 SQL；
- 趋势追问复用 `ReportContext`，但不绕过模型和 Runtime 校验；
- 没有证据时不输出因果结论。

### 用户体验

- 直接报表请求通常一轮完成；
- 首个业务进度目标在 1 秒内出现；
- 简单报表首张有效卡片 P50 目标不超过 5 秒；
- 跨域报表完整结果 P95 目标不超过 15 秒；
- 报表范围、截止时间和口径版本始终可见；
- 空数据、无权限、部分失败、超时和数据不完整 100% 区分；
- 失败分支可以原地重试；
- 文本不重复卡片全部内容；
- 窄屏不通过多层滚动才能看到核心结论。

### 对比、导出与订阅

- 跨期比较使用同版本口径；
- 导出复用原 `ReportRun`；
- 下载权限、TTL 和导出审计有效；
- 订阅范围、频率、静默期、退订和去重有效；
- 权限变化后报告、下载和通知重新校验。

## 12. 现有数据事实门禁

数据库、写入链路和接口的重新审查结果统一登记在 `analytics-business-definition-confirmation-checklist.md`。该文件现已改为“现有数据事实与实现边界”，不再要求产品经理为系统不存在的概念补规则。

新增指标必须先回答：具体表和字段是什么、哪个现有业务动作写入、使用哪个时间字段、当前代码真实产生哪些状态、如何稳定关联，以及空数据代表什么。

当前事实边界：

- 生产计划只有订单中的参考 JSON，不存在审批版本、顺延或正式计划达成率；
- 确认生产领用扣减读取 `production_order_material.status=PICKED`，其 `picked_at` 与同事务出库/扣减时间一致；
- 旧 `semi_prepare_pool*` 与 `production_consumption_record` 不进入现行统计；
- 当前数据库没有返工、报废、损耗和 SLA 字段，相应指标不实现；
- 通用 XLSX 已作为当前正式导出，不等待品牌模板；
- 任何无法从现有资产确认的指标都保持不实现，而不是交给模型或产品经理补想象口径。

## 13. 明确不做

- 任意 SQL、任意表列和任意图表生成；
- 模型自行定义指标和阈值；
- 模型自行选择对它有利的比较期间；
- 用当前状态反推历史趋势；
- 用打印、二维码或入库数量冒充产量；
- 用当天投入和当天产出直接计算良率；
- 用平均耗时掩盖未完成和长尾任务；
- 把相关性描述成确定因果；
- 在数据不足时生成预测数字；
- 通过报表或通知执行库存、生产、质量或任务写操作。
