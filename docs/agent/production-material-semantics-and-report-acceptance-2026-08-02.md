# 生产领用口径复核与 Agent 报表回归验收

验收日期：2026-08-02
验收环境：本地开发数据库、Java Agent Gateway、Python Agent、Warehouse MCP、真实浏览器
结论：生产领用语义与生产投入—产出查询通过本轮验收；库存趋势的生产发布门禁仍未通过

## 1. 本轮结论

本轮纠正了此前对“半成品备料池”的误判，并以数据库结构、现行写入代码、MCP 工具和真实查询结果重新确认：

1. `semi_prepare_pool*` 和 `production_consumption_record` 属于已停用旧流程，不进入当前 Agent、MCP 或报表统计。
2. 当前成品生产领用事实来自 `production_order_material`。用户确认领用后，同一事务完成出库、库存扣减、领用记录写入和二维码释放；当前实际可达状态为 `PICKED`，时间字段为 `picked_at`。
3. “备料池余额”只作为用户可能继续使用的旧称。Agent 应把它解释为“已确认领用、库存已扣减、生产订单尚未完成的在制半成品”，不得查询或展示旧备料池余额。
4. 半成品订单可按最终确认的煮糖批次使用关系展示订单归属，但数据库没有独立的现场投料时间，因此不得把该关系解释为现场实际投料。
5. 生产投入与稳定登记产出是两条独立事实序列。当前数据库不能支持计划达成率、退料、返工、报废、损耗、收率或 SLA 指标，Agent 不得推算。

以上结论与 [报表分析现有数据事实与实现边界](analytics-business-definition-confirmation-checklist.md) 和 [生产投入—产出数据成熟度审计](production-input-output-data-readiness-audit-2026-07-31.md) 保持一致。

## 2. 本轮发现并修复的问题

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 旧称“备料池余额”可能被路由到旧语义 | 主 Agent 与生产专家提示中没有明确停用旧称的唯一映射 | 主 Agent、生产专家和 GoalContract 统一映射到 `IN_PROCESS_MATERIALS`，明确库存已扣减 |
| Java 偶发先于 Python 结束等待 | Java 默认等待 30 秒，小于 Python LLM 整轮 90 秒预算 | Java 默认等待调整为 100 秒 |
| 长上下文生产报表偶发“模型结构化决策响应超时” | 单次专家结构化分析碰到原 30 秒上限；工具调用本身不足 1 秒 | 单次模型决策预算调整为 45 秒，Python 整轮仍保持 90 秒，不增加模型调用 |
| MCP 预热与源码工具清单不一致 | 本地运行的 Warehouse MCP 可执行 JAR 早于当前源码 | 重新构建当前 MCP JAR；预热随后成功 |

超时调整不改变“模型理解 → 专家决策 → 工具调用 → 结果分析”架构，也不会主动延长正常请求；它只避免合法慢请求被错误地在 30 秒处截断。

## 3. 真实验收用例

### 3.1 停用旧称兼容

输入：`查询备料池余额`

实际结果：

- 正确进入生产在制物料查询；
- 返回 2 托已确认领用的黄中冰，均属于生产订单 `PO202605070003`；
- 返回托盘 `BT0010Z4`、`BT000YGI`、所在仓库和位置、件数、重量及领料人；
- 明确说明库存已经扣减，且在制记录不代表仍可再次领用、质量已放行或实时库存结余；
- 未调用旧备料池余额接口，未展示内部状态枚举。

判定：通过。

### 3.2 现行在制物料自然语言

输入：`当前有哪些已确认领用但订单未完成的半成品？`

实际结果：返回与 3.1 相同的两条现行事实，并正确解释订单状态和托盘信息。

判定：通过。

### 3.3 生产领用与产出趋势

输入：`查询2026-06-30到2026-07-21的生产领用和产出趋势`

实际结果：

- 实际领料：2 条、1 个订单，1 整板加 16 散件，折算 41 件、1640 kg；
- 稳定登记产出：2 条、2 个订单，3 整板加 16 散件，折算 121 件、3640 kg；
- 三个生产订单分别展示投入和产出事实，未将无事实的订单补零后宣称完成；
- 明确领料按 `picked_at`、产出按 `production_date` 统计，两条序列不直接相除；
- 返回 `production_input_output_flow` 卡片，没有暴露 `PREPRINTED` 等内部枚举；
- 在同一浏览器会话先查询旧称、再查询该报表，未再出现结构化决策超时。

判定：通过。

### 3.4 生产订单原料追溯

输入：`查询生产订单 PO202606300003 的原料领用情况`

实际结果：返回 2 条已确认领用记录，合计 1640 kg，并明确领用确认时已经完成库存扣减；返回 `production_material_trace` 卡片，没有生成计划差异、损耗或收率。

判定：通过。

## 5. 仍未通过的边界

1. 库存趋势的本地历史回放已经证明查询、卡片和导出链路，但不能替代生产可信快照门禁。
2. 当前本地环境会关机，缺少连续真实日终快照；该门禁仍为 `BLOCKED`，不得宣称库存趋势已具备生产发布条件。
3. 当前只完成少量人工性能样本，不能据此声称达到 P50/P95 目标。
4. 预测没有明确预测目标和足够可信历史，继续保持不实现；不得让模型自由外推预测数字。

## 6. 下一步计划

### P0：先稳定现有六类登记报表

1. 增加按阶段记录的端到端耗时采样，至少覆盖主 Agent、专家决策、工具调用、结果分析和首个可见进度；用固定用户语料重复采样后再给出 P50/P95。
2. 将 MCP 工具注册表与运行 JAR 的一致性校验纳入启动/发布门禁，避免“源码正确、运行包过期”。
3. 保留 45/90/100 秒三层预算，但优先压缩专家输入事实和减少无效上下文；不得通过继续提高超时替代性能优化。

### P1：实现一个用户导向的“今日经营概览”登记报表

新增一个受控组合报表，而不是让模型临时拼接 SQL。它只组合现有已登记事实：

- 今日稳定登记产出；
- 今日化验结果与无标准/标准多候选等数据质量事实；
- 当前库存水平，以及仅在可信门禁通过后展示的库存历史变化；
- 今日生产订单确认领用与稳定登记产出的两条独立序列；
- 已登记托盘任务的完成、进行中和处理耗时。

后端负责确定性聚合和数据质量说明；模型只负责摘要、重点提示和追问建议。首版卡片按“产量、质量、库存、生产流转、任务效率”分区，可展开/收起，并复用不可变 `ReportRun` 与 XLSX 导出。

### P2：跨期比较与综合总结

1. 让今日概览支持与上一可比自然日、上周同期或用户指定区间比较；比较仍复用冻结的登记报表事实。
2. 只输出可由数字直接支持的变化和数据缺口，不输出原因推断。
3. 支持多工作表 XLSX：摘要页加各登记报表明细页；不新增 PDF、签字栏或品牌模板前置要求。

### P3：预测与主动触发的准入审计

1. 先盘点可预测目标、历史覆盖、修订率和数据质量，不先实现预测模型。
2. 只有目标字段、时间口径、训练窗口和验收指标都能由现有资产确认后，才选择一个最小预测目标；否则保持阻断。
3. 主动触发仅在登记报表稳定、调度可靠且通知对象/频率明确后接入；第一版只生成报告或提醒，不执行库存或生产写操作。

## 7. 当前建议

下一开发切片应选择 P0 和 P1：先关闭性能与制品一致性风险，再实现“今日经营概览”。这比继续新增单点报表更贴近用户问题，也能复用已完成的六类登记报表，同时不引入数据库中不存在的业务概念。

> 2026-08-03 进度更新：制品一致性门禁、分阶段性能采样和 `today_operations_overview_v1@1` 工程实现已完成。性能采样确认端到端 P95 仍未达标，因此功能验收不等于性能封板；真实部署烟雾测试与后续模型阶段优化仍需继续。
