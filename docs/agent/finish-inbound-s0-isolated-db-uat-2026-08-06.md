# 成品入库 S0 隔离数据库验收记录（2026-08-06）

## 1. 结论

- `FINISH_INBOUND_S0_LOCAL_MYSQL_UAT_GO`
- `BATCH_ROLLBACK_PASS`
- `CONFIRM_CANCEL_RACE_PASS`
- `FIXTURE_CLEANUP_PASS`
- `AGENT_L3_EXECUTION_NO_GO`
- `PRODUCTION_NOT_RELEASED`

本轮验证的是既有人工成品入库事务的批量原子性和确认/取消并发终态，不是 Agent execute 验收。没有登记、实现或启用任何 L3 工具。

## 2. 环境与样本边界

- 后端：本地隔离端口 `38082`，关闭调度任务。
- 数据库：`127.0.0.1` 本地 MySQL；脚本拒绝非本机数据库地址。
- 样本：独立库位、托盘和 `FINISH_IN + PENDING` 任务，统一使用唯一 `S0UAT_*` 前缀。
- 用户：本地管理员账号，只用于走真实认证和现有人工 HTTP 接口。
- 清理：脚本在 `finally` 中按外键逆序删除库存事件、流转、库存、入库单、任务、托盘和库位，再按精确主键断言零残留。
- 凭据、JWT、数据库口令和模型密钥未写入脚本输出或本文档。

可重复脚本：`scripts/verify-finish-inbound-s0.ps1`。

## 3. 首轮验收发现的真实竞态

初次确认/取消竞争复现了非法混合终态：

- 托盘：`INSTOCK`
- 任务：`CANCELED`

根因不是缺少托盘行锁，而是 MySQL `REPEATABLE READ` 快照语义：取消事务在等待托盘锁前已经做过普通读取；确认事务先提交后，取消事务虽然取得了最新的 `INSTOCK` 托盘行，随后仍可能从旧快照读取到 `PENDING` 任务并取消它。

修复保持既有领域架构不变：

1. 取消事务取得托盘行锁后，托盘最新状态不是 `PENDING` 时立即结束；
2. 当前轮次待处理入库任务改为 `SELECT ... FOR UPDATE` 当前读；
3. 锁顺序仍为按托盘主键排序后“托盘 → 任务”，没有引入新的跨模块事务入口；
4. 新增单元合同，锁定已确认托盘不能再取消旧快照任务，并验证任务锁 SQL 包含 `FOR UPDATE`。

## 4. 修复后验收输入与结果

执行参数：一轮批量回滚、五轮确认/取消竞争。脚本输出前缀为 `S0UAT_20260806020602_439b63`。

| 用例 | 输入/流程 | 结果 |
|---|---|---|
| 整批回滚 | 两个成品入库任务；第一项使用有效独立库位，第二项使用不存在库位 | HTTP 业务结果 `500`；两个托盘和任务仍为待处理；首项库存、入库单、库位容量、流转和库存事件均为 0，`PASS` |
| 竞争 1 | 对同一托盘并发发送确认和取消 | 确认胜出；确认 `200`、取消 `200`；最终为已入库/已确认，且只有一套库存事实，`PASS` |
| 竞争 2 | 同上 | 取消胜出；确认 `500`、取消 `200`；最终为空闲/已取消，无库存写入，`PASS` |
| 竞争 3 | 同上 | 取消胜出，`PASS` |
| 竞争 4 | 同上 | 取消胜出，`PASS` |
| 竞争 5 | 同上 | 取消胜出，`PASS` |

竞争失败方返回业务失败或幂等式无操作属于预期；验收判断以唯一合法数据库终态和业务事实是否一致为准，不要求两个 HTTP 请求都报错或固定某一方胜出。

脚本最终返回 `Result=PASS`，并在输出后完成清理断言；因此该前缀没有遗留验收行。

## 5. 门禁影响

本证据关闭：

- 既有成品入库批量第二项失败时的整批事务回滚；
- 既有确认/取消竞争只有一个合法业务终态；
- S0 专用样本的可重复创建与清理。

本证据不关闭：

- 精确表单级 L2 执行预览；
- 用户确认、撤销、一次性 execution token；
- 幂等请求与结果恢复；
- Agent 专用执行权限；
- 与业务事务同边界的完整执行审计；
- 隔离角色的 L3 execute UAT 和生产发布评审。

因此下一切片仍是 S1 `preview_finish_inbound_execution`，而不是直接实现 `execute_finish_inbound_task`。
