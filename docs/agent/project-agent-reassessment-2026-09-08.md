# Agent 项目复审与后续推进建议

复审日期：2026-09-08。对象：当前本地工作区代码、设计和历史验收记录。

后续进展：本文保留实施前复审基线。第一批生产日报只读接入已完成本地开发与自动化测试，当前数量为 59 个目标、55 个 Java 工具；真实模型和数据库联调尚待验收，详见 [实施与测试记录](production-daily-report-agent-2026-09-08.md)。

## 1. 结论与证据边界

- 当前不是从零建设 Agent：已有统一目标契约、专家决策、受控工具执行、事实校验、交互卡片、报表和知识检索基础。
- 成品入库已有独立的受控确认及实际执行链路；不能因为 MCP 没有 `execute_*` 工具就判断“尚未实现写入”。
- 下一步应先对齐现行业务和发布基线、验收已有能力，再完善成品入库。其他写入需单独确认业务范围，不能把历史出库/调拨预览误当作已验收的 Agent 执行能力。
- 本次未修改业务实现、未操作业务数据、未连接生产数据库，也未部署。本次自动化通过不等于当前生产版本、真实模型和现场操作全部验收通过。

## 3. 需要优先处理的差异

### 3.1 生产日报尚未与 Agent 生产分析衔接

新增 Web 日报使用 `production_daily_report`、`production_daily_report_section` 等数据结构，并具有独立查看、编辑、导出权限。当前 Agent 生产产出报表通过 `ProductionOrderOutputMapper.listRegisteredOutputsForReport` 读取生产订单登记产出；今日运营概览继续组合这一口径。

因此，“生产日报已有数据”不保证“Agent 今日产量报表有同样数据”。这是已确认的数据源差异，不是已证实的 SQL 计算错误。

推进方式：先基于日报现有字段、明细、单位及草稿/提交状态，提供日报查询目标与结构化结果；对外明确区分“生产日报填报量”和“订单登记产出”。没有明确业务对应关系前不得相加、覆盖、计算差额为损耗，也不得自行认定某一来源必然是真实产量。若同一句“今日产量”涉及两种口径，应明确标识或引导选择。

相关代码：`production/controller/ProductionDailyReportController.java`、`production/mapper/ProductionDailyReportMapper.java`、`production/mapper/ProductionDailyReportSectionMapper.java`、`analytics/service/impl/RegisteredReportServiceImpl.java`。

### 3.2 设备管理尚未接入 Agent 工具契约

Web 后端已有设备台账、维修和基础资料接口；当前模型工具 schema 和 MCP 工具配置中没有对应设备能力。不能把 Web 页面可用理解为 Agent 可查询。

如纳入下一阶段，先做设备台账与维修记录只读查询，仅围绕现有业务字段设计目标；没有可靠依据不新增设备效率、停机损失、预测性维修等指标。设备写入不建议与本轮入库完善一起启动。

### 3.3 库位粒度已变更，旧验收口径必须退出

当前库位粒度 V2 不向用户要求左右、排、层。精确入库快照的用户输入字段也已移除这些坐标。后端兼容值不代表现场位置。

但 `finish-inbound-l3-gate.yaml` 仍保留 2026-08-13 的 `side` 输入和历史发布结论。后续应同步当前协议、用例、发布门禁；不能照旧文档重新开发侧别或据旧 `NO_GO` 宣称当前所有实现均不可用。

依据：`docs/warehouse/warehouse-location-granularity-v2.md`、`agent/model/FinishInboundExecutionPreviewSnapshot.java`。

### 3.4 本地、历史发布和当前生产不能混为一个基线

工作区有大量未提交的 Agent、Java、MCP、Web 修改，以及未跟踪的 Android、库位相关资产。已存在 2026-08-29 的真实模型生产上线记录，但这只是历史证据。

后续需核对当前部署的代码版本、规划模式、工具注册 hash、专家配置、知识库版本、精确预览版本和写入开关；本次未连接服务器重新确认。建议生成一次匹配的发布清单，避免只更新 Java/Web 而遗漏受协议影响的 Agent/MCP。

### 3.5 权限疑点复核结果：未确认现行仓管流程故障

旧 `FinishInboundExecutionControlController` 保留管理员限制，但当前 Web `confirmAndExecuteFinishInbound` 调用新的 S3 `confirm-and-execute` 路径。S3 使用 `requireAgentAccess` 和 `agent:finish-inbound:execute` 专门权限，而不是管理员角色硬限制。

不应直接放开旧接口来“修复”未经证实的问题。真实验收仍需覆盖仓管、管理员、普通员工、缺权限账号，确认页面入口和后端授权一致。

## 5. 建议推进顺序

### 第一批：已有能力与现行业务对齐

1. 整理当前工作区和发布清单，更新能力矩阵及历史门禁的有效状态，不覆盖其他人的改动。
2. 接入生产日报只读查询，明确与订单登记产出的区别；同步今日运营回答的数据来源和覆盖范围。
3. 对已有 58 个目标按用户场景回归：模糊产品、同名候选、相对时间、单日、连续追问、多订单、跨页结果、无数据、权限不足、超时恢复、任务完成后卡片刷新。
4. 核验真实库存快照连续性、报表导出与页面一致性、当前知识库来源和引用。缺数据与数值为零必须区分；模拟不能当正式库存趋势。
5. 输出每项输入、前置数据、输出/截图、判断及版本。真实数据写入测试只在隔离环境执行。

### 第二批：完善成品入库闭环

沿用现有链路：模型理解 → 专家补齐产品/库位/二维码 → 受控预览 → 用户明确确认 → Java 执行与审计 → 查询并展示实际结果。

重点场景：

- “3号库位入库2板黄冰糖”：产品重名、数量不足、二维码重复、库位不可用或容量不足。
- 明确区分“已绑定且待入库二维码”与“空闲固定二维码”；前者处理待办，后者先创建对应任务，不能混用权限或重复创建。
- 只管理到库位，不追问左右排层；用户说“二维码/一板糖”，内部字段不直出。
- 预览后任务已被 App/Web 处理、预览过期、容量改变、重复点击、确认与取消并发、超时后重试、断线后查询执行状态。
- 成功后任务、卡片可选状态、库存及库位详情一致；失败和不确定结果不能显示为已成功，也不能误称必然未写入。
- 测试事务整批回滚、幂等、专门权限、审计，以及按既定规则处理历史任务。

不必为实现写入另起 Agent 架构，也不必优先把安全执行端点暴露为自由模型工具。模型负责理解及准备，业务服务负责校验及执行，用户确认是明确边界。

### 第三批：在范围获确认后扩展

设备台账/维修只读可独立追加。写入建议在成品入库验收后，再讨论调拨、出库；已有预览和业务接口可复用，但分别补充精确预览、权限、幂等、状态校验、审计与验收，不能简单复制接口注册。

个人微信采集仍维持暂停；退料、旧半成品备料池、未经定义的损耗/预测不纳入本轮。

## 6. 架构约束

- 继续复用 GoalContract，不以新增关键词分支代替模型理解或专家决策。
- 主模型不直接访问任意工具；专家只见目标允许工具，业务身份以服务端解析为准。
- 分析依据受控事实与真实字段，指标计算在业务侧，模型不补造数据。
- 完成结论由证据及契约校验约束；对用户展示必要的处理进度，不暴露内部字段或无意义解释。
- 不为覆盖复杂请求盲目提高全局工具调用次数；先确认组合目标和事实闭环是否完整。

推荐下一项实际开发：生产日报只读目标与运营口径衔接，同时建立新版场景回归清单；其后集中完善现有成品入库。
