# 成品入库首个 L3 候选准入设计（2026-08-05）

## 1. 结论

本轮完成的是基于现有代码、数据库字段和页面表单的准入设计，不是写工具实现。

- `FINISH_INBOUND_L3_DESIGN_READY`
- `FINISH_INBOUND_S0_CODE_AND_UNIT_CONTRACT_GO`
- `FINISH_INBOUND_S0_ISOLATED_DATABASE_UAT_REQUIRED`
- `FINISH_INBOUND_EXECUTION_IMPLEMENTATION_NO_GO`
- `AGENT_L3_EXECUTION_NO_GO`
- `PRODUCTION_NOT_RELEASED`

当前不得登记、开放或调用 `preview_finish_inbound_execution`、`execute_finish_inbound_task`。现有 `preview_task_transition` 仍是 L2 任务资格预览和既有弹窗交接，不是执行计划、确认记录或 execution token。

首个候选严格限定为 `FINISH_IN + PENDING` 的成品入库确认。现有确认接口同时支持 `SEMI_IN`，但首个 Agent L3 不得因此顺带开放半成品入库，也不得扩展到出库或调拨。

## 2. 审计到的现有真实流程

人工页面当前调用 `POST /api/pallet-codes/tasks/confirm`，权限为 `task:confirm`，请求是 `ConfirmPalletInBatchDTO.items`。单项已有字段如下：

| 字段 | 现有含义 | 首个候选约束 |
|---|---|---|
| `code` | 托盘码 | 必填；1～20 个，去重后按固定顺序处理 |
| `warehouseName` | `warehouse.warehouse_name` | 必填；由后端重新解析并校验状态 |
| `entryDate` | 入库日期 | 可选；为空时沿用现有任务/托盘生产日期规则 |
| `side` | 左/右，默认左 | 只允许现有枚举值 |
| `rowNumber`、`layer` | 指定位置或为空自动分配 | 首个 Agent 版本不接收，由既有分配规则决定 |
| `quantity`、`unit` | 入库数量及单位 | 显示最终有效值；有关联生产产出码时以后端记录为准 |
| `remark` | 备注 | 可选，遵守现有数据库长度限制 |

`PalletCodeServiceImpl.confirmFinishedTaskInBatch` 已使用事务，并逐条调用单托盘确认。单托盘确认会锁定托盘，重新核对当前轮次待处理任务，然后根据任务类型进入既有业务分支。成品入库可能在同一业务事务中联动：

- 成品入库单、明细、库存和库位容量；
- 库存移动事件；
- 托盘状态、当前任务状态和托盘流转记录；
- 已有化验关联或回填逻辑；
- 生产订单产出码、产出和订单进度；
- 当任务关联已登记的历史半成品用料时，更新相应余额并登记消耗记录。

这些都是现有调用链，不是新增业务口径。Agent 层不得复制或重写这些规则，只能在门禁关闭后调用唯一的既有领域事务入口。

## 3. 当前阻断项

| 阻断项 | 代码事实 | 风险 |
|---|---|---|
| 当前预览不是精确执行计划 | `TaskTransitionPreviewDTO` 只有版本、transition 和托盘码 | 用户最终选择的仓库、日期、侧、数量、单位和备注没有被绑定 |
| 确认/取消并发未统一 | 审计时确认使用行锁、取消未使用；S0 已统一为显式托盘行锁并按托盘主键固定排序 | 代码和单元合同已关闭；仍需隔离数据库并发复验 |
| 批量边界不完整 | 审计时只有 `@NotEmpty`；S0 已补最多 20 条、服务层双重校验、规范化/别名去重和写前完整预解析 | 代码和单元合同已关闭；仍需隔离数据库整批回滚复验 |
| 缺少专用 Agent 执行权限 | 当前人工入口只有 `task:confirm` | 无法把人工页面权限与 Agent 代执行权限分离 |
| 缺少执行幂等记录 | 当前没有 execution token/idempotency key 生命周期 | 重试、双击或断网恢复可能造成重复执行或结果不确定 |
| 缺少完整写入审计 | 现有工具调用审计不覆盖确认、消费、业务结果和恢复全过程 | 无法闭合“谁确认了什么、执行了什么、最终怎样” |
| 审计与业务事务未绑定 | 当前 Gateway 先调用工具再登记工具审计 | 如果未来直接用于写入，业务成功后审计失败会形成不可接受的不一致 |
| 自动化覆盖不足 | 当前没有确认/取消竞争、重复执行、批量回滚、断网重试和审计失败测试 | 无法证明写入失败关闭和一次性语义 |

现有 `@LogOperation` 切面也不能直接作为 L3 解决方案：它不是这条入库入口的当前审计边界，并且失败路径需要单独整改和复核。首个 L3 必须使用专门的持久化执行审计，而不是简单增加一个注解。

## 4. 两类预览必须分开

### 4.1 保留现有资格预览

`preview_task_transition` 继续只回答：所选托盘当前是否存在匹配的待处理任务、能否打开类型匹配的既有业务弹窗。它不持有最终表单值，不签发执行权。

### 4.2 未来的精确执行预览

计划名称：`preview_finish_inbound_execution`，风险 L2，当前未登记、未实现。

它只能在用户完成成品入库表单后接收受控字段，后端完成规范化和重新读取，返回用户可见的确定摘要，例如：托盘、产品、目标仓库、入库日期、侧、最终有效数量/单位和备注。服务端快照还需保存但不向模型暴露：

- 当前任务 id、类型、状态、轮次和创建时间；
- 托盘 id、状态、当前轮次、产品和更新时间；
- 产品状态、每板件数、可堆叠规则和更新时间；
- 目标仓库 id、状态和更新时间；
- 有关联生产产出码时的 id、状态、数量、单位和库存关联；
- 有关联历史用料余额时的 id、状态、剩余数量和更新时间；
- 全部规范化最终输入及状态摘要哈希。

上述服务端字段只是并发重检依据，不能作为新增业务规则。执行时仍必须重新读取当前事实，快照一致并不等于可以跳过既有业务校验。

## 5. 确认、令牌和执行协议

推荐的首版交互：

`用户填写现有弹窗 → 精确 L2 预览 → 页面展示确定摘要 → 用户点击“确认执行” → 服务端签发一次性 executionToken → 执行`

约束如下：

1. 首版确认必须是用户在受控界面上的显式按钮动作；模型不能根据自己的回复、用户早先的泛化表达或模型生成的 `confirmationText` 代替确认。
2. 确认记录绑定用户、Agent 会话、精确预览引用、内容哈希、权限快照、确认时间和短有效期，并支持确认前撤销。
3. `executionToken` 和 `idempotencyKey` 由服务端生成和保存；模型不得创建、改写或展示给普通用户。
4. 未来 `execute_finish_inbound_task` 只接收受控 token 与 idempotency key，不接收完整入库 DTO，也不能修改已确认的仓库、日期、侧、数量、单位或备注。
5. 同一确认只能成功消费一次；相同幂等键必须返回相同已提交结果，不能再次执行业务事务。

## 6. 建议的事务边界

执行设施和既有业务事务必须形成可恢复状态机，不能在独立事务中先消费 token 再写库存：

1. 在业务事务前持久化执行请求和审计起点；如果执行基础设施不可用，失败关闭，不进入业务写入。
2. 业务事务内锁定执行记录，按规范化托盘码固定顺序锁定托盘，重新读取权限、确认、有效期、任务、托盘、产品、仓库、生产关联和用料余额。
3. 状态摘要不一致时整批拒绝，不部分执行；一致时调用现有成品入库领域入口。
4. 业务写入、token 消费、成功结果和成功审计在同一提交边界内落定；业务回滚时 token 不得被标记为已消费。
5. 对于事务外可观察的技术失败，执行记录保留结构化失败原因并允许按同一幂等键安全查询结果；不得用再次执行业务来“补审计”。

真正实现前必须通过数据库事务传播和异常路径测试验证这一设计，不能仅凭 `@Transactional` 注解推断已经满足。

| `TASK_STATE_CHANGED` | 托盘任务状态已变化，请刷新后重试 | 否 |

## 8. 实施切片与放行条件

1. **S0 既有业务加固**：代码和单元合同已完成——统一确认/取消托盘锁顺序；批量上限 20、规范化/别名去重、固定排序；标签关联变化时在取得意外行锁前失败关闭。隔离数据库并发胜者和整批回滚复验仍待完成。该切片不增加 Agent 写能力。
2. **S1 精确 L2 预览**：实现成品入库表单级预览、不可变快照和用户可读摘要；仍只回到确认界面，不执行写入。
3. **S2 确认与执行基础设施**：持久化确认、撤销、token、幂等请求、结果查询和完整审计；先用无业务副作用的测试适配器验证状态机。
4. **S3 单一 execute 候选**：只接入成品入库，独立权限 `agent:finish-inbound:execute`，功能开关默认关闭，在隔离数据库执行真实角色 UAT。
5. **S4 单场景放行评审**：全部门禁通过后才决定是否启用；出库、调拨和主动触发继续不在范围。

## 9. 后续需要产品确认、当前不应猜测的事项

- 哪些真实角色可以获得 `agent:finish-inbound:execute`；建议新增权限后默认不分配，待职责评审和 UAT 再决定。
- 预览、确认、执行和审计记录的保留期限；现有业务资产没有给出统一口径。
- 首版是否接受自然语言确认；本设计推荐首版只接受受控按钮，待安全数据证明后再评估自然语言确认。

以上三项不阻塞 S0/S1 的工程准备，但在 S3 前必须明确。

## 10. 2026-08-06 S0 实施记录

本次只修改既有人工任务事务的安全边界，没有新增 MCP 工具、Agent 权限、确认令牌或业务规则：

- `ConfirmPalletInBatchDTO` 和服务层共同限制单次最多 20 个托盘；
- 整批先规范化并解析全部输入，拒绝重复文本以及不同标签指向同一托盘，再开始任何业务写入；
- 以托盘主键排序，确认和取消都通过同一个显式 `SELECT ... FOR UPDATE` 锁入口处理；
- 真正加锁前再次验证标签仍指向预解析的托盘，关联变化时整批失败关闭；
- 外层 `@Transactional` 仍覆盖整个批次，任何一项失败都会抛出异常并阻止后续项。

新增 10 项单元合同覆盖入库/取消 20 条上限、入库/取消别名重复、确认顺序、取消锁顺序、统一行锁及其 `FOR UPDATE` SQL、标签关联变化和整批事务注解边界。该证据证明代码合同已建立，但 Mockito 单元测试不能证明第二项失败时第一项写入已经由 MySQL 回滚，也不能替代真实锁等待，因此 S0 当前为 `PARTIAL`。下一步必须在隔离数据库使用专用样本做两项复验：确认/取消并发只有一个确定性结果，以及第二项失败后第一项的全部业务写入均回滚。
