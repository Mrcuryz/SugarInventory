## 1. 结论

本文先冻结基于现有代码、数据库字段和页面表单的准入设计；截至 2026-08-10，S0 业务加固、S1 精确 L2 预览、S2 零写入控制面和 S3 受控界面真实领域执行候选已经完成本地隔离验收。S3 默认关闭、专用权限默认不分配、没有登记 MCP execute 工具；S4 放行评审尚未完成。

- `FINISH_INBOUND_S1_EXACT_L2_PREVIEW_LOCAL_UAT_GO`

- `PRODUCTION_NOT_RELEASED`

当前可以调用已登记的 L2 `preview_finish_inbound_execution` 生成精确表单预览；它没有执行权。S2 已提供不经模型调用的确认、撤销、一次性凭据、幂等结果重放和专用审计控制面。S3 在默认关闭的受控 Web 入口中复用既有成品入库领域事务，完成一次真实写入和断线后结果重放；执行凭据仍只存在于服务端。仍不得登记、开放或调用 `execute_finish_inbound_task`。现有 `preview_task_transition` 继续只负责任务资格预览和既有弹窗交接，不是精确执行计划、确认记录或 execution token。

首个候选严格限定为 `FINISH_IN + PENDING` 的成品入库确认。现有确认接口同时支持 `SEMI_IN`，但首个 Agent L3 不得因此顺带开放半成品入库，也不得扩展到出库或调拨。

## 2. 审计到的现有真实流程

人工页面当前调用 `POST /api/pallet-codes/tasks/confirm`，权限为 `task:confirm`，请求是 `ConfirmPalletInBatchDTO.items`。单项已有字段如下：

| 字段 | 现有含义 | 首个候选约束 |
|---|---|---|
| `code` | 托盘码 | 必填；1～20 个，去重后按固定顺序处理 |
| `warehouseName` | `warehouse.warehouse_name` | 必填；由后端重新解析并校验状态 |
| `entryDate` | 入库日期 | 可选；为空时沿用现有任务/托盘生产日期规则 |
| `side` | 左/右，默认左 | 只允许现有枚举值 |
| `rowNumber`、`layer` | 指定位置或为空自动分配 | 首个 Agent 版本不接收，由既有分配规则决定 |
| `quantity`、`unit` | 入库数量及单位 | 显示最终有效值；有关联生产产出码时以后端记录为准 |
| `remark` | 备注 | 可选，遵守现有数据库长度限制 |

`PalletCodeServiceImpl.confirmFinishedTaskInBatch` 已使用事务，并逐条调用单托盘确认。单托盘确认会锁定托盘，重新核对当前轮次待处理任务，然后根据任务类型进入既有业务分支。成品入库可能在同一业务事务中联动：

- 成品入库单、明细、库存和库位容量；
- 库存移动事件；
- 托盘状态、当前任务状态和托盘流转记录；
- 已有化验关联或回填逻辑；
- 生产订单产出码、产出和订单进度；
- 当任务关联已登记的历史半成品用料时，更新相应余额并登记消耗记录。

这些都是现有调用链，不是新增业务口径。Agent 层不得复制或重写这些规则，只能在门禁关闭后调用唯一的既有领域事务入口。

## 4. 两类预览必须分开

### 4.0 用户业务目标到受控表单的引导层

技术接口验收不能替代真实用户场景验收。用户通常不会先给出完整 DTO，而会说“3号库位入库2板黄冰糖”。该表达中的“2板”表示本次要选择两个成品入库托盘任务，不表示把每个二维码的入库数量都改成 2 板。首版引导链路固定为：

`模型理解业务目标 → 物流专家识别缺失信息 → 产品/库位受控解析 → 查询该具体产品的待入库二维码 → 用户恰好选择 N 个二维码 → 资格预览 → 既有业务弹窗核对 → 精确 L2 预览 → 受控按钮确认`

必须补齐或确认的范围只有：具体产品、目标库位、板数和与板数完全一致的二维码。产品名称存在多个规格时必须展示产品候选卡片，不得按大类或模糊名称直接执行；二维码查询由 Runtime 使用已确认产品的内部引用精确过滤，`productId` 不暴露给模型或用户。库位解析也必须来自受控解析器，不能猜测库位 ID。

入库日期、左/右侧、数量/单位和备注不应全部变成对话式追问，否则用户体验会退化成逐字段填表。首版继续沿用现有业务表单默认值：日期沿用现有任务/生产日期规则、侧默认左、位置自动分配、数量/单位遵守生产产出记录或当前表单规则；这些值必须在既有弹窗和精确预览中展示，用户可以修改允许修改的字段并在最终确认前复核。引导层本身没有写入权，也不能把用户最初的自然语言当作最终执行确认。

### 4.1 保留现有资格预览

`preview_task_transition` 继续只回答：所选托盘当前是否存在匹配的待处理任务、能否打开类型匹配的既有业务弹窗。它不持有最终表单值，不签发执行权。

### 4.2 已实现的精确执行预览（S1）

名称：`preview_finish_inbound_execution`，风险 L2，已登记、实现并完成本地 Agent 全链路验收。

它只能在用户完成成品入库表单后接收受控字段，后端完成规范化和重新读取，返回用户可见的确定摘要，例如：托盘、产品、目标仓库、入库日期、侧、最终有效数量/单位和备注。服务端快照还需保存但不向模型暴露：

- 当前任务 id、类型、状态、轮次和创建时间；
- 托盘 id、状态、当前轮次、产品和更新时间；
- 产品状态、每板件数、可堆叠规则和更新时间；
- 目标仓库 id、状态和更新时间；
- 有关联生产产出码时的 id、状态、数量、单位和库存关联；
- 有关联历史用料余额时的 id、状态、剩余数量和更新时间；
- 全部规范化最终输入及状态摘要哈希。

上述服务端字段只是并发重检依据，不能作为新增业务规则。执行时仍必须重新读取当前事实，快照一致并不等于可以跳过既有业务校验。

## 5. 确认、令牌和执行协议

推荐的首版交互：

`用户填写现有弹窗 → 精确 L2 预览 → 页面展示确定摘要 → 用户点击“确认执行” → 服务端签发一次性 executionToken → 执行`

约束如下：

1. 首版确认必须是用户在受控界面上的显式按钮动作；模型不能根据自己的回复、用户早先的泛化表达或模型生成的 `confirmationText` 代替确认。
2. 确认记录绑定用户、Agent 会话、精确预览引用、内容哈希、权限快照、确认时间和短有效期，并支持确认前撤销。
3. `executionToken` 和 `idempotencyKey` 由服务端生成和保存；模型不得创建、改写或展示给普通用户。
4. 未来 `execute_finish_inbound_task` 只接收受控 token 与 idempotency key，不接收完整入库 DTO，也不能修改已确认的仓库、日期、侧、数量、单位或备注。
5. 同一确认只能成功消费一次；相同幂等键必须返回相同已提交结果，不能再次执行业务事务。

## 6. 建议的事务边界

执行设施和既有业务事务必须形成可恢复状态机，不能在独立事务中先消费 token 再写库存：

1. 在业务事务前持久化执行请求和审计起点；如果执行基础设施不可用，失败关闭，不进入业务写入。
2. 业务事务内锁定执行记录，按规范化托盘码固定顺序锁定托盘，重新读取权限、确认、有效期、任务、托盘、产品、仓库、生产关联和用料余额。
3. 状态摘要不一致时整批拒绝，不部分执行；一致时调用现有成品入库领域入口。
4. 业务写入、token 消费、成功结果和成功审计在同一提交边界内落定；业务回滚时 token 不得被标记为已消费。
5. 对于事务外可观察的技术失败，执行记录保留结构化失败原因并允许按同一幂等键安全查询结果；不得用再次执行业务来“补审计”。

真正实现前必须通过数据库事务传播和异常路径测试验证这一设计，不能仅凭 `@Transactional` 注解推断已经满足。

## 10. 2026-08-06 S0 实施记录

本次只修改既有人工任务事务的安全边界，没有新增 MCP 工具、Agent 权限、确认令牌或业务规则：

- `ConfirmPalletInBatchDTO` 和服务层共同限制单次最多 20 个托盘；
- 整批先规范化并解析全部输入，拒绝重复文本以及不同标签指向同一托盘，再开始任何业务写入；
- 以托盘主键排序，确认和取消都通过同一个显式 `SELECT ... FOR UPDATE` 锁入口处理；
- 真正加锁前再次验证标签仍指向预解析的托盘，关联变化时整批失败关闭；
- 外层 `@Transactional` 仍覆盖整个批次，任何一项失败都会抛出异常并阻止后续项。

初次本地 MySQL 竞争验收发现过一个真实非法组合：确认事务先提交后，取消事务可能在 `REPEATABLE READ` 旧快照中读到 `PENDING` 任务，最终形成托盘 `INSTOCK`、任务 `CANCELED`。修复后，取消路径在取得托盘行锁后先按最新托盘状态失败关闭，并对当前轮次待处理入库任务执行 `FOR UPDATE` 当前读；新增单元合同锁定该场景和 SQL 合同。

随后使用 `scripts/verify-finish-inbound-s0.ps1` 在 `127.0.0.1` 本地 MySQL 完成一轮批量回滚与五轮确认/取消竞争复验。批量第二项使用不存在库位触发失败，首项产生的库存、入库单、容量、流转和库存事件均回滚；并发复验同时覆盖确认胜出和取消胜出，未再出现混合终态。全部带唯一前缀的测试数据在脚本 `finally` 中清理并通过零残留断言。S0 因此升级为 `LOCAL_MYSQL_UAT_GO`；在该切片结束时精确预览、确认、token、幂等、专用权限和原子审计均未实现，L3 总体继续 `NO-GO`。详细证据见 `finish-inbound-s0-isolated-db-uat-2026-08-06.md`；后续精确预览的实现状态以第 11 节为准。

## 12. 2026-08-10 S2 实施记录

S2 新增独立控制面表：确认记录、幂等执行请求和追加式专用审计。用户确认只提交 S1 的 `previewRef`；服务端绑定当前用户、Agent 会话、权限快照、内容哈希、状态摘要和短有效期，并派生一次性 token 与幂等键，数据库只保存其 SHA-256。重复确认得到同一凭据；跨用户、跨会话、错误 token、撤销、过期或当前业务摘要变化均失败关闭。执行请求不接受原始入库 DTO，因此不能在确认后修改仓库、日期、侧、数量、单位或备注。

唯一 S2 消费 Controller 由 `agent.finish-inbound.s2-noop-enabled=true` 显式控制，默认不注册；适配器固定为 0 次业务写入且不依赖库存、入库、任务或生产服务。请求起点和审计先提交，成功审计、结果、确认消费与预览消费在同一事务；适配器失败不消费 token。相同幂等键读取已提交结果，不再次进入适配器。

定向测试与根项目全量测试通过。本地 `38082 → 38091` 正式 Agent 链路完成 S1 预览、重复确认、首次零写入消费和同键重放：同一 `executionRef`、`attempt_count=1`、3 条专用审计、业务写入 0、execute 工具调用 0，临时数据已清理。首次真实 MySQL 验收发现并修复执行请求非空初始状态的 INSERT 顺序问题。S2 因此为 `LOCAL_MYSQL_ZERO_WRITE_UAT_GO`；专用执行权限、受控 UI、真实领域事务适配器和真实写入原子审计仍在 S3，L3 总体继续 `NO-GO`。详细证据见 `finish-inbound-s2-control-plane-uat-2026-08-10.md`。

## 13. 2026-08-10 S3 实施记录

S3 新增独立权限 `agent:finish-inbound:execute`，迁移脚本只创建权限，不自动分配给任何角色。默认关闭的受控 Web 入口只允许同时具备 `task:view`、`task:confirm` 和该独立权限的用户使用，并继续校验 Agent 管理角色与会话归属。用户从服务端保存的精确预览进入确认弹窗；界面只提交预览引用或托盘码集合，不接收、不展示 token、幂等键、内部主键或原始领域 DTO。

真实执行适配器只解析服务端持久化的规范化输入，并调用既有 `PalletCodeService.confirmFinishedTaskInBatch` 领域事务，因此没有复制库存、仓库、任务、生产或化验规则。执行成功时，业务写入、成功结果、确认/预览消费和成功审计位于同一 Spring 事务；相同已消费确认可回读同一已提交结果，不会再次调用领域服务。业务异常形成最终失败并使本次确认失效；技术异常保持可安全重试，但数据库级审计故障注入仍属于 S4 门禁。

本地隔离 UAT 在 `127.0.0.1` 完成一条成品入库真实写入，验证任务、托盘、库存、流转事件、库存事件和仓库容量一致；得到 `attempt_count=1`、3 条控制审计、0 次 MCP execute 工具调用。随后用同一确认重放已提交结果，未发生第二次业务写入；临时业务数据、控制面记录、测试账号和临时角色权限关联均已清理。S3 因此为 `CONTROLLED_DOMAIN_EXECUTION_LOCAL_UAT_GO`，但功能仍默认关闭，权限仍未分配真实角色，`execute_finish_inbound_task` 仍未登记。L3 总体和生产发布继续 `NO-GO`。详细证据见 `finish-inbound-s3-domain-execution-uat-2026-08-10.md`。

## 14. 2026-08-10 用户场景引导补充

新增 `FINISH_INBOUND_GUIDED_PREPARATION` GoalContract，用于承接“3号库位入库2板黄冰糖”这类不完整但业务目标明确的表达。模型负责识别成品入库目标并交给物流专家；专家依次完成产品和库位受控解析。2026-08-10 起，Runtime 还必须确认二维码来源：已有待入库任务进入 `FINISH_INBOUND_PENDING_TASK_PREPARATION`，再把已确认产品绑定为精确 `productId` 查询 `FINISH_IN + PENDING + 成品`；空闲固定二维码进入 `FINISH_INBOUND_FIXED_QR_PREPARATION`，只查询具体产品精确匹配且当前空闲的固定码。模型不能看到或生成内部 ID，两条路径不得静默互相回退。

任务卡片会显示目标产品、目标库位和要求数量，只允许用户选择恰好 N 个二维码；数量不足时不允许继续。已有任务路径可直接进入任务资格预览。固定二维码路径必须先通过独立确认弹窗复用现有固定码启用入口创建待入库任务，此步只创建任务并生成标签 PDF，不写库存；任务真实存在后才进入同一套任务资格预览和成品入库弹窗。弹窗预填目标库位和左侧默认值，其余字段继续使用现有业务规则供用户复核。该补充只完善从自然语言到既有受控界面的交接，不新增 MCP execute 工具，也不改变 S4 放行结论。自动化合同已通过，真实浏览器中的产品消歧和弹窗预填仍需单独验收，证据见 `finish-inbound-guided-scene-uat-2026-08-10.md`。
