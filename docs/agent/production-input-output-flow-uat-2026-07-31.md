## 1. 验收边界

本次验收的是两条独立的生产事实序列和订单归属并列视图：

- 成品订单的输入只统计已经保存的实际领料，按北京时间 `picked_at` 归入每日序列；
- 半成品订单只展示最终确认的煮糖批次使用事实；当前缺少真实投料发生时间，不能混入每日实际领料；
- 产出只统计状态为 `BOUND`、`PART_INBOUND` 或 `INSTOCK` 的稳定登记产出，按 `production_date` 归入每日序列；
- 产品筛选以稳定登记产出的产品为范围，不能根据计划 JSON 猜测没有稳定产出的订单属于哪个产品；
- 每日领料与每日登记产出的时间基准和业务语义不同，只能并列展示，禁止直接相除；
- 成品订单领用在用户确认时同步扣减库存，可作为已确认生产投入；登记产出仍不等于最终合格产出；
- 单次报表最多 366 天，不能静默截短用户范围；
- 核心数字由 Java/SQL 确定性聚合，模型只负责理解、选择登记报表和分析受控结果。

## 3. 验收中发现并修复的缺陷

首次 180 天查询中，登记报表工具已在约 5 秒内返回成功，但工具结果约 6 万字符，完整每日零值序列和订单明细被继续提交给专家模型，导致工具调用后的结构化决策超过 30 秒超时。

修复方式：

- 受控报表的完整事实继续保留在 `ReportRun`、业务卡片和 XLSX 导出中；
- 只对提交给模型进行结果分析的观察数据做确定性压缩；
- 核心指标、数据质量、限制和元数据完整保留；
- 大型序列同时记录总行数，并最多保留 6 条代表性记录；
- 每日序列优先抽取有实际活动的日期，避免“只截前 50 天”遗漏中后段真实活动；
- 压缩逻辑适用于全部登记报表，而不是为本报表新增架构分支；
- Runtime 测试同时断言模型观察被压缩、完整卡片事实未被裁剪。

修复后，同一 180 天真实查询完成，分段耗时约为：

- 主模型路由：3.5 秒；
- 专家首次决策：4.5 秒；
- 工具返回后的专家分析：16.0 秒。

该单样本只能证明超时缺陷已关闭，不能据此声明达到 P50/P95 性能目标。
