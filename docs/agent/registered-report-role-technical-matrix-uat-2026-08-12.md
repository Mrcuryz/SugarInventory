# 七类登记报表角色技术矩阵与浏览器验收

日期：2026-08-12（Asia/Shanghai）

结论：`TECHNICAL_PERMISSION_MATRIX_PASS / FORMAL_ROLE_DESIGN_AND_HUMAN_UAT_PENDING`

## 1. 验收边界

本轮使用 shadow 库中的真实在职账号和真实 Chromium，核对七类登记报表的服务端权限、库存趋势门禁和 AI 助手入口。它是技术权限矩阵，不是仓管、质检、生产主管本人参与的业务口径访谈，不能替代 P1 正式用户验收。

当前系统只有 `ADMIN`、`QC`、`STAFF` 三类技术角色；“仓管”“车间主任”是部门或岗位字段，不是可独立授权的角色代码。

| 业务视角 | 账号组织属性 | 实际角色 | 实际权限数 | AI 助手入口 |
| --- | --- | --- | ---: | --- |
| 仓管 | 仓库 | `ADMIN` | 99 | 可见 |
| 质检 | 化验室 | `QC` | 41 | 不可见 |
| 生产主管 | 车间主任 | `ADMIN` | 99 | 可见 |

账号名称、token、密码和数据库凭据不写入本文。验收密码只以进程级临时配置注入，未修改用户 env 文件。

## 3. Agent 入口核对

- 仓管和生产主管账号因为实际角色都是 `ADMIN`，可创建 Agent 会话；
- QC 页面不展示 AI 助手，直接请求创建 Agent 会话也返回 403“仅管理员可使用 AI 助手”；
- 这说明报表 HTTP 权限与 AI 助手入口权限是两层独立门禁：QC 可直接运行其有权报表，但当前不能通过 AI 助手使用；
- 仓管和生产主管的 99 项权限来自过宽的 `ADMIN`，不能据此证明最小权限设计正确。

## 4. 监控口径现场修正

角色矩阵暴露出报表级 `@PreAuthorize` 拒绝发生在 Controller 进入之后、Service 调用之前，旧实现会把权限拒绝和库存趋势业务门禁都记为 `FAILED`，污染系统故障率。本轮把状态拆为：

- `SUCCEEDED`：报表运行和快照持久化成功；
- `REJECTED`：权限拒绝或确定性业务校验/发布门禁拒绝；
- `FAILED`：非预期技术异常。

新构建再次用真实 Chromium 触发一次 QC 生产日报权限拒绝和一次库存趋势 0/7 门禁拒绝。`GET /api/analytics/operations/status` 显示运行 2、拒绝 2、失败 0、最近技术失败为空；页面控制台 0 error。最近执行、最近拒绝和最近失败统一限制在 24 小时窗口。

## 5. 数据与环境清理

第一轮产生 15 个临时 `ReportRun`、21 条执行审计和 2 个空 Agent 会话。两个会话先撤销并确认所有依赖表为 0，再与报表/审计按精确主键删除。监控复验新增的 2 条 `REJECTED` 也按精确引用删除。最终确认：

- 临时报表、执行审计和会话均为 0；
- 三位真实用户仍全部存在；
- 没有修改库存、生产、化验、任务或权限事实；
- Java/Vue 服务、Chromium 页面和临时日志均已关闭或清理。
