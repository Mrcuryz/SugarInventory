# 个人微信群视觉采集与入库候选接入设计

日期：2026-08-14  
状态：**方向已确认，开发暂缓**  
当前用途：保存产品决策、技术验证结论和后续恢复开发的实施基线  
适用范围：个人微信群报数采集 → 成品入库候选单 → Web 人工确认

## 1. 决策摘要

商业试点的硬约束是：甲方继续使用现有个人微信工作群，现场人员不迁移企业微信、不复制报数文本、不要求 `@机器人`，系统自动识别群内新消息。

在这一约束下，当前决定是：

1. 首版采用 **Windows 微信客户端视觉采集 + 本地 OCR**，而不是企业微信会话存档、个人微信 Hook 或非官方协议；
2. OCR 采集应工程化为可监控、可追溯、可恢复的 `WeChatVisualAdapter`，不是临时截图脚本；
3. 微信消息只触发解析和候选单生成，不继承发送人的系统权限，也不直接执行库存写入；
4. 最终成品入库继续由具备权限的仓管在 Web 受控界面确认，并复用现有精确预览、一次性确认、幂等、重检、事务和审计链路；
5. 微信采集目前暂停开发。下周演示前优先完成现有 Agent 的整体测试与封板；
6. 渠道层保持可替换，将来可切换企业微信、官方消息接口或经过重新评估的其他适配器，不重做 Agent 和入库业务链路。

“完全自动化”在本方案中指工作时间内自动打开目标群、采集、识别、去重、分类并生成待确认候选单，不表示模型可以自动修改库存。

## 2. 为什么选择视觉采集

### 2.1 产品约束

- 甲方目前使用个人微信工作群；
- 迁移企业微信会带来开会、流程调整、账号治理和培训成本；
- 演示价值依赖“沿用现有群和报数习惯”；
- 人工复制消息的“智能报数”入口已经存在，但不符合自动触发目标；
- 首个写入试点只做成品入库，其他写操作继续暂停。

### 2.2 路线比较与结论

| 路线 | 对现有个人微信群的改造 | 主要优点 | 主要问题 | 当前结论 |
| --- | --- | --- | --- | --- |
| 企业微信会话存档 | 高 | 结构化消息、官方游标和消息 ID | 组织、群、同意和培训成本较高 | 保留为长期替代通道，不作为当前前置条件 |
| 腾讯个人微信 ClawBot/openclaw-weixin | 中 | 官方长轮询、扫码登录 | 当前只支持直接会话，机器人身份无法正常加入普通群聊 | 不满足群消息需求 |
| PC Hook / Pad / 非官方协议 | 低 | 可获得结构化群消息事件 | 封号、版本失效、合规和供应持续性风险 | 暂不进入商业试点 |
| Windows UI 自动化读取控件树 | 低 | 不读取协议 | 当前微信聊天区未暴露可用消息控件树 | 不能单独承担采集 |
| 截图 + 本地 OCR | 低 | 不改群、不逆向协议、初期成本低，原图可审计 | 需要固定运行环境，缺少官方消息 ID，恢复和完整性需要额外设计 | **当前试点首选** |

这里的“稳定”是相对于 Hook/协议方案的账号风险和版本断裂更可控，不表示 OCR 天然不会漏采。

## 3. 已完成的技术验证

本地验证环境：

- Windows 11；
- 微信桌面端 `4.1.11.55`；
- 测试群：`报数自动入库测试`；
- 采集方式：定位微信主窗口和聊天渲染区域，截图后执行本地中文 OCR；
- 微信顶层窗口类：`Qt51514QWindowIcon`；
- 聊天渲染子窗口类：`MMUIRenderSubWindow`。

控件树检查显示聊天消息区主要是 Qt 渲染画布，没有可稳定读取的发送人和消息文本控件，因此此前的 UI Automation SDK 无法直接返回结构化消息。

视觉 PoC 已从测试群截图中识别并形成结构化结果，包括：

- 当前账号消息：`WX-UAT-GROUP-B-002：今天入库黄冰糖两板`；
- 群成员“肖柳航”消息：`WX-UAT-GROUP-A-002：3号库位入库2板黄冰糖`；
- 输出字段包含群名、发送人、正文、采集时间和 SHA-256 指纹。

该结果证明“固定群、固定窗口条件下从微信画面提取报数消息”可行，但还没有证明：

- 24～72 小时连续运行不漏消息；
- 窗口最小化、遮挡、缩放或 DPI 变化后的稳定性；
- 关机期间消息的完整补采；
- 同文重复报数和更正消息的正确区分；
- 多群、多媒体和长消息的生产可用性。

此前生成的 `.tmp/` 验证程序和截图均属于本地临时证据，不是正式产品实现，也不应被当作发布制品。

## 4. 目标架构

```text
个人微信工作群
  → Windows 专用采集端
  → WeChatVisualAdapter
      → 窗口/群白名单校验
      → 聊天区域截图
      → OCR 文本块与坐标
      → 消息气泡分组、发送人关联和时间推定
      → 图像/文本指纹与重复检测
  → 不可变原始消息事件 + 截图证据
  → 异步消息处理队列
  → 模型理解：无关 / 支持的成品入库 / 其他业务 / 不确定
  → 入库专家决策
  → 产品、库位、数量、日期和二维码的确定性解析工具
  → 入库候选单
  → Web 人工复核和补充
  → 待入库任务 / 精确执行预览
  → 仓管再次确认
  → 受控成品入库、审计和结果回写
```

### 4.1 组件边界

`WeChatVisualAdapter` 只负责把屏幕事实转成带证据的候选消息。它不得：

- 调用库存写接口；
- 猜测产品、库位或二维码 ID；
- 使用群成员身份授予业务权限；
- 把 OCR 低置信内容自动修正为确定事实；
- 在不能证明采集连续时报告“没有消息”。

Agent 继续遵循统一范式：

```text
模型理解 → 专家决策 → 受控工具调用 → 结果分析 → 完成裁决
```

视觉采集是新的输入通道，不是第二套 Agent，也不能绕过 GoalContract、专家白名单和现有 L3 安全链路。

### 4.2 部署形态

试点建议使用：

- 一个独立业务微信号，不使用个人主账号；
- 一台工作时间常开的 Windows 电脑或小主机；
- 固定并经过验收的微信版本，关闭自动更新；
- 固定系统 DPI、微信窗口尺寸和显示器配置；
- 只监听一个明确白名单群；
- 采集服务、微信进程和处理队列均具备健康检查与开机启动；
- 采集端只读，不自动发群消息、不管理联系人、不抢红包、不执行群控。

## 5. 采集与消息重建

### 5.1 采集循环

每轮采集至少执行：

1. 确认微信已登录；
2. 确认当前打开的是白名单群，群名与窗口特征一致；
3. 确认聊天渲染区域尺寸、DPI 和主题符合已验收配置；
4. 截取聊天区域并计算图像差异；
5. 有新增画面时运行本地 OCR，保留文本、坐标和置信度；
6. 按头像/气泡侧别、纵向位置和文本块间距重建消息；
7. 关联可见发送人和时间标签；
8. 生成候选消息事件，保存裁剪图和整屏证据；
9. 去重成功后异步提交处理；
10. 更新采集锚点和健康状态。

模型不能直接读取整段聊天截图后自行决定写入。OCR、消息分组和原图证据应先形成可审计输入，再进入业务模型。

### 5.2 消息事件建议结构

```json
{
  "source": "WECHAT_VISUAL",
  "collectorId": "collector-01",
  "groupName": "报数自动入库测试",
  "senderDisplayName": "肖柳航",
  "sentAt": null,
  "capturedAt": "2026-08-14T10:00:00+08:00",
  "content": "3号库位入库2板黄冰糖",
  "ocrConfidence": 0.97,
  "messageFingerprint": "sha256:...",
  "screenEvidenceRef": "controlled-ref",
  "captureContinuity": "CONTINUOUS",
  "reviewRequired": false
}
```

`sentAt` 无法从画面可靠确定时必须为空，不得用采集时间冒充发送时间。截图引用只能通过受控权限查看，不能把本机路径暴露给普通用户或模型。

### 5.3 三层去重

OCR 没有微信官方 `msgid`，因此需要三层去重，同时避免误删合法的重复报数：

1. **画面去重**：整屏/聊天区域感知哈希，避免静止画面反复 OCR；
2. **消息候选去重**：群、发送人、规范化正文、相对位置、相邻消息和截图指纹组合；
3. **业务重复检测**：同产品、库位、数量、日期、二维码和时间窗口的候选单提示人工确认。

第三层只能标记“疑似重复”，不能简单丢弃。同一个人连续发送相同文本，可能代表两笔真实业务。

## 6. 连续性、关机与恢复

### 6.1 连续性状态

采集端必须维护以下状态：

- `HEALTHY`：微信、目标群、画面和 OCR 均正常；
- `DEGRADED`：可采集但置信度或窗口条件异常；
- `GAP_DETECTED`：最小化、遮挡、退出、切群、电脑休眠或进程停止导致可能漏采；
- `RECOVERING`：正在向上滚动并寻找上次锚点；
- `REVIEW_REQUIRED`：无法证明缺口已经补齐；
- `STOPPED`：采集被人工关闭。

系统只有在 `HEALTHY` 且连续性成立时，才能显示“当前没有新的入库报数”。存在缺口时应明确显示“微信采集可能中断，请人工核对”，不能把未知解释为无消息。

### 6.2 恢复策略

微信或采集服务重启后：

1. 打开白名单群；
2. 从当前画面向上加载历史；
3. 查找最近一个已经保存的视觉锚点；
4. 从锚点之后逐屏 OCR 和去重；
5. 找到锚点且重叠区连续时恢复为 `HEALTHY`；
6. 找不到锚点、历史未同步完整或画面变化过大时进入 `REVIEW_REQUIRED`。

本方案不能在验证前承诺电脑关机期间百分之百补采。试点首先以“工作时间采集设备持续开机”为运行条件；关机补采能力通过真实测试后再调整承诺。

## 7. 业务分类与候选单

每条消息至少分类为：

- `SUPPORTED_FINISH_INBOUND`：当前试点支持的成品入库；
- `BUSINESS_BUT_UNSUPPORTED`：出库、调拨、半成品、化验写入等其他业务；
- `IRRELEVANT`：普通聊天和与业务无关内容；
- `UNCERTAIN`：OCR 或业务意图不确定；
- `POSSIBLE_DUPLICATE`：疑似重复但不能自动丢弃；
- `CORRECTION_CANDIDATE`：可能在更正上一条报数。

模型只提取原文中存在的产品、库位、数量、单位、业务日期、侧别和二维码，并保留字段证据。产品、库位和二维码最终由后端 resolver 确定。

候选单状态建议为：

```text
RECEIVED
  → IGNORED / UNSUPPORTED
  → NEEDS_REVIEW
  → NEEDS_INFORMATION
  → READY_FOR_TASK_PREPARATION
  → TASK_CREATED
  → PREVIEWED
  → CONFIRMED / REJECTED / FAILED
```

原始消息、更正、人工修改和最终执行结果均保留关联，不覆盖历史事实。

## 8. 页面与用户体验

视觉采集结果进入独立的“入库报数收件箱”，不能在解析前直接混入真实待处理任务。

候选卡片应展示：

- 来源群、报数人、可确认的发送时间和采集时间；
- 原始消息正文；
- 必要时展示受控截图证据；
- 模型提取值、确定性匹配值和 OCR 置信提示；
- 缺失信息、疑似重复或采集连续性风险；
- 人工修改前后差异；
- 关联待入库任务和最终结果。

建议筛选状态：待复核、待补充、可生成任务、已转任务、已完成、已忽略、采集异常。

二维码来源必须继续显式区分：

1. 处理已经绑定且待入库的二维码任务；
2. 使用空闲固定二维码创建新的待入库任务；
3. 信息不足，等待仓管选择。

不能因为报数中写了“两板”，就默认选择任意两个二维码。

## 9. 安全、隐私与审计

- 只采集明确白名单群，不扫描其他聊天；
- 原始截图可能包含非业务聊天，应配置最短必要保留期和查看权限；
- OCR 和识别首选本地运行，截图不发送到未经批准的外部服务；
- 日志不记录完整聊天正文、截图、本机路径、模型密钥或登录凭据；
- 群消息属于不可信输入，提示词注入不能扩大工具和权限；
- 群成员身份只是来源事实，不能映射为执行权限；
- 所有候选单的人工修改、拒绝、预览、确认和执行必须可审计；
- 视觉采集故障不得触发库存写入或自动补猜。

## 10. 首版范围

首版承诺范围：

- 一个白名单个人微信群；
- 纯文本成品入库报数；
- 固定 Windows 设备、微信版本、窗口大小和 DPI；
- 工作时间设备持续运行；
- 自动生成候选单；
- Web 仓管人工复核；
- 最终写入继续走现有受控成品入库流程。

首版明确不承诺：

- 图片、语音、视频和文件中的报数；
- 任意数量群并发监听；
- 任意窗口布局、主题、分辨率和微信版本；
- 长时间关机后的百分之百补采；
- 自动回复群消息；
- 模型自动执行入库；
- 出库、调拨、半成品或化验写入。

## 11. 恢复开发后的实施顺序

### P0：采集器工程化

- 从 `.tmp` PoC 中提炼独立 `WeChatVisualAdapter`；
- 配置群白名单、窗口特征、DPI 和裁剪区域；
- 建立截图证据、OCR 结果和采集健康状态；
- 不接业务写入。

### P1：消息重建与可靠性

- 消息气泡分组、发送人关联、三层去重；
- 视觉锚点、滚动补采和缺口暴露；
- 一群 24～72 小时连续运行；
- 重启、最小化、遮挡、切群和 DPI 异常测试。

### P2：入库收件箱

- 持久化不可变消息事件；
- 模型分类、字段证据和确定性 resolver；
- 人工复核、补充、拒绝、疑似重复和更正关联；
- 仍不写库存。

### P3：接入受控入库

- 复用现有成品入库引导；
- 区分已有待入库任务和空闲固定二维码建任务；
- 复用精确预览、一次性确认、幂等、重检、事务和审计；
- 只由已登录且有权限的仓管最终确认。

### P4：小范围试运行

- 开关默认关闭；
- 限定一台采集机、一个群和少量仓管；
- 记录漏采率、重复率、OCR 人工修正率、业务字段修正率、候选处理耗时和执行失败率；
- 再根据真实节省时间和运维成本决定报价及是否扩展。

## 12. 验收清单

恢复开发后至少验证：

| 场景 | 必须结果 |
| --- | --- |
| 正常报数 | 自动形成一条带原图证据的候选单 |
| 普通闲聊 | 标记无关，不创建任务 |
| 产品名称有歧义 | 提供产品候选，不自行选择 |
| 缺二维码 | 要求选择已有任务或空闲固定码，不随机绑定 |
| 连续多条报数 | 顺序正确、没有合并丢失 |
| 同文连续发送两次 | 不静默丢弃，提示疑似重复 |
| 后续发送更正 | 关联原消息，保留两个版本 |
| OCR 低置信 | 进入人工复核，不自动执行 |
| 微信最小化/遮挡/切群 | 立即进入异常状态并告警 |
| 微信/采集服务重启 | 尝试从锚点补采，不重复建单 |
| 电脑重启 | 能恢复服务；无法证明补齐时明确提示缺口 |
| 模型超时 | 原消息仍已保存，可重试且不重复 |
| 数据库暂时不可用 | 不推进采集锚点或明确进入可恢复失败 |
| 重复截图 | 不重复生成消息事件 |
| 提示词注入文本 | 不扩大权限、不绕过专家和确认 |
| 最终入库 | 必须经过 Web 预览与仓管明确确认 |

工程门禁建议：

- 连续运行 24～72 小时；
- 测试集合中已显示消息的采集漏失为 0；
- 重复消息事件为 0，同时保留合法重复报数；
- OCR 错误全部进入可见复核，没有静默改写；
- 采集异常 1 分钟内可见；
- 所有候选均可追溯到原始截图；
- 未确认前库存、任务和二维码业务状态没有副作用。
