## 0. 用户确认的现场背景与实施约束

- 系统尚未全面投入运行，现有生产订单、领料、产出等业务记录不能覆盖全厂生产，不能以其合计代替全厂产量。
- 当前由车间主任自行填写生产日报，这是现阶段的数据采集方式。Agent 的默认生产概况、产量汇总和相关生产分析以生产日报为依据，直接调用现有日报查询能力；不是要求用户先选数据来源。
- **数据来源选择本身不需要修改业务代码**：不修改订单报表 SQL，不替换既有业务接口，不为此新增运营报表后端版本，不修改数据库结构或同步数据。需要调整的仅限必要的 Agent 目标选择/编排、能力说明及文档，并继续遵守现有权限与工具边界。
- “以日报为来源”针对上述生产汇总场景，不表示日报可以回答其中没有的实时库存、化验详情或具体订单执行事实；这些明确的查询仍使用其已有业务来源，不能推算或伪造。
- 保留后续根据实际生产业务数据生成日报的可能性，但本轮不实现自动生成、自动覆盖、对账补齐或双源合并；后续另行设计生成与人工修订规则。Agent 不应被绑定为永远只支持人工录入方式。
- 当前不做预测；待业务数据持续稳定、覆盖充分后再评估，不承诺现在能够预测。
- 下文批次 C 已据此修订：撤销原拟 `today_operations_overview_v2` 后端改造。趋势、比较、快照和导出是独立的新增分析功能，不是解决当前来源问题的前置条件。

## 1. 本轮目标和范围

优先让用户得到可信、连贯的业务回答：产了多少、每天怎么变化、与上一期间相比怎样，以及能导出与回答一致的报表。填报条数、提交状态和覆盖情况作为必要说明，不再代替产量。

推进顺序：

1. 稳定现有生产概况与连续追问。
2. 将生产日报来源接入现有登记报表体系，补按日趋势及同快照导出。
3. 在 Agent 层对齐生产来源与跨域追问，补受约束的期间比较。
4. 整体回归、形成匹配的发布基线。
5. 再集中完善已有成品入库试点，不扩展其他写入。

本轮不做：通用报表搭建器、任意 SQL、预测、未经业务字段支持的效率/损耗指标、设备管理扩展、个人微信采集、出库/调拨等新增 Agent 写入。Android 已有业务功能不因此删除或改变。

## 3. 架构：复用现有链路，不新增分析框架

```text
用户问题及已确认上下文
  → 主模型识别业务目标和范围
  → 既有专家决定查询/澄清及允许调用的工具
  → Runtime / GoalContract 校验目标、参数、权限上下文和事实
  → Java 读取业务字段、确定性计算并返回结构化事实
  → 模型依据事实分析，Web 展示回答、卡片或报表
```

- 普通生产概况、查原始日报明细：继续由 `production_expert` 使用 `query_production_daily_reports`。
- 日报趋势、期间比较、生成可导出分析报告：由 `analytics_expert` 使用现有 `run_registered_report`。
- 追加一个“生产日报分析”GoalContract（暂定 `PRODUCTION_DAILY_REPORT_ANALYSIS`），不要将旧 `DAILY_PRODUCTION_ANALYSIS` 的订单语义偷偷替换；同一报表的趋势/比较/导出不拆成多个重复目标。
- 不新增专家或通用工具，不让主模型直接查询数据库，不以关键词短路取代模型理解和专家决策。
- 两条日报路径共用小范围的 Java 日报事实聚合组件，保证相同范围得到相同基础数值；只抽取当前业务需要的聚合能力，不建设通用指标引擎。
- Python 负责适配与事实约束，Web 负责展示；二者都不重算权威产量。模型不能通过当前页明细求和生成总量。
- 前端“导出这份报表”使用已展示的 ReportRun；若当前只有普通概况，应明确“生成报表并导出”，不能假装已有历史快照。

## 4. 口径与用户交互

### 4.1 数据来源与上下文

| 用户场景 | 拟定行为 |
|---|---|
| 无其他来源上下文：“今天产量如何？” | 根据生产日报回答，不要求用户先理解两个系统来源 |
| “最近七天产量走势” | 日报来源的登记报表，日期、来源、单位清楚可见 |
| “生产订单 PO… 的产出”“订单登记产出趋势” | 保持订单事实/订单报表 |
| 日报后追问“和前七天比呢”“导出这个” | 保留日报来源、产品和车间范围，进入对应分析目标 |
| 订单报表后追问“昨天呢” | 保留订单来源；明确说“改看生产日报”时才切换 |
| 日报无数据，但订单有数据 | 说明日报未记录；可提供查看订单登记产出的选项，不静默替代 |
| “这两个产品”“只看多晶”“改成昨天” | 继承仍有效条件；替换日期/产品/车间时清除冲突条件和旧分页，不重走已经完成的候选选择 |

“最近 N 天”沿用 Asia/Shanghai、含当天的 N 个自然日，并展示确切日期；单日写“2026-09-06”，不写“2026-09-06 至 2026-09-06内”。“昨天”与“上一期间”分开处理，未来日期和超范围按现有约束校验。

### 4.2 首批指标

| 指标组 | 字段依据 | 聚合与展示 |
|---|---|---|
| 全厂总产量 | `FACTORY_TOTAL_OUTPUT` 的 `daily_actual`、已保存 `converted_tons` | 按日点和期间合计分别展示件、折吨；不由产品行反推 |
| 多晶冰糖产量 | `POLY_OUTPUT` 同上 | 独立系列；不补造红糖/单晶同名总量指标，不再加到全厂总量 |
| 产品分类数量 | 产品行的当日值与已保存折吨，按车间、类别、状态、单位及快照分组 | 回答指定范围的已记录数量；不同加工阶段不相加；不称为完整全厂产量 |
| 全厂耗电/耗汽/耗水 | `FACTORY_TOTAL_POWER/STEAM/WATER.daily_actual` | 各自按原单位统计，不读取通用折吨列、不计算吨均能耗 |
| 产率、月累计、年累计 | 已保存字段 | 仍可查看原值明细，本轮不新建期间平均率或累计值再求和 |

所有数据只来自现有四张日报表。按业务日期，不按创建时间；保留名称、单位与分类快照。不同单位或不同快照口径不强行合并。产品筛选不附带全厂无关汇总；车间筛选不返回其他车间总量。

### 4.3 缺数、草稿与比较

- 维持现有“包括已保存草稿”的默认范围，突出产量后用短句提示未提交；不能因草稿就宣称没有数据或数据必然错误。本期暂不追加“仅已提交”筛选，避免同时引入另一套默认统计范围。
- `null`、没有记录、已记录的 0 分开；趋势缺日断点，不补零、不连接成连续真实产量。部分行缺值时返回已记录合计和覆盖说明。
- 数量与折吨分别追踪有效行数和覆盖天数，不能因为数量完整就认定折吨完整。
- 第一期比较只支持紧邻前期等长区间，以及用户明确指定的非重叠等长区间；两期各不超过 31 天。暂不承诺跨月不限天数、同比和不同长度期间比较；不支持的请求明确解释边界。
- 同源、同指标、同单位、同车间/产品范围才允许计算差额和变化率。后台计算：差额＝本期－前期；前期大于 0 时计算变化率。前期为 0 时只给两期值和差额，不输出无限增长；为负或无值时不输出增长率。
- 两期存在缺日、空值或被截断系列时，不给“整体增产/减产百分比”；并列展示已记录值及不足条件。即便所有已保存行完整，也不声称现场生产绝无漏报。
- 产品分类仍标明是该分类登记数量的变化，不代表实际全厂产量变化。不将数值升降直接解释成效率、质量、原因或预测。

## 5. 登记报表与权限设计

### 5.1 新日报分析定义

暂定 `production_daily_report_analysis_v1`，显示名称“生产日报分析”，使用现有 `run_registered_report` 与 `/api/analytics/agent-read/reports/run`，保留旧订单报表定义。

输入：复用日期、产品查询与比较参数；为新定义增加可选车间筛选，按现有车间目录白名单验证。`productQuery` 只筛选产品名称，不能直接照搬原明细接口同时匹配指标名的 `itemQuery` 语义。指定能耗等指标时使用受控 `metricKey` 白名单；其他报表拒绝不适用参数。

输出需要包含：来源、业务日期范围、产品/车间筛选、口径版本、生成时间、指标组、按日数值、覆盖信息、未提交信息、截断情况及可比较性。新增指标字段采用该报表的结构化类型，不滥用订单报表的重量/件数字段承载含义不同的日报值。

沿用现有快照存储，不预设新增业务表或修改库存结构。期间合计必须读取完整筛选范围。图表按指标和单位分开，缺值与部分值可辨识；折吨和件数不共用同一数值轴。系列超限时明确截断并引导缩小范围，不把前 10 组当全部结果；仍使用有界 DTO，不提高全局工具/卡片限制来容纳无限明细。

普通概况与正式报表允许生成时刻不同，但同一输入、同一底层数据版本必须得到相同基础指标。导出后重新查询可能有更新，旧快照不得自动覆盖成新值。

### 5.2 导出权限不能遗漏

当前日报 Controller 已将查看与导出分别设为 `production:daily-report:view`、`production:daily-report:export`；而现有分析 Controller 的入口白名单尚无日报查看权限。这是接入工作，不是通过赋予订单权限来绕开。

拟定：

- 运行、查看历史日报分析：必须拥有日报查看权限，以及现有 Agent 访问条件。
- 导出日报分析：在查看权限基础上，额外校验日报导出权限。仅有查看权限仍可查询，但不显示可执行导出入口，后端直接请求也须拒绝。
- Controller、执行服务、归档可见性、当前权限复核、MCP/专家能力描述及前端动作一并对齐；不能只改一层。
- 快照读取继续限定所有者、有效期、内容校验和当前权限。保留现有 30 天生命周期；过期时提供重新生成，不悄悄替换旧文件。
- 导出额外权限不应误写成整份报告的查看条件；应按报告定义/版本区分查看与导出要求，不放宽其他报表权限。
- XLSX 使用同一 ReportRun 的事实，包含查询范围、来源、单位、按日明细、比较值和缺数/草稿提示；导出的汇总不能从卡片可见部分重新计算。本文不是新增 Web 原始日报导出模板的要求。

### 5.3 今日运营中的生产来源：仅处理 Agent 选择与编排

不新增 `today_operations_overview_v2`，不改 `today_operations_overview_v1` 的 SQL、指标或历史快照。

- 用户询问全厂生产概况时，Agent 直接使用 `query_production_daily_reports`；无日报总量就说明未记录，不能以订单记录数或填报率代替产量。
- “今天整体运营情况”包含多个领域。生产事实应来自日报；库存、化验、待办保留各自业务事实。继续使用既有主模型、专家、GoalContract 和组合框架，不擅自把其他专家工具加入单一目标白名单。
- 现有运营报表里的订单产出仅代表订单登记事实，不能作为全厂产量，也不能与日报相加。Agent 如调用该报表，不得在回答或卡片中把其订单数据包装为日报数据。
- 实施前检查现有组合契约能否承载日报事实；若暂不能，明确分项展示并记录组合缺口，不谎称仅改文档就已完成全链路对齐，也不绕过完成校验来强行回答。
- 用户明确查询具体订单或既有订单报表时仍保留原能力；原快照继续按原版展示。日报权限不足不自动回退订单数据冒充全厂产量。
- 现有报告导出仍导出原快照，不把 Agent 临时组合的回答假称为已归档报表。日报来源的正式快照/导出按批次 B 单独开发，遵守已有日报导出权限。

## 7. 用户场景验收清单

以下是计划用例，不是已经执行的结果。A～C 每个核心自然语言场景至少运行 3 轮，覆盖新会话和追问；数值、权限、重试另有确定性测试。测试在隔离环境使用可核对的标记数据，禁用无关写入；验收后按标记清理，不修改既有账号与库存。

| 编号 | 输入/操作 | 必须验证 |
|---|---|---|
| P01 | 今天产量如何？ | 首句业务产量、日报来源，统计条数不喧宾夺主 |
| P02 | 查某一天产量；最近7天产量 | 单日正常表述，时区/边界正确，跨度不丢记录 |
| P03 | 黄冰糖生产了多少？→只看袋装 | 按实际名称与候选确认；选择后续查，不循环 |
| P04 | 最近7天→只看多晶→改成昨天→看全部车间 | 来源保持，过时日期/车间/分页清除 |
| P05 | 展开明细、下一页、再看概况 | 汇总始终是完整范围，不由当页求和 |
| P06 | 数据分别为0、null、缺行、仅有草稿 | 能区分四种状态；数量/折吨分别提示覆盖 |
| P07 | 只有产品分类，没有全厂总量 | 不把半成品与二次加工相加充当全厂产量 |
| P08 | 这几天耗电多少？结晶率呢？ | 能耗独立单位；率只给可证实原值，不自行平均 |
| P09 | 最近七天走势；其中一天没记录 | 图表断点与缺值说明；不补零，不强行连续 |
| P10 | 超过31天；超过展示系列上限 | 明确边界和缩小范围建议，不伪装完整结果 |
| P11 | 和前七天比；指定另一个等长区间 | 源/范围/单位一致，后端差额及基期可核对 |
| P12 | 前期0、前期全空、两期覆盖不同 | 无无限增长、无缺数造成的“整体下降”结论 |
| P13 | 昨天日报→查订单产出→昨天呢 | 显式切换与继承正确；日报空不自动换订单 |
| P14 | 今天产量→今天整体运营情况 | 产量同口径；订单领用产出与日报分开，不相加 |
| P15 | 日报和订单故意设置不同值 | 两种报告各自正确且来源可见，历史v1不改写 |
| P16 | 只有日报查看权限；无日报查看权限 | 可见入口与后端授权一致，无订单权限不应阻断日报查询 |
| P17 | 查看有权限、导出无权限；归档后撤销权限 | 查看与导出分离；直接URL/旧快照不能绕过授权 |
| P18 | 导出这个→刷新底层日报→重新打开旧报表 | 导出/历史仍是原快照；重新生成明确为新结果 |
| P19 | 工具异常、模型超时、断线重试、旧候选再次点击 | 不把失败说成空数据；不永久加载或重复选择；旧响应不覆盖新请求 |
| P20 | 当前库存、质量趋势、知识流程、入库请求交叉追问 | 现有能力不被日报路由抢占；知识引用不充当实时库存事实 |

每项记录：版本/配置、账号权限、前置标记数据、完整输入和选择步骤、工具事实、最终文本、卡片/图表截图、期望与实际、耗时、PASS/FAIL/BLOCKED，以及原始证据路径。导出用例核对文件里的值、单位、来源和限制提示；不只验证下载成功。

发布阻断：错误数值/口径、越权、旧数据冒充新结果、工具错误冒充无数据、循环/无法恢复、任何未授权写入。文字赘余与延迟波动可单列改进项，但不得将错误业务结论列为纯文案问题。真实库存快照门禁不足或 RAG 语料未验收，应独立标为受限，不用模拟数据宣称整套通过。

## 8. 成品入库下一步设计边界

报表稳定后，以“3号库位入库2板黄冰糖”为主线复核现有闭环，而不是新增自由执行工具。

1. 模型识别入库意图；产品/库位/二维码有歧义时用候选卡片补齐，不猜 ID。
2. 已绑定待入库二维码走既有任务处理；空闲固定二维码走既有任务创建准备。两者分别校验状态与权限，不能重复创建任务。
3. 只要求库位，不要求左右、排、层；后端兼容值不作为现场输入。界面称“二维码”“一板糖”，不暴露内部字段。
4. 复用精确预览、用户明确确认、服务端执行与审计。不能因用户说“可以”就跨到未展示范围的操作。
5. 重点覆盖 App/Web 已处理、预览过期、重复点击、确认取消并发、整批回滚、断线后执行状态不确定。只有查询到实际结果才给成功/失败结论，不自动重做未知结果的写入。
6. 完成后任务卡片状态、选择框、库存及库位详情同步；不允许再次选中已完成任务。

本阶段只做必要缺陷修复和验收。若发现必须变更现有写入协议/权限/数据库，先单独设计送审。微信触发、出库、调拨、半成品入库及设备写入不随本计划恢复。

## 10. 已确认的推进决定

用户已同意总体方向，数据来源按第 0 节最新澄清执行：

1. **先完善日报分析，再集中完善成品入库；其他写入仍暂停。**
2. **Agent 的生产汇总以现有日报为来源；不为来源选择修改业务代码，订单查询能力保留但不能代表全厂生产。**
3. **沿用包含已保存草稿的当前行为，明确提示；首批不追加提交状态筛选。**
4. **首批交付按日趋势、前期/等长自定义比较和 XLSX；暂不承诺预测、同比或任意时长分析。**
5. **导出遵循已有独立权限，不自动给任何账号加权限；撤销新增运营后端定义的安排。**

先实施 A 批，再按证据推进 B/C。来源补充说明本身只同步文档；后续实施进度另行记录，计划获准不等于生产上线授权。
