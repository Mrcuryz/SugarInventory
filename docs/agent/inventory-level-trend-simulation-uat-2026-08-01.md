# 库存水平趋势本地历史回放验收记录

日期：2026-08-01
结论：`LOCAL_UAT_ACCEPTED / PRODUCTION_GATE_BLOCKED`

## 1. 为什么允许模拟

本地开发机夜间会关机，无法依赖 Web 进程连续跨零点运行来积累 7 天日终快照。等待 7 个自然日只能验证调度持续运行，不能提高 Agent、报表、卡片、历史重开或导出链路的开发质量。

因此采用双轨制：

- 本地/UAT：显式设置 `INVENTORY_TREND_SIMULATION_ENABLED=true` 后，允许用当前库存和已有登记流水反向回放；
- 生产：仍只认可连续通过每日守恒对账的真实 `DAILY_CLOSE` 快照，查询范围不在可信窗口时拒绝运行；
- 模拟结果不写入日终快照和对账表，不修改库存业务数据，也不推进 `INVENTORY_LEVEL_TREND` 发布门禁。

## 2. 回放口径

回放以当前产品总库存为锚点，按北京时间从当前日期向过去逐日反向撤销：

- 普通入库登记；
- 半成品入库登记；
- 普通出库登记。

运行前必须核对当前库存与累计入库减出库在件数和重量上守恒；不守恒时拒绝模拟。首版只输出产品总库存水平，不重建历史库位分布。系统登记时间不等同于生产日期或现场实际发生时间，迟到补录可能改变回放结果。

## 3. Agent 链路

库存水平趋势继续遵守统一架构：

1. 主模型把用户问题识别为 `INVENTORY_LEVEL_TREND_ANALYSIS`；
2. 委派 `analytics_expert`；
3. 专家选择唯一受控 `run_registered_report`；
4. Java 根据 `inventory_level_trend_v1@1` 确定性计算事实；
5. 专家分析受控事实，Runtime 用 FactEnvelope 和 CompletionEvaluator 校验；
6. 前端展示 `inventory_level_trend_report` 卡片，并支持同快照历史重开和 XLSX 导出。

没有新增库存专用 MCP 工具，也没有把趋势计算交给模型。

## 4. 本轮修复

- 增加 `inventory_level_trend_v1@1`、`INVENTORY_LEVEL_TREND_ANALYSIS`、库存指标、逐日序列和产品分解；
- 增加生产可信快照与本地历史回放两种互斥数据源；
- 回答、卡片、ReportRun 和 XLSX 统一标注“本地历史回放模拟”；
- 增加 `inventory:view` 运行、历史读取和导出权限复核；
- 中文明确日期范围不再被压缩为首日，已覆盖 `2026年7月14日至7月20日`、`7月14日到20日` 和 ISO 日期范围；
- Java 非流式 Agent 本地验收超时调整为 120 秒，报表工具本身保持亚秒级，完整问答耗时主要来自两轮模型决策与分析；
- Java/Python 能力握手只计算 Java Gateway 管理的专家权限映射，进程内 `knowledge_expert` 不再改变仓储工具授权哈希。

## 7. 发布边界

本地验收通过只说明“用户问题 → 模型理解 → 专家决策 → 工具调用 → 结果分析 → 卡片/历史/导出”链路可用，不能证明生产数据已经满足趋势发布条件。

生产开放前仍必须：

1. 在目标部署环境安装独立 Capture/Verify 定时任务；
2. 连续积累至少 7 个自然日可信日终快照；
3. 每日产品全局和仓库维度守恒对账均为 `PASSED`；
4. 对失败退出码、缺快照和零点后污染事件完成告警处置；
5. 使用生产数据重新执行权限、空数据、范围、卡片和导出验收。
