# 成品入库自然语言引导场景验收

日期：2026-08-10  
场景：`3号库位入库2板黄冰糖`  
当前结论：二维码来源已拆分为“已有待入库任务”和“空闲固定二维码新建任务”两条受控路径；自动化合同和本地真实只读 HTTP 首轮链路通过，真实浏览器视觉点击与固定码任务创建副作用验收待执行；没有新增 MCP 写工具，也不改变通用 L3 总体 `NO_GO`

## 1. 为什么需要这项验收

此前使用完整托盘码、完整库位和完整表单参数验证的是接口与事务能力，只能证明“参数已经齐全时系统能处理”。真实仓管用户通常只描述业务目标，因此还必须证明 Agent 能判断缺失信息、完成受控消歧，并把用户带到现有业务表单，而不是要求用户先理解接口参数。

本场景中的“2板”定义为本次要选择两个不同二维码/托盘任务。它不表示每个托盘的 `quantity` 都应填写为 2，也不能由 Agent 任意挑选两个二维码。

## 2. 预期用户旅程

1. 用户输入“3号库位入库2板黄冰糖”。
2. 主 Agent 将其识别为 `FINISH_INBOUND_GUIDED_PREPARATION`，交给物流专家。
3. “黄冰糖”若对应多个具体规格，展示产品候选卡片并等待用户选择；不得按产品大类直接继续。
4. “3号库位”通过库位解析器确认；不存在或不唯一时展示库位候选或明确提示。
5. 产品与库位都确认后，如果用户没有说明二维码来源，必须展示业务模式选择：`处理已有待入库任务` 或 `使用空闲固定二维码新建任务`。不得默认选择，也不得在一条路径数量不足时改用另一条路径补足。
6. 已有任务模式进入 `FINISH_INBOUND_PENDING_TASK_PREPARATION`，只查询该产品当前 `FINISH_IN + PENDING + 成品` 的二维码任务。内部 `productId` 只能来自解析结果，不出现在模型参数、回答或卡片中。
7. 固定二维码模式进入 `FINISH_INBOUND_FIXED_QR_PREPARATION`，只查询与具体产品精确匹配、`fixed_mode_enabled=true` 且当前 `FREE` 的二维码；原始状态枚举不进入回答或卡片。
8. 两种卡片都要求用户恰好选择 2 个二维码。已有任务直接进入既有任务资格预览；固定二维码先打开独立的“创建待入库任务”确认弹窗，要求用户核对生产日期和任务影响。
9. 固定二维码创建动作继续复用系统现有 `/fixed-product/activate/pdf` 业务入口，并新增 `qrcode:activate` 方法权限保护。确认后只创建待入库任务并生成标签 PDF，不写库存；卡片随即标记为已创建且不可再次选择。
10. 创建完成后，前端重新提交一条受控的任务资格预览请求，继续由主模型、物流专家和 `preview_task_transition` 核对这两个新任务；预览通过后用户才可进入既有成品入库弹窗，预填 3号库位和默认侧。用户完成表单后生成精确 L2 预览；真正入库仍必须由受控界面的再次明确确认触发。

## 3. 必须追问与不必逐项追问

| 信息 | 处理方式 | 原因 |
|---|---|---|
| 具体产品规格 | 名称不唯一时必须让用户选择 | 同名不同规格不能混用二维码 |
| 目标库位 | 必须由解析器唯一确认 | Agent 不得猜测库位 ID |
| 本次板数 | 原话没有数量时必须追问；限制 1～20 | 决定二维码选择数量和批量边界 |
| 二维码来源 | 未明确时必须选择“已有任务”或“空闲固定二维码” | 两者分别代表处理已有任务和创建新任务，事务含义不同 |
| 具体二维码 | 必须由用户恰好选择 N 个 | Agent 不得替用户决定实物对象 |
| 固定二维码生产日期 | 固定码创建任务弹窗中必须核对 | 新建入库任务需要生产日期；不能从待入库任务上下文伪造 |
| 入库日期 | 不逐项追问，使用现有默认并在弹窗展示 | 降低对话负担，最终仍可核对 |
| 左/右侧 | 默认左并在弹窗展示，可按现有表单修改 | 复用现有规则，不新增口径 |
| 行/层 | 不向 Agent 开放，由现有自动分配规则决定 | 避免复制库位分配逻辑 |
| 数量/单位 | 使用生产产出记录或现有表单规则并展示 | “2板”不是单托盘数量覆盖值 |
| 备注 | 可选，不主动追问 | 不影响资格准备 |

### 5.1 连续追问的流式回归修复

- 现象：用户选择具体产品后，Runtime 已正确生成二维码来源选项，但页面随后又被通用失败消息覆盖。
- 经真实链路复验确认的直接原因：恢复产品选择时，流式终止上下文携带已消费的旧中断 ID；新的二维码来源追问又生成了新中断 ID。组装 `message_end` 时旧 ID 覆盖新 ID，Java 侧检测到“追问事件与终止事件不一致”后按安全失败处理。
- 修复：连续追问的终止事件始终保留本轮新中断 ID；新增回归测试固定这一规则。
- 同步清理：完整审查轨迹只走内部 `audit` 事件，不再重复放入公开 `message_end`。这是独立的安全收敛，不作为上述故障直接原因。
- 前端体验：一次选择已被安全消费后，即使恢复结果是下一项追问，原产品卡也保持收起并显示已选结果，不会重新启用；只有错误、超时或取消才恢复原选择。
- 真实结果：`产品选择 → 库位解析 → 二维码来源选择` 返回两个用户可读选项，终止原因是 `interrupt_required`，没有错误事件，且未发生任何业务写入。

### 5.2 连续选择的中断状态闭环

- 2026-08-11 用户页面复验通过后，从本地审计记录发现一个隐藏状态问题：产品候选已经成功消费并进入二维码来源选择，但原产品中断仍停留在 `PENDING`；新的二维码来源中断则正常创建。
- 原因是链式追问的公开 `message_end` 必须携带新的中断 ID，以保证事件一致性；Java 流代理此前没有另外保存本次恢复所消费的旧中断 ID，因此无法在生成下一张卡片时关闭旧记录。
- 修复保持现有架构和协议不变：Java `ActiveStream` 只在服务端保存被消费的旧中断 ID。收到合法的新追问及其 `message_end / interrupt_required` 后，将旧中断记为 `RESUMED + COMPLETED`，新中断继续保持 `PENDING`。普通首次追问不会被误标为已恢复。
- 新增 Java 回归测试，锁定“旧中断已恢复、新中断待选择”，并确认不会把新中断错误写成终态。
- 本地真实 HTTP/SSE 复验结果：输入“3号库位入库2板黄冰糖”并选择“黄冰糖（袋） 25.0kg/件 40件/板”后，旧中断为 `RESUMED / COMPLETED`，新的二维码来源中断为 `PENDING`；再次提交旧选择只返回“这个选择已经处理过了。”，不会再次调用业务链路。
