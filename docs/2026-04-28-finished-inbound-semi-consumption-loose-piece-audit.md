# 成品入库、半成品消耗、散件逻辑检查记录

日期：2026-04-28

## 检查结论

当前后端成品入库主链路已经改为“登记备料池半成品用量”，并在成品入库确认后扣减 `semi_prepare_pool_balance`，不再依赖半成品托盘码作为消耗对象。

散件 QR 入库主链路已按“一个二维码 = 一个库存占位 = 一条 inventory 记录”处理：整板写 `quantity=1,pieces=0`，散件写 `quantity=1,pieces=实际件数`，并禁止单个二维码承载达到或超过一板件数。

小程序端发现散件校验仍允许“件数等于每板件数”，本次已改为与后端一致：散件数量必须少于每板件数；整板必须使用 1 板。

## 保留但不作为新版入口的旧逻辑

- `/api/pallet-codes/semi/consume/confirm` 仍保留为旧版确认消耗接口，Controller 已标注旧版接口。
- `semi_prepare_pool`、`SemiPreparePoolMapper`、`SemiPreparePool` 仍保留用于旧版兼容记录。
- 小程序 `confirmSemiConsume` API 包装保留，但已加注释说明不作为新版成品消耗入口。

## 已修正的用户口径

- Web 首页与任务概览中的“绑定半成品”改为“登记半成品用量”。
- Web 与小程序流转字典中的“半成品绑定/成品绑定”改为“半成品入库登记/成品入库登记”。
- 成品任务接口文档由“绑定半成品明细”改为“登记半成品用量”。
- 小程序二维码详情中的“已被成品绑定消耗”改为“已被成品生产消耗”。

## 小程序端差距

小程序当前只有 `bindSemiItemsToTask` API 包装，没有页面使用该 API，也没有“选择备料池批次 + 登记 x 板 y 件”的表单。因此小程序端可以确认成品入库位置和数量，但不能独立完成新版“登记半成品用量”动作；如果现场需要在小程序端直接登记半成品用量，需要新增对应 UI。

## 后续风险

- `InStockServiceImpl.java` 存在大量历史乱码注释，本次未触碰业务逻辑，后续如果继续改该文件，建议单独做一次注释清理，避免编码污染继续扩散。
- 普通出库服务仍支持按件部分出库并扣减 `inventory.pieces`，这是库存出库能力，不属于“新散件补旧散件行”逻辑；本次未改。
