# 来宾糖厂仓储管理系统：基础业务面试问答

## 1. 一句话简介

这是一个面向糖厂仓储现场的 WMS 系统，覆盖产品资料、化验质量、入库、出库、库存、库位、二维码托盘流转、生产订单和操作审计，提供 Web 管理端和微信小程序双端协同。

面试时可以这样说：

> 这个项目不是普通 CRUD，而是围绕“产品、质量、库存位置、二维码托盘、生产订单”建立的一套仓储闭环。核心目标是让每一板/件糖品从生产、化验、入库、库位占用、出库到流转记录都能被查询和追溯。

## 2. 项目背景

糖厂仓库现场有几个典型问题：

- 产品规格多：黄冰糖、白冰糖、半成品、成品，不同包装、重量、每板件数不同。
- 仓库位置复杂：库位、左/右侧、排、层共同决定库存位置。
- 质量数据重要：出入库需要关注产品生产日期、化验结果、质量标准。
- 托盘可复用：二维码状态会在 `FREE`、`PENDING`、`INSTOCK`、`INVALID`、`ORDER_RESERVED` 等状态间流转。
- 生产与仓储边界容易混乱：系统需要既支持生产订单追溯，又避免 WMS 变成完整 MES。

## 4. 核心业务模块

### 产品与基础资料

产品包含名称、类型、状态、包装方式、单件重量、每板件数、是否可堆叠、筛网规格等字段。

设计重点：

- 产品类型限定在黄冰糖、白冰糖等业务范围。
- 产品状态区分半成品和成品。
- `piecesPerPallet` 是板/件换算的核心字段。
- 半成品入库要求产品配置筛网。

常见问法：

> 为什么产品表里要有每板件数？

可回答：

> 因为现场库存既会按板管理，也会出现散件。系统内部需要把“几板几件”统一折算成等价件数，再反算展示成板件结构。出库扣减、散件入库、二维码拆分和生产产出都依赖这个字段。

### 化验与质量标准

化验指标包括色值、还原糖、干燥失重、电导灰分、蔗糖分、不溶于水杂质、pH。

设计重点：

- 化验记录可以按产品和生产日期查询。
- 质量标准通过产品和标准关系绑定。
- 判定结果区分合格、不合格、无标准、多候选标准。
- 化验更新不是简单覆盖，而是新建版本，保留历史。
- 删除化验时如果被库存或出入库记录引用，会阻止删除。

常见问法：

> 化验判定是怎么做的？

可回答：

> 后端会根据产品找到当前启用且生效的质量标准关系，然后逐项判断 7 个指标。每个标准项支持小于等于、大于等于、范围等比较方式。如果没有启用标准，结果是无标准；如果命中多个标准，会标记多候选并保留风险提示；如果指标缺失或越界，则判定为不合格。

### 入库

入库分为传统入库、半成品入库、成品入库、二维码任务确认入库、智能报数入库。

核心流程：

```text
选择产品和库位
  -> 校验产品、库位、筛网、化验
  -> 按板/件拆分库存占位
  -> 分配库位位置
  -> 写入 inventory
  -> 写入 in_stock / semi_product_record
  -> 更新库位容量
  -> 写入托盘流转记录
```

设计重点：

- 板和件要统一折算。
- 散件也会占一个板位。
- 库位位置由库位、侧别、排、层确定。
- 二层入库需要产品允许堆叠。
- 库位位置有唯一索引，防止并发写入同一格子。

常见问法：

> 入库并发冲突怎么处理？

可回答：

> 数据库层对 `(warehouse_id, side, row_number, layer)` 做唯一约束，对托盘库存也做唯一约束。业务层分配库位时如果遇到唯一索引冲突，会重试；超过重试次数后返回“库位分配冲突，请重试”。这样即使多个用户同时入库，也不会把两板货写到同一个位置。

### 出库

出库支持普通出库、栈式出库、托盘出库、调拨出库。

核心流程：

```text
选择产品、库位、数量、单位、优先级
  -> 查询可出库库存
  -> 按整板优先或散件优先排序
  -> 折算需要扣减的总件数
  -> 逐行扣减或删除库存
  -> 校验化验记录
  -> 写出库记录
```

设计重点：

- `unit="0"` 表示板，`unit="1"` 表示件。
- 出库不足时抛业务异常，并给出差额。
- 每个出库批次会查产品生产日期对应的化验。
- 出库和调拨类写操作需要事务保证一致性。

常见问法：

> 出库为什么不直接减一个数量字段？

可回答：

> 因为库存不是只有产品总量，还带有库位、侧别、排、层、生产日期、托盘码、化验等维度。出库必须明确扣的是哪一批、哪个位置的库存，否则后续追溯、化验、调拨和二维码状态都会不一致。

### 库存与库位

库存是系统的核心数据。库存行记录产品、库位、生产日期、数量、散件、托盘码和化验关联。

设计重点：

- 产品库存概览用于回答“某产品还有多少”。
- 库位库存用于回答“某库位有什么”。
- 库位状态用于回答“某库位满了吗、还有多少容量”。
- 库位容量通过 `curCapacity` 和 `maxCapacity` 管理。
- 平面图和扫码任务都依赖库存位置模型。

常见问法：

> 库存数量为什么有 raw 和 normalized 两套口径？

可回答：

> 因为底层库存可能同时存在整板和散件。原始字段只代表数据库存储形态，不能直接当最终展示。系统会根据产品每板件数把整板和散件统一折算，得到标准化板数、散件数、等价总件数和重量，用于前端和 Agent 回答。

### 托盘码与二维码任务

二维码是连接现场扫码、库存位置和流转追溯的关键。

核心状态：

- `FREE`：可用
- `PENDING`：已有待处理任务
- `INSTOCK`：已入库
- `INVALID`：已作废
- `ORDER_RESERVED`：生产订单预留

核心流程：

```text
生成或启用二维码
  -> 扫码绑定产品并创建任务
  -> 确认任务
  -> 写库存并更新二维码状态
  -> 出库/调拨/生产领用后释放或流转
  -> 写 pallet_flow_record
```

设计重点：

- 同一个二维码可以跨轮次复用，所以引入 `cycleNo`。
- 流转记录按轮次保留历史。
- 二维码作废、恢复、删除流转属于高风险管理操作。
- 生产订单可预留固定产品二维码，避免现场临时分配。

常见问法：

> 为什么托盘码要有 cycleNo？

可回答：

> 因为二维码会复用。如果只按二维码编码追溯，一张码第一次入库、出库后再次入库会把历史串在一起。`cycleNo` 用来区分同一二维码的不同生命周期，保证库存、流转、生产订单追溯不会跨轮次混淆。

### 生产订单

生产订单模块是轻量生产管理，不是完整 MES。它负责把半成品领用、产出登记、固定二维码预留和后续入库任务串起来。

核心流程：

```text
创建生产订单
  -> 成品订单领用半成品
  -> 预留或分配固定产品二维码
  -> 登记实际产出
  -> 创建待入库托盘任务
  -> 扫码确认入库
  -> 回写订单产出和进度
```

设计重点：

- 订单号格式为 `POyyyyMMddNNNN`，创建时加锁防止并发重复。
- 成品订单才能领用半成品。
- 领料会锁定二维码和库存，写领料快照、出库记录和流转记录，并释放半成品二维码。
- 产出二维码从固定产品码池分配，使用 `FOR UPDATE` 锁定。
- 入库确认时不信任前端传入数量，而使用后端产出码记录的数量。

常见问法：

> 生产订单和仓储系统是什么关系？

可回答：

> 生产订单不是完整 MES，而是仓储闭环的一部分。它负责解决“生产领用了哪些半成品、产出了哪些成品、这些成品对应哪些二维码、是否已经入库”的问题。生产过程中的配方、班组效率、产耗比等不是当前 WMS 的核心职责，避免系统边界失控。

### 智能报数入库

智能报数用于把现场自然语言报数解析为结构化入库草稿。

核心流程：

```text
用户提交报数文本
  -> LLM 解析产品、日期、数量、库位等信息
  -> 后端校验产品、库位、化验和二维码数量
  -> Redis 缓存批次 24 小时
  -> 用户确认后分配固定二维码
  -> 创建托盘任务并走既有入库确认链路
```

设计重点：

- 解析阶段不直接写正式库存。
- 草稿中展示缺失字段、风险提示、二维码需求和可用数量。
- 成品报数不再强制自动绑定半成品来源。
- 生产消耗信息只做备注和留档，不直接扣库存。

常见问法：

> 为什么智能报数不让 LLM 直接入库？

可回答：

> LLM 适合做文本理解，但不适合作为库存写入的最终决策者。项目里把 LLM 放在解析层，输出草稿，再由后端确定性校验产品、库位、二维码、化验和数量，最后还要用户确认。真正写库存仍走已有事务服务，避免模型误识别造成库存错误。

## 5. 架构设计思路

### 分层

```text
Controller
  -> DTO/VO
  -> Service
  -> Mapper
  -> MySQL / Redis
```

设计原则：

- Controller 只接收 DTO、返回 VO，不直接暴露 PO。
- Service 负责业务规则、事务和异常。
- Mapper 负责 SQL 和数据访问。
- 统一返回 `Result<T>`，分页统一为 `PageResult<T>`。
- 业务异常使用 `BusinessException`，错误码集中维护。

### 权限与安全

- 使用 Spring Security + JWT。
- 非公开接口默认鉴权。
- Web 登录、微信登录、手机号绑定和工号绑定共用用户体系。
- 需要当前用户时通过认证上下文获取。
- 关键增删改通过 `@LogOperation` + AOP 记录操作日志。

### 事务与一致性

典型需要事务的场景：

- 入库：写库存、入库记录、库位容量、二维码状态、流转记录。
- 出库：扣库存、写出库记录、更新库位容量、释放二维码。
- 调拨：锁定源库存和目标库位，移动库存，写流转。
- 生产领料：写材料快照、出库记录、删除库存、释放二维码。
- 生产产出：锁定固定二维码，创建产出行和任务。

并发控制手段：

- 唯一索引防重复位置和重复托盘库存。
- `FOR UPDATE` 锁定订单号、二维码、库存、库位、标签批次。
- 事务包裹多表变更。
- 冲突重试和结构化业务异常。

## 6. 主要难点与解决方案

### 难点 1：板、件、重量和库位容量口径复杂

问题：

- 现场既按板报数，也按件报数。
- 散件也会占库位。
- 不同产品每板件数不同。

解决：

- 产品表维护 `piecesPerPallet` 和 `weightPerPiece`。
- 入库、出库、库存展示统一折算为等价总件数。
- 展示层再转回“几板几件”和总重量。
- 跨规格汇总时不虚构统一板数，只展示等价件数和重量。

### 难点 2：库位位置分配和并发冲突

问题：

- 同一库位还有左/右、排、层。
- 多人同时入库可能抢同一格。

解决：

- 库存表对库位位置建立唯一索引。
- 分配失败时捕获唯一索引冲突并重试。
- 调拨和生产场景中对关键库存、库位和二维码使用行锁。

### 难点 3：二维码状态机和历史追溯

问题：

- 二维码可以复用。
- 同一码的历史流转不能混在一起。
- 入库、出库、调拨、生产领料都会改变二维码状态。

解决：

- 设计二维码状态和 `cycleNo`。
- 当前库存和历史流转都带轮次。
- 每次确认任务写入 `pallet_flow_record`。
- 高风险操作如作废、恢复、删除流转不开放给 Agent 直接执行。

### 难点 4：化验标准和历史质量可追溯

问题：

- 同一产品可能有多套标准。
- 标准可能更新。
- 出库和追溯需要知道当时的质量结果。

解决：

- 产品和质量标准通过关系表绑定。
- 化验判定保存标准快照和版本。
- 更新化验时新增版本，不直接覆盖旧记录。
- 无标准、多候选标准、不合格都作为明确状态处理。

### 难点 5：WMS 和生产管理边界

问题：

- 现场报数会包含生产消耗、原料来源、半成品领用、成品产出。
- 如果 WMS 强行承担 MES，会导致库存、二维码和生产消耗耦合过重。

解决：

- WMS 只负责库存、二维码、库位、出入库和流转。
- 生产订单只做轻量闭环：领料、产出、标签、入库进度。
- 生产消耗信息在智能报数中只做备注和留档，不自动扣库存。
- 后续如果接 MES，可通过生产订单和批次追溯接口扩展。

### 难点 6：智能报数可靠性

问题：

- 用户输入是自然语言，包含别名、日期、板件混写、备注。
- LLM 可能识别错产品或库位。

解决：

- LLM 只做解析，不直接执行写操作。
- 解析结果进入 Redis 草稿。
- 后端对产品、库位、数量、化验、二维码数量做确定性校验。
- 前端展示风险和缺失字段，用户确认后才执行。
- 写入仍复用已有二维码入库任务链路。

## 7. 项目亮点

- 不是简单后台管理，而是围绕糖厂仓储现场建立业务闭环。
- 库存模型同时支持产品、库位、板件、散件、托盘、化验和生产日期。
- 二维码任务链路把扫码、库存、流转和追溯打通。
- 生产订单把半成品领用、产出贴码和入库进度串起来。
- 化验标准有版本和判定逻辑，质量结果可追溯。
- 智能报数引入 LLM，但通过草稿、校验、确认、事务服务控制风险。
- Web 管理端和微信小程序覆盖办公室和仓库现场两类使用场景。
- 有操作日志、权限、事务、锁和唯一索引等工程化保障。

## 8. 高频面试问答

### Q1：这个项目你会怎么介绍？

这是一个糖厂智能仓储系统，核心是管理半成品和成品从入库、化验、库位存放、二维码托盘流转、出库、调拨到生产订单追溯的全过程。后端用 Spring Boot，前端用 Vue 3，现场操作通过微信小程序完成。项目难点主要在库存口径、库位位置、二维码状态机、化验质量追溯和生产订单闭环。

### Q2：项目中最核心的表有哪些？

核心有产品表、库位表、库存表、入库/出库记录表、托盘码表、托盘任务表、托盘流转表、化验表、质量标准表、生产订单及其材料/产出/标签相关表。库存表是中心，连接产品、库位、生产日期、托盘码和化验。

### Q3：为什么要有托盘任务，而不是扫码后直接入库？

扫码后直接入库缺少中间校验和协作空间。托盘任务可以承载“待入库、待出库、待调拨”等状态，支持 Web 创建任务、小程序现场确认，也方便失败回滚、追踪操作人和生成流转记录。

### Q4：出入库如何保证数据一致？

出入库服务使用事务包裹多表写入。入库同时写库存、入库记录、库位容量、托盘状态和流转记录；出库同时扣库存、写出库记录、更新容量并处理二维码状态。关键资源通过数据库唯一索引和行锁控制并发。

### Q5：项目中用了哪些设计模式或工程实践？

主要是分层架构、DTO/VO 分层、统一响应和分页、业务异常和错误码、AOP 操作日志、事务脚本、领域服务封装、只读查询与写操作分离、状态机建模、预览和确认式流程设计。

### Q6：如果让你优化这个系统，你会做什么？

我会优先补齐三块：第一是把传统出入库和二维码出入库的库存容量口径做统一测试；第二是给写接口补幂等键和更细粒度权限；第三是把生产订单状态集中成枚举和状态机，减少状态字符串分散在 Service 里的维护成本。

### Q7：项目中最大的技术难点是什么？

最大的难点是业务一致性，不是单个接口实现。比如一次入库会影响库存、库位容量、二维码状态、任务状态、流转记录、化验关联和生产订单进度。只要其中一步不一致，现场看到的库存和二维码状态就会冲突，所以需要事务、锁、唯一索引和明确的状态流转。

### Q8：智能报数为什么是亮点？

它把现场自然语言报数转成结构化入库草稿，降低录入成本。但关键不是简单接入 LLM，而是把 LLM 限制在解析层：后端继续做确定性校验，确认后复用二维码任务入库链路，避免模型直接改库存。

### Q9：你怎么理解这个项目里的 WMS 和 MES 边界？

WMS 负责仓库里的库存、库位、二维码、出入库、调拨和流转。MES 负责生产计划、配方、产耗比、工序和班组过程。这个项目里生产订单只是轻量地连接仓储和生产结果，不试图实现完整 MES，这样系统边界更清晰，也更容易落地。

### Q10：这个项目如何体现业务建模能力？

它把现场对象抽象成产品、库位、库存、托盘码、任务、流转、化验、生产订单等模型，并明确它们之间的关系。比如二维码不是库存本身，而是库存占位和流转追溯的载体；生产订单不是库存表，而是连接材料领用、产出贴码和入库任务的业务聚合。

## 9. 面试讲述模板

一分钟版本：

> 我做的是一个糖厂智能仓储系统，后端是 Spring Boot + MySQL + Redis，前端是 Vue 3，现场还有微信小程序。系统覆盖产品资料、化验、入库、出库、库存、库位、托盘二维码和生产订单。核心难点是库存不是简单数量，而是带库位、侧别、排层、生产日期、化验和二维码状态的多维数据。我们通过事务、行锁、唯一索引、二维码状态机和流转记录保证一致性，同时用智能报数降低现场录入成本。

三分钟版本：

> 这个系统面向糖厂仓储现场。业务上，产品分半成品和成品，不同规格有不同每板件数；库存要精确到库位、侧别、排、层；出入库还要关联化验结果和二维码托盘状态。  
> 技术上，后端用 Spring Boot、Spring Security、MyBatis-Plus、MySQL、Redis，前端用 Vue 3 和 Element Plus，小程序负责扫码和现场任务。  
> 我们把系统拆成产品、库位、库存、化验、托盘码、生产订单几个核心模块。入库时校验产品、库位、筛网、化验，按板件拆分库存并分配库位；出库时按策略扣减具体库存行；二维码任务负责把扫码、确认、库存和流转记录串起来；生产订单负责半成品领用、产出贴码和入库进度。  
> 难点在一致性和业务边界。比如入库要同时写库存、入库记录、库位容量、二维码状态、任务状态和流转记录，所以用了事务、行锁、唯一索引和冲突重试。智能报数引入 LLM，但只让它做解析，真正写库存仍走后端校验和用户确认。整体亮点是把仓库现场的板件库存、质量化验、二维码流转和生产追溯做成了一个闭环。
