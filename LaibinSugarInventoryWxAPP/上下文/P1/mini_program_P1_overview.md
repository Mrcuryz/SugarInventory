# 小程序 P1 阶段概述（补查询能力）

## 1. 阶段定位
P0 已完成小程序主骨架建设，已经具备：

- 登录页
- 工作台首页
- 扫码作业页
- 托盘详情页
- 任务中心
- 公共组件与统一样式体系

接下来进入 **P1：补查询能力**。  
这一阶段的目标不是继续反复微调 P0 页面，而是把小程序从“能扫码、能建任务”推进到“**能查询、能追溯、能辅助现场判断**”的状态。

---

## 2. P1 的核心目标

### 目标 1：把查询中心做成真正入口页
查询中心不再只是托盘查询占位页，而应成为移动端查询能力的总入口，承接：

- 托盘查询
- 库存查询
- 化验查询
- 作业记录查询

### 目标 2：建立完整的“查询闭环”
用户在小程序里应当能够完成以下动作链：

- 从托盘码进入详情
- 从库存结果进入托盘或库位
- 从托盘详情进入化验信息
- 从作业记录进入托盘详情
- 从查询结果回到现场作业判断

### 目标 3：继续保持“移动端优先”
P1 页面不能做成 Web 表格页压缩版，而要继续坚持：

- 卡片化
- 状态优先
- 筛选轻量
- 重点信息前置
- 以现场查询和追溯为中心

---

## 3. P1 的页面范围

P1 包含以下页面/模块：

1. 查询中心首页
2. 库存查询
3. 化验查询 / 化验详情
4. 作业记录中心
5. 我的页面
6. 使用手册 / 帮助中心

---

## 4. 推荐推进顺序

不建议平均推进，而建议按“最先形成业务闭环”的顺序来做：

### 第一批：先把查询主链打通
1. 查询中心首页
2. 库存查询
3. 化验查询列表
4. 化验详情页

### 第二批：补追溯与辅助能力
5. 作业记录中心
6. 作业记录详情
7. 我的页面增强
8. 帮助中心重构

这样做的原因是：

- 托盘查询已经有基础，最容易扩成完整查询体系
- 库存与化验是现场最常见的补充查询诉求
- 作业记录是“追溯维度”，放在第二批更合适
- 我的 / 帮助中心是收口页面，适合在主链稳定后补齐

---

## 5. P1 的统一产品原则

### 5.1 功能定位
P1 不是做后台，而是做 **移动端查询中台**。  
即：

- 不是让用户在小程序里做重管理
- 而是让用户快速查、快速看、快速判断

### 5.2 信息结构
所有 P1 页面继续保持以下统一结构：

- 顶部标题 + 简短说明
- 轻量筛选区
- 卡片式结果区
- 明确的空状态 / 加载态 / 失败态
- 详情页支持联动跳转

### 5.3 视觉规范
延续现有小程序的统一风格：

- 浅蓝灰背景
- 白色卡片
- 主蓝按钮
- 浅色状态标签
- 线性图标
- 统一圆角 / 阴影 / 间距 / 字号层级

### 5.4 数据规范
所有 P1 页面都应遵守：

- 时间格式统一
- 状态枚举统一文案
- 位置为空时不乱展示
- 化验为空时不报错
- 空列表必须有自然空态

---

## 6. P1 与后端改造的关系

P1 要建立在新的后端能力上，尤其是化验逻辑已经重构为：

- 入库不再强制要求化验
- 先查 assayId
- 再按 productId + 日期 fallback
- 唯一命中自动回填
- 化验关联进入流转记录

因此，P1 各页面中凡是需要展示化验的地方，都不能自己写死逻辑，必须使用统一后的接口结果。

---

## 7. P1 完成后的预期结果

P1 完成后，小程序应达到以下能力水平：

### 7.1 现场主链
- 扫码建任务
- 任务确认
- 托盘追溯
- 单码详情查看

### 7.2 查询主链
- 查托盘
- 查库存
- 查化验
- 查作业记录

### 7.3 辅助能力
- 帮助中心可查
- 我的页面完整
- 常用入口清晰
- 小程序整体具备正式试用版形态

---

## 8. P1 的验收标准

P1 可以认为完成，至少要满足：

1. 查询中心不再是占位页，而是真正入口页
2. 库存查询可用，且能联动托盘详情
3. 化验查询与化验详情可用，且兼容“无化验 / 自动回填 / 多候选”状态
4. 作业记录中心可用，能按时间和类型追溯现场动作
5. 我的页面不再只是信息壳子
6. 帮助中心风格与新小程序统一
7. 所有新页面继续遵守现有统一样式体系

---

## 9. 总结

P1 的本质不是“多做几个页面”，而是：

> **把小程序从扫码工具，升级为现场查询与追溯入口。**

只要 P1 做好，小程序就不再只是“扫一个码、建一条任务”，而是真正具备：

- 查询
- 判断
- 追溯
- 辅助作业

这四种现场核心能力。
